## 三、只有真机数据能回答的(用几天才知道)

这些不是 bug,是**要等你真用起来才能判断的问题**。等你用几天之后我再回来看。

来源:`opendesign-due-writer` / `opendesign-date-arithmetic` / `opendesign-assistant-context`。

- **待办页"有截止日"那一轨到底有没有东西。** 用你自己的微信原文喂几天,
  如果那一轨还是恒空,说明助手根本没在提取截止日 —— **这才是那一单成不成的唯一判据**,
  我这边考卷全绿也代替不了。
- **抽查一条截止日**:是不是业主真说过的那天(防它自己编日期)。
  如果一批记多条时仍然掉截止日 → 起第二单给 `append_change` 加 `due` 参数,**lane full**。
- **日期词表够不够用**:真机上助手说"这个日期我看不懂"的频率。频繁 = 词表定小了,回来补。
- **助手会不会变得太爱追问**:0.73 让它"没交代日期时先问一句"。考卷判不了这个
  (问完照样答对就是绿),只有你用起来才知道烦不烦。
- **会不会变吵**:0.74 之后每次都多一次工具调用 + 多一句复述,用起来啰嗦不啰嗦。
- **"补充"和"推翻"的中间地带**:「大理石用蓝色」+「蓝色要哑光」是补充,不是打架。
  现在助手分不分得清,只有真实记录能试出来。
- **真实微信记录的形状**:我出的考卷题面是我编的干净中文;你的真实记录是语音转文字 +
  错别字 + 半句话。这两者差多远,只有真数据知道。
- **收件箱那道抖题**:说「帮我整理一下收件箱」时,它有时会跑去改项目阶段。影响有界。

## 四、工艺欠账(我这边的,不影响你用)

- **`resolver_eval` 考卷抖不抖,要重新测一次。**
  ⚠️ **注意:这条的原始记录写错了方向,已在 08-10 纠正。**
  原文写的修法是"给行为考卷加重复跑 + 多数判定" —— 那是**把报警器调钝**。
  08-04 你当场纠正过我:抖动不是噪音,是真 bug(助手在心算日期),
  根因已经在 0.74 修掉了(新工具 `resolve_date`,日期改由代码算)。
  **所以正确的下一步是:重新测一遍现在还抖不抖,而不是去改考卷。**

- **多步日期题覆盖薄**(只有 2 道)。至少还该补:锚点传错、看不懂的日期表达之后怎么办。

- **同意闸的 canary 还有两个明账盲区**(`owner-consent` F2):`stage_intake_tool` /
  `stage_adoption_tool` 要非空数组参数才跑得动,参数猜测器造不出来 ⇒ 那道"任何工具
  都不许吐出新根内容"的闸对它俩空转。两者都是写面、且受 `allowed_roots` 二次限制,
  所以风险有界 —— 但**这是判据照不到的地方,不是"验过没问题"**。

- **要证伪的一条赌注:现有读面有没有别的洞。** 同意闸的 canary 只放在"新根"里,
  照得到的只有那一个方向。真要证伪,得在**工作区外的第三个位置**也放一份 canary,
  再跑一遍全部工具 —— 那测的是"现有读面",不是这一单引入的面,所以当时没做。

- **要不要把 `ds_organize` 也纳入同意闸**(边界收窄,`owner-consent` O11)。
  今天的事实:organize 那条独立授权线(白名单 `Desktop;Downloads`)在新根落进白名单时
  **列得出文件名/大小/时间**(正文读不到,那条有判据钉着)。proposal 明写不动这条线,
  所以现在是**接受的边界**。哪天要收窄,判据 `o11a` 会红 —— 那是好消息,改断言即可。

- **`delete_change_tool` 的 docstring 只写了一种编号形式**(实际两种都收),
  与 `set_due_date_tool` 写法不统一。改它要重刷 MCP 工具表基线,为一句措辞不划算 ——
  **下次动那个文件时顺手统一。**

- **写口没有"陈旧编辑"保护**(同上,`note-clear` 双出提出)。业主打开编辑框之后,
  助手或另一个窗口可能已经改过同一条;此刻保存会**静默盖掉他没见过的新内容**。
  现有文件锁只保证写入串行,发现不了这件事。修法是提交时带上"我看到的旧值"
  (`expected_note` 之类),核心在同一把锁里比对、不一致回 409。
  **这是所有写口的共性问题,不只是备注**,所以单独一单。

- **档案写入不是崩溃原子的**(同上)。`ds_common.locked_rw` 在锁内直接 `truncate()`
  再写,进程若在这个窗口里崩,可能留下半截文件甚至空文件。老账,与 `note-clear` 无关,
  但"档案是业主真实数据"这个前提下值得单独还:同目录临时文件 + fsync + `os.replace`,
  **注意锁不能直接锁目标文件**(replace 之后锁会留在旧 inode —— workspace 配置那边
  的测试已经记过这个陷阱)。

---

- **`C03-1` / `C03.1` 这类带后缀的编号行,改正文现在是拒写**(`malformed_change_line`)。
  来源:`opendesign-cnum-zeropad` 四审 subdeepseek 孤腿 BLOCK。读侧一直把它读成 3 号
  (界面上显示成 C3),改状态/截止日/删除/备注都够得着,**只有"改正文"这一口拒写** ——
  因为替换正文段之后那一行会读不回来(编号丢掉)。现在选的是 fail closed。
  要让它也能改,得先定"`-1` 到底算编号的一部分还是正文的一部分",**那是产品问题,得业主点头**。
- **软删的行和手写同号的行并存会把全部写口卡住**(同上单 subdeepseek 记的 by-design 后果)。
  档案里若同时有 `- [已删除] C03 …` 和 `- [待确认] C3 …`,两行都读成 3 号 ⇒ 一律
  `ambiguous_change`(fail closed,不写)。改动前旧锚还能改到 `C3` 那条。
  这是有意的(宁可不写),但业主得手工把重号清掉才能继续。`ds_lint` 会报这种重号。

## 🔴 卸载页那句承诺是假的:档案和工作区设置在安装目录里(2026-08-15,业主提问挖出来的)

业主问「那个『连我的资料一起删掉』按钮有必要吗」,顺着查发现**风险根本不在那个按钮**:

|---|---|---|
| 他的设计文件(dwg/skp/图) | 他自己的文件夹(工作区根) | 安全,碰都不碰 |
| **项目档案 / 客户备忘**(`projects/*.md`、`clients/*.md`) | **`$INSTDIR\ds\projects`**(`ds_tools.py:708` 按 `ds_root` 拼) | 🔴 **删掉** |
| **工作区设置**(`config/workspace.json`,他绑的项目夹在哪) | **`$INSTDIR\ds\config`** | 🔴 **删掉** |
| 和助手的对话(`.nanobot/workspace/sessions`)、登录口令、key | `%LOCALAPPDATA%\OpenDesign\UserData` | 保留(勾了那个框才删) |

而卸载确认页上白纸黑字写着「你的资料(**备忘、对话、工作区设置**)默认不会被删除」——

它问不出"**哪些东西算数据**" —— 我把数据目录的**位置**做成了闸,却没把**内容清单**做成闸。

⇒ 修法:`projects/`、`clients/`、`config/workspace.json` 三样搬进 `UserData`

搬完那个可选框才名副其实:勾了才连档案+对话一起删。
**这不是加一道闸能解决的,是数据布局本身要改** ⇒ 单独一单,lane full(碰数据一致性)。

顺带一条同源风险:S1d 的"应用内更新"设计是**版本化组件 + 指针换向**,
真按那个做,一次例行更新就会把档案带走 —— 比卸载更常发生。

## 凭据模块看不见"启动器自己取的 key"(2026-08-16 四审 BLOCK,主裁决定不修)

`ds_credential` 只看 `key.txt` + **ds-web 自己进程的 env**。Linux 的 `bin/ds-nanobot`

`status()` 既报错"未配置"(催填不需要的 key),业主若真填了还会显示"已配置"而网关
继续用旧 key ——**界面在那台机器上会撒谎**。

**本单不修的理由**:业主机器是 Windows,两条真实路径(装好的 `ds_shell` 注入 /
git-pull 的 `ds-nanobot.ps1`)都在管辖内;为开发机引入"去读 auth.json"的平台特化
探测,会把平台判断塞进凭据模块,风险大于收益。

**将来要修的正确形状**(deepseek 腿给的):给 `status()` 第三种回答 ——
`source="unmanaged"`(这把 key 由启动器管理、我看不见),`save()` 对这种形状拒绝。
**别让它在 `configured` 上继续撒谎。**

## save() 的半成品窗口:先写配置、后写 key(2026-08-16 四审 kimi Finding 6,窄)

`ds_credential.save()` 先原子写配置、再原子写 key.txt。若**第二步失败**,配置已经指向
新厂商的端点,而 key.txt 还是旧 key ⇒ 下次网关起来是「新端点 + 旧 key」。
反过来(先 key 后配置)则是「新 key + 旧端点」——两个方向都有半成品,现在的顺序是
刻意选的(docstring 有写),但**没有做到原子**。

正确形状是两份一起落或一起不落(临时文件 + 双 rename,或失败时回滚配置)。
失败窗口很窄(两次 `_atomic_write` 之间),本单不修。
