# 评审与修复规则

本仓库走 PR + 关卡流程的评审与修复,都按这份。**这是唯一的一份**:`review-pr` 每次评审前从 main 上读它和
`.aiwork/accepted-risks.md`(已接受风险清单),一起交给评审模型;`CLAUDE.md` / `AGENTS.md`、以后 OpenClaw 的
`AGENT.md` 都只引用这里,不另抄一份(抄了就会各写各的,又成了"同一件事几种说法")。

放在 `.aiwork/` 下:它属于判卷面(关卡规则 G2),**改它要业主批准** —— 受这份规则约束的 Builder 自己改不了它。
每条都写明防的是什么、删掉会怎样;说不出来的规则不加。接入第二个项目时,再把它挪到几个项目共用的地方。

**通用,加腿不用改这份文件**:这里不写任何具体的腿、家族或数量。
- 有哪些评审腿、各属哪个家族:在 aiwork 的腿登记表里(`bin/_review_result.py` 的 `ADAPTER_IDENTITIES`);
- 一个 PR 要几条腿、要哪几个家族才能放行:在项目的关卡策略里(本仓库是 `.aiwork/policy.json` + 关卡规则 G3 / G6);
- 这份文件只规定"每条腿怎么审、修改方怎么修、什么时候停",对一条腿、十条腿都一样。
以后加腿、换腿、加 QA 这类新的检查者,只改登记表或项目策略。

下文"评审方"指任何对 PR 给出 PASS / BLOCK 结论的一方(评审腿,以后的 QA 腿等),"修改方"指这个 PR 的 Builder;
多腿、多 PR 并行时额外的约定见第四节。

**一轮** = 当前 head 上**项目策略要求的**评审方都给出结论 → 修改方把这些结论里所有 P1 一次修完、推一次。
轮数按 PR 算,跟有几条腿无关。

来历:OpenDesign PR #10(放行关卡)评审修改了 13 轮、修了 37 个问题。前几轮找到的都是真漏洞;
越往后越窄,而且好几轮是在补丁上再补丁,直到第 9 轮换掉错的前提,代码反而少了约 60 行。这份规则就是那次的教训。

## 一、修复方:按第一性原理修,不堆屎山(最重要)

> 防的是:每轮修一个"点",修法是加一个特例、一个 if、一个白名单;下一轮评审在旁边又找到一个同类的点;
> 几轮下来代码里同一件事有好几种说法,谁也说不清哪个算数 —— 这就是屎山,也是评审停不下来的根源。
> 删掉会怎样:评审轮数越修越多,代码越修越乱。

### 1. 动手前先回答三个问题

1. **这个概念是不是有两种以上的说法?** 同一件事在两处各算一遍、各写一遍、各有一套判断。
   例:评审的"生效时刻"一处按提交时间、一处按撤销时间;"正文结论"和"结论块"是同一个结论的两种写法。
2. **是不是某个前提本身错了?** 同一类问题换着花样反复出现,多半是前提错了,不是缺一个特例。
   例:"从哪个事件叫醒它去推该算哪个 PR"这个前提,连着漏了好几轮,换成"每次都全算一遍"就一次性没了。
3. **我是不是在已有的补丁上再加补丁?** 修法如果是"在这里再加一个特殊情况",先停下来重想。

### 2. 修法的标准

- **一个概念只留一处定义**,其他地方都用它。修完之后,规则应该**更少、更一般**,而不是特殊情况更多。
- **同类一起扫**:修一个问题时,把它所属的那一类在整个项目里扫一遍,最好写成"从仓库推出来"的测试
  (例:高风险清单不是手工补一个文件,而是写一条规则让测试把所有该进清单的文件推出来)。
  这是评审能收敛的关键:不扫,下一轮就会找到它的"兄弟"。
- **被取代的一起删掉**:旧的特殊处理、只为它存在的测试,随新修法一起删。代码量不降反升,要在 PR 里说明为什么。
- **不能用"不可能发生"来搪塞**;真是平台做不到的(见第三节),写进已接受风险清单,由业主拍板。

### 3. 修的步骤

1. 按评审描述**原样复现**(写一个会失败的测试,或一段能跑的复现);
2. 按上面的标准找根源、定修法;
3. 修,确认复现的测试变绿、其他测试不受影响;
4. 在 PR 说明里逐条写:评审发现 / 修前表现 / 修后表现 / 根源 → 修法 / 钉住它的测试。

### 4. 提交前自查

- [ ] 这次改动有没有让某个概念多出一种说法?(有 ⇒ 收成一处)
- [ ] 同类问题在别处还有没有?(扫过了吗?推导型测试有没有覆盖?)
- [ ] 被取代的旧代码、旧测试删了没有?
- [ ] 注释、文档、测试说的和代码做的一致吗?
- [ ] 新测试在修之前的代码上是红的吗?(不红说明没测到点子上)

## 二、评审方:分级,一次报全

> 防的是:评审把所有问题都当成"必须修",一轮挤一条,合并永远等不到。
> 删掉会怎样:回到 PR #10 前 12 轮的样子。

### 1. 三级

| 级别 | 什么算 | 拦不拦合并 |
|---|---|---|
| **P1 必须修** | 正常使用中会出错:结果错、丢数据、安全漏洞、该拦的没拦(关卡误放行)、程序崩溃。**必须附能复现的具体步骤或测试**,拿不出复现的不算 P1 | 拦 ⇒ 结论 BLOCK |
| **P2 记下不拦** | 发生条件极端、只影响显示或时效、性能、可维护性 | 不拦;写进评审正文,修改方记入待办 |
| **P3 可选** | 写法、风格、命名建议 | 不拦 |

**屎山也算问题**:本 PR **新引入**的"同一个概念两种说法""补丁叠补丁""测试和代码各说各的"算 **P1**
(现在改最便宜,留下来以后就是下一轮评审的源头);本 PR 没碰的老代码里的,算 P2。

**已接受风险**:`.aiwork/accepted-risks.md` 里列的(业主已拍板接受的平台上限),不当问题报。

### 2. 评审方的义务

- **一次报全**:每轮把能找到的 P1 一次报完,不留到下一轮。
- **结论只看 P1**:有 P1 ⇒ `Conclusion: BLOCK`;没有 ⇒ `Conclusion: PASS`,P2 / P3 写在正文里当建议。
- 每条 P1 写清:在哪个文件哪几行、怎么触发、实际得到什么、应该得到什么。

## 三、刹车:防止无限审查

> 防的是:评审和修改一轮接一轮,谁也不知道什么时候算完。
> 删掉会怎样:PR #10 那样的 13 轮。

1. **修改最多 3 轮**(业主 2026-09-28 的决定)。第 3 轮修完还有 P1 ⇒ **停,交业主**,附一段说明:
   每轮找到几条、是不是在收敛、剩下的是什么。业主从三条里选一条:
   - 再给几轮;
   - 剩下的记为已接受风险(写进 `.aiwork/accepted-risks.md`,业主批准),直接合;
   - 推倒重新设计。
2. **同一类问题连续两轮出现 ⇒ 换思路**:说明前提错了,按第一节第 1 条的第 2 问重新设计,不许再补。
3. **只报不拦的功能**(比如关卡的 shadow 阶段):没有 P1 就合,靠真实使用发现剩下的问题。
4. **P2 / P3 不开新一轮**:修改方可以顺手改,也可以记待办;不因为它们再请一轮评审。

## 四、多条评审腿、多个修改方并行

> 防的是:几条腿各报各的、一条一条推修复让评审追着 head 跑;几个 PR 并行时各自给同一件事发明一种说法,
> 合进 main 之后才发现 —— 屎山从 PR 之间长出来。
> 删掉会怎样:并行越多,返工越多,main 上同一概念的写法越多。

**多条评审腿审同一个 PR**

1. **各审各的、互不参考**:每条腿独立审同一个 head,不看别的腿的结论(否则就不算一次独立的评审)。
2. **合并处理**:修改方把所有腿的发现合在一起、去重,按 P1 / P2 / P3 归类后**一次修完、推一次**;
   不要来一条修一条、推一次(每推一次 head 就变,所有腿都得重审)。
3. **严重程度有分歧**:一条腿说 P1、另一条说不是 ⇒ 看能不能复现。修改方复现得了就按 P1 修;
   复现不了,在该评审下回复复现的尝试和结果;还是说不清 ⇒ 交业主(不在腿之间来回辩)。
4. **一条腿的有效 BLOCK 就是 BLOCK**,不因为另一条腿 PASS 就抵消。
5. PR 说明里每条发现注明是哪条腿提的。

**多个修改方并行**

1. **一个 PR 同一时间只有一个修改方**。要并行就拆成几个 PR,不要两个 agent 同时往一个分支推。
2. **一个概念同一时间只在一个 PR 里改**:派活时(以后由 OpenClaw)按"改的是哪块概念"分,
   两个任务要动同一个概念(同一个判定规则、同一份配置结构、同一个公共函数),就排队或合成一个 PR。
3. **动手前先看 main 和开着的 PR**:要新加一个概念、函数、配置项,先确认 main 上和别的开着的 PR 里没有同义的;
   有就复用,或者先停下来商量,不要各写一份。
4. **后合的负责统一**:两个 PR 合进 main 之后才发现各写了一份同义的东西 ⇒ 后合的那个(或它的后续 PR)
   负责收成一处,这算它的 P1。
5. **评审进行中不推**:这一轮的腿还没审完,修改方不往这个 PR 推新提交(除非修的是 CI 红),
   否则评审作废、白审一轮。

## 五、落地

| 谁 | 怎么用这份规则 |
|---|---|
| `review-pr`(本机) | 每次评审前从 PR 所在仓库的 main 上读本文件 + `.aiwork/accepted-risks.md`,放进给评审模型的任务书 |
| `.aiwork/accepted-risks.md` | 业主已接受的风险;在 `.aiwork/` 下,属于判卷面:改它要业主批准,Builder 自己加不进去 |
| `AGENTS.md` / `CLAUDE.md` | `AGENTS.md` 只写一句"处理评审按 `.aiwork/review-rules.md`",不抄内容;`CLAUDE.md` 只导入 `AGENTS.md`。它们也在判卷面里,改了要业主批准 |
| OpenClaw(阶段 E) | `AGENT.md` 引用本文件;负责数轮数、到第 3 轮就把说明交给业主;派活时按概念分,同一概念不同时派给两个 PR;等一轮的腿都审完再让修改方动手 |
