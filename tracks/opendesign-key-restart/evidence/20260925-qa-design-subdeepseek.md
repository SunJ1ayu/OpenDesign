我先看了这一单的 design/proposal/verify 与上一版 QA 测试设计简报(不读实现代码),下面是**一个**方向的测试设计。

Direction: 「自控假厂商端点当量尺 + 一条不断的会话」——把 key 是否生效/是否扣错家变成可观测事实,所有用例都挂在同一条会话主线上做扰动注入

Core bet: 黑盒条件下,唯一能证明「下一句起真的用了新 key」和「没有扣到别人家钱」的证人是**我们自己控制的 OpenAI 兼容端点**——通过产品自带的「添加供应商」把它接进去,它记下每次请求的到达时间、Authorization、model。赌的是这个入口足够产品化(能填任意 Base URL、能被聊天真实调用),于是不读一行实现就能把「生效/没生效/错家」从"看不见"变成"有收据"。**假设**:Windows 真机(或云 Windows)可达;端点能被产品回环直连;另备一把真厂商便宜 key 做一次对照。**次赌**:用户可见层(有没有「连接不上」、按钮在不在、能不能换厂)是最终判据,端点日志只是证人——两者都要,不能只留一个。

How it works:

## 0. 台面(搭一次,全程复用)
- **仪器 A:假厂商端点**。本机起一个 OpenAI 兼容服务,每个厂商一个路径(`/v1fake/deepseek`、`/v1fake/custom`…),记录 `到达时间 | Authorization | model | 是否流式`;可按开关切 `401 / 500 / 挂起不答 / 慢 30s`。产品里用「添加供应商」把它当一家接进去。
- **仪器 B:同机真网关不在监听层面的"断电开关"**——只在需要模拟"服务起不来"时用,不改产品文件。
- **仪器 C:录屏 + 聊天页截图**,盖住仪器 A 盖不到的界面层。
- **主线会话**:开机 → 填第一家 → 聊一句 → 存第二家 → **同一条会话**接着发 → 换模型 → 再发 …… 全程不断会话。每个用例是这条主线上的一次扰动。

## 1. 用户故事 + 验收标准(用户看得见的结果)

- **US1 连着聊时新填一家** — Given 聊天连着、正在用 A 家;When 在设置页填 B 家 key 并保存;Then 不退出软件,页面没有出现「连接不上」,输入框右下角换模型按钮一直在,下一句回复由 B 家给出(端点 B 收到请求)。
- **US2 全新安装第一把 key** — Given 从没填过任何 key、聊天服务没在跑;When 填第一把并保存;Then 出现「正在启动后台服务,稍等片刻」,几秒内聊天页自己变成能发消息(不需要退出重开),第一句能收到回复。
- **US3 改当前那家的 key** — Given 正在用 A 家且 key 是好的;When 把 A 家 key 改成一个错的并保存;Then 下一句**明确报错**(不是静默、不是继续用旧 key 悄悄扣钱),界面能让我把 key 改回去并立刻恢复。
- **US4 换模型仍在聊天框** — Given 已存了 A、B 两家;When 点输入框右下角按钮;Then 列出"已填 key 的厂商"含 B,选 B 后下一句由 B 家给出;设置页模型列表**不承担**换模型(那里仍只有测试/编辑)。
- **US5 存 key 不换我当前用的模型** — Given 正在用 A 家模型;When 存 B 家 key;Then 当前模型仍是 A,直到我主动在聊天框里换。
- **US6 自动更新之后** — Given 已存 key 并选好模型,软件自动更新到带本修复的新版;When 更新完打开;Then key 与当前模型都还在,能直接接着聊。

## 3. 探索式测试任务(做好后拿真界面去试)

- **E1 断线迷宫(不重启软件走出来)**:目标是穷举"坏状态"——每一处坏状态都只用界面走:出错后能不能改对、能不能换到别家、能不能重试。重点看有没有哪一条坏状态是**只有退出重开才能出去**的(那正是这一单的病根,不许它换个地方复发)。
- **E2 会话连续性的体感**:同一条会话里连续存 5 次不同家的 key、来回切 10 次模型。重点看回复**有没有串台**(选了 B 结果答话的其实是 A)、有没有重复发送、有没有消息顺序错乱。仪器侧逐条比对"这一次到底是哪家答的"。
- **E3 时间感**:从点保存到"能发出下一句"的体感时长;首装起服务那几秒界面上有没有"在动"的信号(转圈/文字变化),会不会让人以为死了。重点看有没有静默的空白期。
- **E4 提示不说假话**:把界面上出现的每一句提示,和仪器 A 上真实发生的事逐条对照。重点抓"还没生效却自称已生效/已重启"——上一单为这句改过两轮,这单不许再犯。
- **E5 钱的路径**:在端点侧核对每一次发送打到了哪一家、带哪把 key。故意把 A 家的 key 填进 B 家(或填反两家),看产品是**报错**还是**静默扣到别家**。重点:P0 的"扣错钱"只能这样看见。

## 4. 需要产品负责人拍板的疑问

- **Q1** 首装时"起服务"失败,给不给我一个能自己走出去的按钮(重试 / 手动启动)?出事那几分钟我除了退出重开还有别的路吗?
- **Q2** key 填错时能不能保存?(先存后试 = 下一句才炸;先试后存 = 填错就存不进去)这决定 T08/T09 判谁对。
- **Q3** 保存失败和"保存上了但连不上"要不要用两套不同的提示?现在听起来是同一句,我会分不清该重填还是该等。
- **Q4** 老装法「请手动重启」——我怎么知道自己是老装法?只给这句话我会当成 bug 上报。
- **Q5** 首装"几秒后自己连上"上限是多少?超过上限之后界面做什么(继续转 / 报错 / 给按钮)?

Best at: 把这一单最贵、最难判的三件事变成有收据的事实——**新 key 真的生效了没有、谁在答话、钱扣给了哪家**;失败路径和组合场景有了统一的注入器(端点开关),不必为每条用例单独造环境;同一条会话主线让"聊天断开"这类只在真实连续使用里才暴露的问题有地方显形。

Sacrifices: 台面成本高(要先搭假端点、接进"添加供应商"),比一份纯点界面的用例表慢;只能覆盖"走得通网络"的路径,**Windows 管道卡死那处判据测不出来**,必须靠云 Windows 上用修好的包真跑一次首装存 key(这是这一单的必要非充分证据);真厂商对照只跑一次便宜的,别的厂商的鉴权怪癖(如 GLM 套餐/按量)不做穷尽。**当它不合适**:如果这一单只改文案不改机制,或者产品不允许接自定义 OpenAI 地址时,这套仪器直接失效,退回纯界面用例表。

Blind spots in the brief:
- **"扣错钱"被列为 P0,但 brief 没给黑盒看见钱的办法**。不通过"添加供应商"接一个自控端点,这一档实际上测不了——测试设计里必须自己补上这个仪器,否则 P0 是空的。
- **流式中途存 key 的期望没人定**。brief 只保证"聊天不断",但没说"正在回的那半句"是保留还是掐断;这是最真实的组合场景,现在落在灰区。design 的 L 组也没回答。
- **"几秒后自己连上"没有上限,也没有超时后的行为**。判据只能靠体感,最后会变成主观争论;而 design 自己记着真机冷启动见过近 4 分钟。
- **提示语只给了一个例子,没有状态清单**。失败态该说什么、哪个状态允许说"已生效",brief 不说,测试就无法判这句提示是"对"还是"假话"。
- **"老装法"没有可判定的定义**。"仍提示手动重启"这条测试写不出 Then——用户怎么知道自己是老装法?是不是该提示、提示够不够?
- **单网关假设没写**。多窗口/多工作区时"聊天不断"在哪一层成立,brief 与 design 都没定,而这是最容易在真机上下不来台的邻接面。
- **自动更新只在一句跨功能里被带过,但它本身就是"运行时重启"**。更新后 key 与当前模型还在不在,是这一单最近、最容易一脚踩塌的邻接面,值得单独一条故事。
- **GLM 套餐 vs GLM 按量是"同厂商两家"**,换模型列表里怎么标、key 会不会串,黑盒测试没法从 brief 判断该期待什么。

Smallest first step: 先只验证**仪器通路**:本机起一个只记「到达时间 + Authorization」的假 OpenAI 端点,用产品的「添加供应商」接进去,真机上聊一句,确认端点真的收到了那把 key。这条不通,T02/T08/T09/E5 全部作废——半天内能给出结论。
