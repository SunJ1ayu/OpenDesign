# 主 agent 自己的方向(派独立挑战前落盘,不喂给独立腿)— 2026-09-21

## 我倾向的方向:A「后台同时拿着所有已配厂商的 key,切换 = 只改当前预设,不重启」

- key 存储:`<home>/.openDesign/keys/<vendor>.txt` 每家一个文件(原子写、同一套不变量)。
  老 `key.txt` 在第一次被新代码碰到时归入「配置当前 apiBase 认出来的那一家」的槽位。
- 配置:每家一条 nanobot 自定义 provider(例 `providers.od_mimo` / `providers.od_deepseek`),
  `apiKey: "${DS_LLM_KEY_<VENDOR>}"`;预设 `provider: od_<vendor>` 强制路由(实验已证 nanobot 0.2.2 支持)。
- 外壳 build_env:对配置里**每一个**引用到的厂商变量都注入(有 key 注入 key,缺 key 注入空串,
  避免「缺一个变量整份配置加载失败」);key 只进网关那条腿不变。
- 填/换某家 key ⇒ 仍要重启网关(env 只在启动时读),与今天一样走锁通道;
  在已配好的厂商之间切换 ⇒ 只写 modelPreset,下一句生效,不重启。
- 模型菜单:按厂商分组列出所有「已配 key」厂商的模型;状态以 ds_web 读到的配置+key 文件为准。

## 我认为最危险的前提

1. **静默不切换**:网关每条消息前重读配置,读失败就 logger.exception 后保留旧 provider。
   只要配置引用了一个网关进程 env 里没有的变量(例:刚存了 DeepSeek key、重启没成功),
   之后**所有**切换都悄悄不生效,而界面显示已换 —— 这是本单最大的「界面撒谎」风险。
   我的对策(未验):外壳总是为配置里每个厂商变量注入值(空串兜底);但「刚存新 key 还没重启」这段窗口仍在。
2. **老配置迁移**:业主机器上 `providers.custom` 现在可能指 MiMo 也可能指 DeepSeek(取决于最后一次 save);
   迁移要按 apiBase 认厂商,认不出(Linux 的 MIMO_TP_KEY、手改过的)就不能动。
3. **别的启动器**:`bin/ds-nanobot.ps1`(git-pull 两台)只设 DS_LLM_KEY;若那边的界面也迁移了配置,
   它会因为缺变量起不来。要么同步改它,要么非外壳形态不迁移。
4. **Windows 上重启网关要多久没量过**(Linux 量到 ~2.3s 到 ws 就绪;S0 真机冷启动见过近 4 分钟)——
   这决定 B 路线(见下)的可接受性,我没有数据。

## 另一条路 B(没选,但记下为什么)

key 按厂商分存,`key.txt` + `${DS_LLM_KEY}` + `providers.custom` 继续表示「当前那一家」;
切换 = 把那家的 key 抄进 key.txt、改 apiBase/预设、请外壳重启网关。
优点:启动器/配置形状/合并脚本一概不动,风险小得多。
缺点:每次换厂商都重启网关(对话断一下、要等,git-pull 那两台要手动重启)。
没选的理由:业主要的是「来回换」,我在对照页写了「点一下就换」;但**这句是我写的,不是业主说的**,
所以这条理由本身要被挑战。
