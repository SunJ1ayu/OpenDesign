## 定案:`design.md` 未知 #1 有答案了

**不走 pythonnet 的 `NativeWindow` 子类化(P0 已证伪),走 ctypes 的
`SetWindowLongPtrW(GWLP_WNDPROC)` 经典 Win32 子类化。**

真机证据逐条:
- 原 proc 返回 `0x1eb476f96bc`(非 0)⇒ 挂载真的成功了,不是静默失败;
- 窗口过程被调用 **15** 次 ⇒ 消息流确实流经我们;
- 收到 `WM_NCCALCSIZE` 1 次,`return 0` 之后
  **`ClientSize` 从 (384,261) 变成 (400,300) == `Size`**
  ⇒ 标题栏那块非客户区**被完全吃掉了**,而这正是方案 B 的核心动作。

对照 P0 同一台机器同一个判据:`called=0`、`ClientSize (384,261) < Size`。
**两条路的差别不是"调得好不好",是"接没接上"。**

## 实现时必须照抄探针的三个细节

1. **回调对象要一直活着。** `WNDPROC(my_proc)` 那个对象被 GC ⇒ Windows 回调进野内存 ⇒ 崩。
   探针里靠局部变量 `hook` 撑住;实现里必须挂在实例上(`self._wndproc_hook`),
   **不能是局部变量**。
2. **不接管的消息用 `CallWindowProcW` 交回原 proc**,不是 `DefWindowProc` ——
   WinForms 自己那层还在下面,绕过去会丢掉它的处理。
3. **argtypes/restype 全声明。** 64 位上句柄和返回值被静默截成 32 位 ⇒
   "改了等于没改"且哪儿都不报错(项目既有判据 `test_win_ctypes_decls.py` 机械查)。
   探针里 `SetWindowLongPtrW` / `CallWindowProcW` / `SetWindowPos` 三个都声明了。

## ⚠️ 探针**没有**回答的(不许当成已验证)

- **最大化时的客户区修正没测。** 探针只跑了普通状态。带 `WS_THICKFRAME` 的窗口
  最大化时会向外溢出一圈边框宽度,不修正就会盖住任务栏 / 内容被切 ——
  WinFormedge 的 `AdjustMaximizedClientRect` 就是干这个的。**这是下一个要单独验的点。**
- **没在 pywebview 建的窗口上挂过。** 探针用的是自己建的干净 `Form`;
  pywebview 那个窗口已经被 WinForms subclass 过一层,我们再挂一层是链式的,
  理论上一样,**但没验**。
- **解挂时机。** 探针在关窗口前解挂;真实场景里窗口销毁、fullscreen 切换、
  DPI 变化都会重算样式,什么时候要重挂/重贴,没测。
- **多线程。** 探针全程在主线程;实际 `js_api` 的调用来自 pywebview 的工作线程,
  现有代码靠 `_on_ui` 回到 UI 线程 —— 挂载这件事必须也在 UI 线程做,未验。
