# Proposal: opendesign-stage-timer

- Date: 2026-08-02
- Status: open

## Goal

让每个项目在档案里记下**阶段变更流水账**,并据此在界面上显示「当前阶段已经待了几天」。
助手侧同一条路:设计师说「进效果图了」→ 阶段改了、日期同时落账。

## Motivation

设计师的痛点是「哪个项目卡住了」。现有的「⛑ N 天没动静」量的是**档案最后更新日**
(记了一条变更就清零),量不到「这个项目在方案深化已经泡了三周」。

**现在做而不是以后做的硬理由 = 数据不可逆。** 阶段变更日期档案里一个字都没存
(`set_stage` 只替换头部 `- 阶段:` 那一行)。代码以后能改,**没记下来的日期永远补不回来**。
用户拍板:「当然是一起记上」。

## 真问题(第一性)

- 用户原话(2026-08-02):
  - 「要不先一起做完阶段计时器我再一起看」
  - 「我觉得可以,但是这个入口做在哪里,我觉得还是需要可以ai助手一起写入的功能,
    比如在平面阶段,然后我比如待办或者跟助手说进入某某项目进入效果图阶段,
    他就会一起改动」
  - 「当然是一起记上,每个项目记得分开记录,不要出现屎山代码」
- 真正要解决的是:**一眼看出哪个项目在当前阶段泡太久了**;并且录入这件事
  **不能只有界面一条路**——他日常是跟助手说话,不是点界面。
- 我在这中间翻译了什么:
  - 「入口做在哪里」→ 我翻译成**两个入口共用一个底层写口**(助手工具 + 界面),
    而不是做两套逻辑。助手那条路其实**已经通了**(`set_stage_tool` 早就存在),
    本单只是让它顺手把日期落下来。
  - 「每个项目记得分开记录」→ 流水账存在**各自的项目档案里**(`projects/<项目>.md`
    新增 `## 阶段历史` 段),不建全局日志文件。这也正好是本仓既有的存储哲学
    (项目档案是单一真相源)。
  - 「不要出现屎山代码」→ 落成两条硬约束,写进 design.md D1/D2:
    **①同一个事实只存一处**(不再在头部加 `- 阶段起始:` 与流水账重复);
    **②不造第二套解析**(段落定位/追加复用 `log_communication` 先例,
    日期校验复用 `set_due_date` 先例)。

## Scope

- in:
  1. **数据**:项目档案新增 `## 阶段历史` 段,append-only,一行一条
     `- YYYY-MM-DD 阶段名`。段缺失自动补建(`log_communication` 先例)。
  2. **写**:`set_stage` 在阶段真的变了时追加一条;新增可选 `since` 参数用于
     **补录/纠正**(旧项目、或助手把日期算错了要改)。
  3. **读**:当前阶段起始日 = 段内最后一条;`list_projects` / `read_project` 透出
     `stage_since` + `stage_days`(缺 = None,**不拿建档日期顶替**)。
  4. **助手**:`set_stage_tool` 加 `since`,职责说明写清什么时候用(补录过去的日期)。
  5. **写口**:`POST /api/projects/stage` 键白名单扩一个可选 `since`,
     **不新开端点**(照 `/api/open-folder` 加可选 `rel` 的先例)。
  6. **界面(两处)**:
     - 工作区阶段 chip 旁显示「方案深化 · 12 天」;下拉里给一个改起始日的入口
       (未记录时显示「起始日未记录」)。**补录入口只在这里**。
     - **待办页项目卡头**(阶段标签旁)显示天数,**只读不可编辑**。
       这才是「一眼扫出谁泡得最久」的地方 —— 用户痛点的原话就是这个。
       **2026-08-02 用户拍板「要吧」**;修正见 Non-goals 那条勘误。
  7. **体检**:`ds_lint` 加一条格式校验(段内行格式 / 阶段名不在词表 / 与头部
     `- 阶段:` 对不上)。档案是人可手改的纯文本,有先例(refs-vocab 手改踩过)。

## Non-goals

- **不做阈值提醒**(「卡超过 N 天标红」)。洽谈卡 10 天和施工图卡 10 天完全是两回事,
  现在定阈值 = 我替用户猜,天天误报。先只显示天数,等他用一阵有谱了再说。
  (主 agent 决定,已当面告知用户。)
- **不做阶段耗时统计界面**(「平均在方案深化待多久」)。本单只保证**数据存下来**,
  报表是后面的事。这正是本单存在的理由——数据不存下来,报表永远做不了。
- **不改「⛑ N 天没动静」**(它量的是最后更新日,是另一个指标,两者并存不合并)。
- ~~**不在待办页项目卡上加阶段/天数小字**(据称用户 07-30 拍板「先别做」且未被推翻)。~~
  **⚠️ 勘误(2026-08-02,gpt-5.6-sol 规划双出点破):这条引用的是一条已经过期的拍板,
  我当成现行规矩用了。** 仓库现状是 `web/src/TodoPage.tsx:555` **已经**在项目卡头渲染
  `card-stage` 阶段标签,`tests/e2e/todo_one_view.e2e.mjs:199` 还有判据锁着它 ——
  **是我自己 08-01 加的**:0.69.0 todo-one-view 单的 design.md 明写「阶段从『第三个看法』
  降为项目卡头上的标签」,那份设计用户看过并通过。**07-30 的「先别做」已被 08-01 取代。**
  失败形态 = [[memory-points-drawer-owns]] 的老病(拿过期抄件当现行规矩),
  代价不只是脚注错:**它砍掉了本功能最有用的那一半**(跨项目扫一眼谁泡得最久)。
  → 现决定:**待办页项目卡显示天数,只读**(用户 08-02 拍板「要吧」)。
- **待办页那处不做补录入口**(只显示、不可编辑)。补录是低频动作,入口一个就够;
  两处都能改 = 两套错误处理 + 两套状态,正是「屎山」。点进工作区改。
- **不自动回填旧项目**。档案里没有任何线索能推出「哪天进的当前阶段」,
  拿建档日期顶替会把数字算得离谱地大。旧项目显示「未记录」,由用户补录一次。
