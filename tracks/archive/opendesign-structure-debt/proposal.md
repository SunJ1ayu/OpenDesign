# Proposal: opendesign-structure-debt

- Date: 2026-08-02
- Status: open

## Goal

把三样**放错位置**的东西挪回它们该在的地方,消掉后端仅有的两处循环依赖,
并把 `ds_web.py` 里与 HTTP 无关的 ~300 行操作系统交互独立出去。
**纯搬运:不改任何行为,用户零感知。**

## Motivation

用户 08-02 主动问了两个问题:「我们现在每一个模块是不是解耦的」「每一块代码会不会
很大,适不适合做全局的一个review」。主 agent 实测后回答,他拍板按「便宜→贵」的顺序做。

实测数据(不是印象):
- 后端 16 文件 6403 行,前端 38 文件 8052 行,合计约 1.45 万行 —— 体量本身健康。
- 但两个文件明显偏胖:`ds_web.py` **2190**、`ds_tools.py` **1537**;其余全 ≤434。
- **两处循环依赖**,都靠"把 import 藏进函数里"绕开,代码里还专门写注释辩解
  (`ds_workspace.py:159` 那段「**函数内延迟 import**……模块层反向 import 会成环」)。

现在做的理由:**总跑开关 `tests/e2e/run-all.sh` 刚上线(`611eeef`)**,31 个 e2e
一条命令 2.5 分钟跑完 + py 827 例 —— 动结构第一次有了机械兜底。顺序不能反:
没有兜底就动结构,是拿最容易改坏的一类改动去赌记性。

## 真问题(第一性)

- 用户原话:「我们现在每一个模块是不是解耦的 每一块代码会不会很大 适不适合做全局的一个review」
- 真正要解决的是:**不是"代码不好看"**,是「以后改这几块时会不会牵一发动全身」。
  用户不是程序员,他问的是**可维护性风险**,不是审美。
- 我在这中间翻译了什么:
  **把"全局 review"翻译成了"只审骨架、不逐行审 1.45 万行"。** 理由已当面讲清并获认可:
  逐行审会吐出几百条清单,九成不会修,读都读不完。**这个转译是本单的地基,写在这里
  以便被推翻。**
  第二处转译:我最初判断两处循环是「两块业务互相要对方」(大手术),
  **查证后是错的** —— 真因见 design.md,是"东西放错位置"(搬家)。
  **教训:结构判断不许凭印象,必须打开文件看成因。**

## Scope

- in: ① 分类规则表 `load_taxonomy` 从 `ds_intake` 抽出 → 消循环 ②
- in: ② `ds_web.py` 里 Windows 开文件夹/窗口置前那一块(~300 行)抽出 → `ds_web` 瘦 ~14%
- in: 两刀都要求**函数体逐字节不变**(纯搬运,见 design 的 oracle)

## Non-goals

- **不做**第 ③ 刀(29 个 MCP 工具的注册层抽出、消循环 ①)。面广、动 3 个模块的
  工具注册,值不值得做本身就是开放问题 —— **单独起 track,先用 panel-explore 问**。
- **不动前端**。三个大文件(ChangesColumn 844 / ChatPage 800 / TodoPage 689)在 React 里
  偏大但不离谱,且改动风险直接落在用户眼前。后端这两刀他一点感觉都不会有,**先做无感的**。
- **不改任何行为**。任何"顺手优化"都出界 —— 纯搬运单里夹私货,是三道闸最难抓的一类。
- 不动 `ds_tools.py` 的业务函数分层(它的胖有一半来自 ③,等 ③ 定了再看)。
