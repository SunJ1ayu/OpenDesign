# Proposal: opendesign-cnum-zeropad

- Date: 2026-08-12
- Status: open

## Goal

档案里手写成 `C03` 这种**带前导零**的变更号,读侧一直认得(`int("03")==3`),写侧却认不得。
这一单让**写侧和读侧用同一个口径认变更号** —— 变更号是个数,不是一串字符。

## Motivation

来源:`docs/backlog.md` 四、工艺欠账(`note-clear` 四审 subdeepseek 提,当时记账不修)。
**但那条记录写的症状不准**,今天先跑探针复现,真实形状有三个,严重度递增:

1. **改备注**:读出来其实是**新**的(读侧"最后一条获胜"恰好救了它),
   但档案里留下**两行备注** —— 0.83.0 刚立的"归一重复行"对它整个失效。
2. 🔴 **清空备注**:接口返回 `ok: True`、`changed_fields: []`,**档案纹丝不动**,
   读出来还是老备注。业主看到的就是「我删了它还在」——
   **和 0.83.0 刚修好的那个 bug 同一个症状**,只是入口不同。
3. 🔴 **主变更行自己带前导零**(`- [待确认] C03 …`,待办池里**根本没写这一条**):
   界面显示成 C3,但改状态 / 改正文 / 改备注 / 改截止日**全部返回 `change_not_found`**
   ⇒ 这条待办在界面上**完全动不了**,而且错误话术是"找不到",指不出真原因。

探针原文见 `evidence/probe-repro.txt`。

## 真问题(第一性)

- 用户原话:「先做2吧」(在我列的 OpenDesign 可做清单里选了这一条)。
  更早的源头是 `note-clear` 四审 subdeepseek 的发现,以及业主 08-11 那句
  「那其实现在的修法是在打补丁吗」→「直接按第一性原理整理掉」。
- 真正要解决的是:**同一个变更号,读的时候和写的时候必须是同一个东西**。
  现在读侧把它当数(`int()`),写侧把它当字符串拼进正则(`C{num}\b`),
  两边对同一行档案给出不同答案 —— 这不是"备注的 bug",是**号码归一化缺了一半**。
- 我在这中间翻译了什么:待办池把它记成"备注读写正则对不上",我把它**放大成
  写侧四处锚点的共性问题**。依据是探针:同一个根因在 `set_change_status` /
  `set_due_date` / `edit_change` / 备注锚点上各有一处,只修备注那处等于留着另外三处。
  **这是一次扩大范围的转译,写在这里备查。**

## Scope

- in: 写侧变更号定位统一归一(接受 `C0*<num>`,内部按数比对),覆盖
  `ds_tools.set_change_status` / `set_due_date` / `edit_change` 三处主变更行锚点
  + `ds_todo.note_line_re` 备注锚点。
- in: 备注 upsert 命中带前导零的旧行时,**写回规范形式**(`- C3 备注:…`),
  顺带把重复行归一掉 —— 这正是 0.83.0 那道归一化本来要做到的事。
- in: 判据钉住上面三个复现形状 + 不许误伤(`C0*3` 不能碰到 `C13`/`C30`/`C003` 以外的行)。

## Non-goals

- **不动读侧**。读侧本来就归一(`int()`),它是对的那一半。
- **不修其它手写歪法**(`- C3备注:` 少空格、全角 `Ｃ`、`C 3` 中间带空格)。
  这一单只认前导零这一种。理由:前导零是**有复现、有来源**的一种;
  其余是我坐在这里想出来的形状,没有证据说业主真会那么写。要做另起一单。
- **不改错误话术之外的任何界面行为**;不动档案格式;不加新参数。
- **不碰陈旧编辑保护(`expected_note`)和写入原子性** —— 业主 08-11 明确说先不做。
