## Approach

分三层,**判据也按这三层分开**,不混判。

### A. 纯逻辑层:新增 `web/src/chat/reconnect.ts`(零 DOM、零 ws、可离线单测)

只回答一个问题:**"第 n 次失败之后,等多久再试、还是根本不该再试"**。

- `nextDelay(failures: number): number` —— 退避序列
  `500 / 1000 / 2000 / 4000 / 8000 / 15000`,**到 15s 封顶后不再增长**。
  封顶不放弃,理由见下面的取舍。
- 抖动:实际等待 = `nextDelay * (0.85 ~ 1.15)` 随机。单机本地 gateway 谈不上惊群,
  加它的真实理由是**多标签页**:工作台常被开成两三个标签,gateway 一重启它们会同时醒。
  随机源**依赖注入**,判据里给定值 ⇒ 序列可断言。
- `shouldReconnect(reason)` —— **口令失效不重连**。`PasswordRejected` 走登录态,
  自动重连不许把它盖住(盖住的表现是:口令改了,界面永远转圈"正在重连",
  用户永远等不到那个登录框)。
- **不做次数上限**。工作台是常驻形态:合上笔记本过一夜,回来它应该自己好了,
  而不是"昨晚试了 8 次放弃了,你自己点一下"。

### B. 接线层:`ChatPage`

- `View` 增加 `{ kind: "reconnecting"; failures: number }`。`ws.onclose` 不再直接进
  `error`(今天 `ChatPage.tsx:255` 就是这一行),改为进 `reconnecting` 并挂定时器。
- **自动重连复用手动重试那条路** —— 今天的「重试」按钮做的是 `setAttempt(n => n + 1)`
  (`:666`),整条连接 effect 依赖 `[session, attempt, resume?.nonce]` 重跑。
  自动重连 = 定时器到点也 `setAttempt(n => n + 1)`。**少一条代码路 = 少一处会烂的地方。**
- 提示条措辞:`reconnecting` 前 ~1 分钟只显示一条细的「正在重连…」;
  连续失败超过阈值后文案换成「连接不上,gateway 可能没在跑」**并把手动「重试」按钮亮出来**,
  但后台**照样**按 15s 慢速继续试。用户永远有手动出口,机器也永远没放弃。
- `navigator.onLine` 的 `online` 事件 + `visibilitychange` 回到前台:
  **立即清零退避并马上试一次**。合盖恢复是主路径,靠 15s 轮询会让人等得莫名其妙。

### C. 补缺口:重连成功后对账

`attached` 之后拉一次 `/api/chat/thread/<chatId>`(**现成端点**,`ds_web.py` 已代理到
`/api/sessions/<id>/webui-thread`;`transcript.ts:109` 的 `hydrateFromThread` 已能解析,
今天开会话时就在用),用服务端历史**校正**本地 transcript。

✅ **前提已被证实,而且不是我推的** —— `docs/nanobot-ws-protocol.md` §4「重连流(断线自愈,
T6 依据)」是 T0 那期**真抓包**留下的,原话:**「断线期间的回复只落 transcript,ws 不重放」**,
并且给了三步配方:重 bootstrap → 新连接 `ready` 后对旧 chat_id 发 `attach` → refetch
`webui-thread` 补缺口。**和我上面独立写出来的 A/B/C 三层逐条对上** ⇒ C 照做。
(我原本打算花一次真机实验去验这条 —— 文档里躺着现成的实抓。**"发过的东西先去翻"
又一次成立**,记忆 [[user-already-sent-it-go-look]] 的同款形态,这次是自己的仓。)

🔴 **同一段文档照出我设计里的一个坑,差点写进判据**:
> 「重 bootstrap(旧 ws token 已被消费,复用必 401 —— **别把这个 401 误判成口令失效**)」

我 A 层写的是「`PasswordRejected` ⇒ 不重连」。**这条本身对,但边界极其危险**:
ws 握手层的 401(token 一次性、被消费过)和 bootstrap 层的 401(口令真错了)
长得一样,一旦混淆,**每次正常重连都会被判成"口令失效"、把用户踹回登录框**——
而这恰恰是断线自愈最常走的那条路,等于把功能做反。
现有 `connection.ts:128` 的 `openSocket()` 每次都重新 `bootstrap()`(注释写着
「握手 token 一次性消费,复用必 401」),结构上已经躲开了。
⇒ **判据必须钉死这条边界**(O1 加一条:ws 握手失败 ⇒ 照常重连,**不**清口令、**不**回登录框;
只有 `bootstrap` 自己返 401 才算口令失效)。这是本单最容易做反的地方。

对账用**替换**不用拼接(拼接必然出现重复气泡),但有一个已知缺口写在下面。

### D. T5b 两小项(判据与 commit 分开)

- **助手干活时的界面反馈**。⚠️ **08-04 实抓推翻了这一项的原方案**(抓包记录已补进
  `docs/nanobot-ws-protocol.md` §2,原来那里只有一句话、没有任何字段):

  原方案是「收到 tool_hint/progress → 显示一行『正在查资料…』」。真抓一次发现:
  1. 那一帧的 `tool_events[].phase` 是 **`"end"`** —— **工具已经跑完才发**。
     照原方案做,那行「正在查资料…」会在用户**等完之后**才出现,等于没做。
  2. 它的 `text` 是**空字符串**,拿不出文案;有信息的是 `tool_events[].name`。
  3. 这一轮实测 `kind:"tool_hint"` **一帧都没出现**,只有 `progress`。

  **等待期间真正在流的信号是 `reasoning_delta`(思考中一直在发)和 `goal_status:running`**,
  而前端今天把 `reasoning_*` 全忽略。

  🔴 **但我上面那句"界面确实是死的"是错的,写实现时才发现 —— 现在更正**:
  `ChatPage.tsx:786` 已经有一个"思考中"的三点动画(track opendesign-connect-ux 做的),
  条件是**派生的**:`busy && 末条消息还是用户的`。所以**用户并非看不到任何反应**。
  我是从"`reasoning_*` 被忽略"直接推出"界面没反应"的,**推错了**:那个指示器根本
  不看事件,它看的是本地状态。
  ⇒ 本项的真实价值缩小到**两条,而且第二条才是新东西**:
  1. `thinking` 改由真事件驱动,比派生条件准(派生条件在"助手没有前置用户消息就开始
     干活"、"重连后 busy 已被清掉"这两种情况下不亮);**与现有三点动画取或**,
     只增不减,不动既有行为(`waitAssistantDone` 等既有 e2e 依赖 `.thinking` 这个类名)。
  2. **活动回执**(「查了待办清单」)是**真正新增的信息**:三个点只说"在忙",
     不说"在干什么"。
  这条更正也是本单的一个教训:**我写规格时用"代码里没接这个事件"推出了"用户看不到反馈"**,
  中间隔着一个我没去看的渲染分支。

  ⇒ 改后的方案(两条,都从实抓来):
  - **等待态**:`goal_status:running` 或收到第一个 `reasoning_delta` ⇒ 显示「正在思考…」,
    第一个答案 `delta` 到达即清掉。**不展示 reasoning 正文**(那是模型的草稿,
    展示它等于把没定稿的话当结论给用户看)。
  - **活动回执**:`message`/`kind∈{progress,tool_hint}` ⇒ 按 `tool_events[].name`
    映射成一句人话(`list_todos` → 「查了待办清单」),作为**事后**的灰字活动行。
    映射表里没有的工具名 ⇒ 通用文案「查了一下资料」,**不许把工具原名甩给用户**
    (`mcp_design-studio_list_todos_tool` 那种字符串对机主是噪音)。
  - **不做进度条**:`phase` 只见过 `end`,没见过 `start`;画进度条就是编数据。
- **链接 target**:`markdown.ts` 加 `components.a` → `target="_blank" rel="noreferrer"`。
  它和 T6 直接相关:今天点助手给的外链会**顶掉工作台本页**,回来还要重连一次。
  ⚠️ `markdown.ts` 头上焊着 XSS 铁律(禁 raw HTML),这次只加 `components`,
  **不碰 `rehype-raw`**,原判据 `tests/test_chat_transcript.mjs` 的 XSS 闸必须继续绿。

## Key trade-offs / risks

- **无限重连 vs 有限放弃**:选了无限(慢速兜底)。风险 = gateway 永久性坏掉时,
  后台每 15s 打一次没人管的请求。判定它可接受:本地进程、无外网、无计费;
  而反面(用户回来发现它早就放弃了)才是这个产品真正的失败形态。
- **对账用替换会踩掉"本地已发出、服务端还没记账"的那条消息**。
  这是真缺口,不是理论风险:用户在断线瞬间敲了一句话,替换后那句会消失。
  处置:替换时**保留本地 `streaming` 中与"最后一条 user 消息尚未在服务端历史里出现"**
  的那条,其余以服务端为准。**判据必须有这一条**,否则这个 bug 会以"偶尔丢一句话"的
  形态存活很久 —— 而那正是最难被用户复现、也最伤信任的一类。
- **自动重连会不会把"口令失效"变成无声转圈**:见 A 的 `shouldReconnect`。
  这条我列为本单**最可能翻车**的地方,判据单列一条。
- **多标签页同时重连**:抖动只是缓解。不做跨标签协调(BroadcastChannel 那套),
  两三个标签的量级不值得引入新的一致性面。
- 🆕 **每次 ws 连接都会在网关那边生成一条会话记录 —— 空连接也算**(08-04 实测,
  见下面「跑基线时撞见的」)。自动重连会**提高这条的发生率**:今天只有开页面/手点重试
  才产生,以后每次自愈都产生一条。判定为**可接受**,理由三条:
  ① 会话只在**连接成功**时产生,gateway 挂着的时候一条都不会多;
  ② 退避封顶 15s ⇒ 最坏也就 4 条/分钟,且那是"连得上却挂不上会话"的异常态;
  ③ 这不是本单引入的,是协议形态(每条新连接必发新 `chat_id`,前端弃用它再 attach
  —— `ChatPage.tsx:223` 那行注释写着)。
  **但要记账**:工作台的会话列表若将来直接铺 `/api/sessions`,这些空会话会显形。
  今天不会(项目线程走 localStorage 映射),所以本单不处理,写在这里免得以后当新 bug 查。

## Alternatives considered

- **纯靠手动重试(现状)** —— 就是本单要修的东西,不再论证。
- **整页 reload 当重连**:一行代码就能"看起来自愈"。弃:会清空当前输入框里没发出的字、
  滚动位置、以及所有本地状态。**而且它会让 e2e 假绿**(页面全新了,当然"恢复"了)⇒
  判据里要专门锁死"没有发生 reload"。
- **服务端加断线缓冲/消息序号**:能根治缺口,但要动 nanobot 侧协议(非目标),
  且我们只是它的一个前端。C 那套"重连后拉全量历史对账"是**在我们这一侧就能做完**的等效解。

**协议冒烟一上来就是红的**,红在 `/api/sessions/<key>/webui-thread` = **404** ——
正是本单 C 层要依赖的那个端点。按规矩先问"是不是真 bug"、不先怀疑判据,查了:
**端点没坏,是夹具取样取错了**。证据:122 条会话里取前 25 条逐个打,
**24 条 200(`schemaVersion:3`,与文档一致)/ 1 条 404**,而那 1 条正是

刚建的那条空会话**。连上但没发过消息的会话没有 webui thread,端点如实回
`"webui thread not found"`。
⇒ 夹具已修(往下找第一条真有 thread 的会话),修完 **OK**,基线绿。
⇒ 附带产出一条与本单直接相关的事实:**每次 ws 连接都会生成一条会话记录,空连接也算**
(已写进上面的风险清单)。
> 这条也算给本单的判据提了个醒:**"重连后拉历史"在"新建的空会话"上必然 404**,
> C 层拿 404 当"没历史"处理,**不许把它当成错误弹给用户** —— O2 单列一条。

**O1 `tests/test_chat_reconnect.mjs`(node --test,纯逻辑)** —— 退避序列逐值断言、
15s 封顶后不再增长、抖动在给定随机源下可复现、`online`/回到前台 ⇒ 退避清零,
以及**两条 401 的分界**(本单最容易做反的地方,见 C 段那条红字):
`bootstrap` 返 401 ⇒ 口令失效、停重连、回登录框;
**ws 握手层的 401/关闭 ⇒ 照常重连,不清口令、不回登录框**。

**O2 `tests/e2e/chat_reconnect.e2e.mjs`(真 chromium + 真 ds_web + stub ws)** ——
沿用 `chat_image.e2e.mjs` 已验证的路子(页面里 stub `window.WebSocket` + `/api/chat/bootstrap`)。
stub 的 ws 能被判据**主动 close**,并能数出**新 WebSocket 被构造了几次**:
① 掐断 → 界面出现「正在重连…」而不是「连接已断开」;
② 到点自动新建连接、`ready` 后回到 connected;
③ **断线前的那条消息还在**(锁死"没 reload");
④ stub 的 `/api/chat/thread/<id>` 返回一条**客户端从未收到过**的助手消息 ⇒ 重连后它出现在气泡里;
⑤ 断线瞬间本地发出的那句话**没有被对账吃掉**;
⑥ bootstrap 返 401 ⇒ 回登录框,**不是**无声转圈。

**O3 `tests/test_chat_transcript.mjs` 增补**(判据按 08-04 实抓的真形状写,不按我猜的)——
`goal_status:running`/首个 `reasoning_delta` ⇒ 等待态开;首个答案 `delta` ⇒ 等待态关;
`message`/`kind:"progress"`(`text` 为空、`tool_events[0].phase==="end"` 的真样本)
⇒ 落一条活动回执且**不进 messages[] 气泡**;未知工具名 ⇒ 通用文案、
**断言渲染结果里不出现 `mcp_` 前缀的原始工具名**;`kind:"tool_hint"` 同样收下
(本轮没抓到,但不许因此崩);`turn_end` 清掉等待态与活动行;
未知事件仍然一律忽略不崩(老约定不许退化);**reasoning 正文一个字都不许出现在 messages[] 里**。

**O4 markdown 渲染断言** —— 外链带 `target="_blank" rel="noreferrer"`;
**XSS 闸原样全绿**(react-dom/server 直测,已有先例)。

### 这个 oracle 能被什么骗过?

- **纯逻辑层全绿、接线没接上**:`reconnect.ts` 的序列可以字字正确,而 `ChatPage`
  压根没调它 —— 单测照样全绿。⇒ 必须有 O2 的 ②(真的数到"第二个 WebSocket 被构造")。
  这正是 07-24 `columnCount==="3"` 全绿而正文被压成竖排的同一形态。
- **"它自己回来了"其实是页面 reload**:⇒ O2 ③ 锁死断线前的消息还在。
- **补缺口断言被本地缓存满足**:如果判据只断"重连后消息条数 ≥ N",本地本来就有的消息
  就能让它绿。⇒ O2 ④ 必须用一条**客户端从未收到过**的消息(只存在于 stub 的历史响应里)。
- **e2e 全绿但真机不灵**:stub 的 ws 关闭码/时序是我编的,真 gateway 重启时的关闭码
  未必一样。⇒ verify 里必须有一条**真机手工冒烟**:起着聊天,`start.ps1 stop` 再 `start`,
  看它自己回来 —— 这条**只有机主能做**,写进真机待验清单。
- **最难接住的一条**:自动重连让"断线"变得无感之后,**用户会不会反而不知道助手漏听了
  他刚才说的话**。这是产品面的,判据接不住,靠真机看观感(记忆里的老教训:
  截图/真机反复抓到判据接不住的观感 bug)。

## 攻我自己的题:gpt-5.6-sol 只读评审的结论(2026-08-04)

日志 `/root/aiwork/logs/reconnect-attack-oracle.txt`(98k token,只读腿,漏洞清单**只回主 agent**)。
问的是两件事:「我的考卷全绿了还能错成什么样」「设计里有没有站不住的前提」。
**主 agent 逐条判决如下 —— 全票不等于全收,不成立的也写在这里。**

### 🔴 两条是**我判据自己的 bug**(不是实现的问题,最值钱)

1. **attach 那条断言写反了。** 我断言重连后 `attach.chat_id` "不以 `chat-new-` 开头",
   而**第一条连接拿到的正是 `chat-new-1`** ⇒ **正确实现会红,硬编码一个假 id 的错实现反而绿**。
   ✅ 已改:stub 记下首个 `ready` 的 id,断言逐字符相等;并加一条前置
   (新连接确实拿到了不同 id,否则这条等于没判);stub 对非它的 id 一律回
   `error: invalid chat_id`(真 gateway 的行为),不再照单全收。
2. **历史请求的地址,我的设计和现状代码不一致,而 stub 的模糊匹配把它盖住了。**
   设计里写 `/api/chat/thread/<chatId>`,现状是
   `/api/chat/sessions/<sessionKey>/thread`(`ChatPage.tsx:197`),
   而 stub 用 `u.includes("/thread")` 一律放行 ⇒ **照我设计的文字写,真环境 404、考卷全绿**,
   而 404 又被"当没历史"吞掉 ⇒ 缺口消息永远补不回来,还没人报错。
   ✅ 已改:stub 精确匹配真实路径,别的地址一律 404;并加断言"补历史打的是那条真路径"。

### ✅ 接受并已补进判据

3. **在 `ready` 就宣告连上**(而不是等 `attached`)也能全绿 —— stub 10ms 必回。
   症状:attach 卡住时输入框已可用,消息发往还没挂好的会话。
   ⇒ 新增 `__holdAttached` 开关 + 两条断言:没回 `attached` 前**不算连上**,回了才算。
4. **退避可能被接线层每轮重置**(`reconnect.ts` 完全正确,但每次 effect 都从
   `initialReconnect` 开始),而原 e2e 第二次就成功、根本观察不到序列。
   ⇒ 新增 `__failConnect` 开关,连续失败,断言**间隔逐次变长**。
5. **拉历史 401 会被误判成口令失效。** 根据在现状代码:`connection.ts:116` 在
   "重签之后仍 401" 时同样抛 `PasswordRejected` —— **来源被抹掉了**。
   症状:口令完全正确,只因历史接口 401 就被踹回登录框并清掉本地口令。
   ⇒ 新增 `__thread401` 支路 + 两条断言:照常连上、**不许**弹登录框。
6. **`attached` 不是"历史已经可见"的屏障**(§4 只规定顺序,没承诺快照水位)。
   ⇒ stub 改成分阶段:`attached` 之前的历史快照**不含**断线期间那条,之后才含 ⇒
   在 attach 前抢跑拉历史的实现会红。

### ⚠️ 判为成立但**本单不做**(记账,不假装解决)

7. **"保留本地未记账的那句"没有可靠身份依据。** 它说得对:我设计里写的
   "保留 `streaming` 中的最后一条 user"是错的 —— 本地 user 消息在
   `transcript.ts` 里明确是 `streaming:false`(`streaming` 是助手输出的标记)。
   本地 id 与服务端 id 不同源,信封的 `turn_id` 也没存进 `ChatMessage`。
   ⇒ 本单按**文本 + 位置**处理并在判据里钉死两支(服务端也有它 / 服务端有一条更早的同文案),
   **但承认这是启发式**,不是身份匹配。真正的解法是把 `turn_id` 存进本地消息 —— 单独一单。
8. **"气泡还在"不等于"消息送到了"。** 这条最扎心:对账后那句话留在屏幕上,
   用户以为发出去了,而 gateway 从没收到 ⇒ "界面说发了,实际没听见"的永久分叉。
   ⇒ **本单不做自动补发**(proposal 里离线队列就是非目标),也**不加"未送达"角标** ——
   因为按第 6 条,"服务端历史里没有"并不能证明"没送达"(可能只是快照更早),
   标错了比不标更伤。**列进真机待验**:让机主实际断网发一句,看他怎么理解。
9. **attach 可能既不回 `attached` 也不回 `error`(永久挂起)。** 协议没给 ACK 超时承诺。
   ⇒ 记账,本单不加 attach 超时:加了就要定义"超时后算失败还是算连上",
   而这两种都可能错,没有实测依据。**列进真机待验的观察点。**

### ❌ 判为不成立 / 不采纳

10. **"扫 4401/4001 等 close code 是表演"** —— 部分对(浏览器确实看不到握手层的 HTTP 状态),
    但那组断言的作用不是"证明握手 401 被正确分类",而是**钉死"任何关闭码都不许变成 login"**。
    换句话说它防的是实现"看码行事",这个价值与浏览器能不能看到码无关。**保留原样。**
11. **"一分钟后的告警按钮 + 后台继续重试没有判据"** —— 属实,但**本单不补 e2e**:
    要跑满阈值才能断言,单条用例就得几十秒,而这条的失败形态(用户看不到手动出口)
    在真机上一眼可见。**改为写进真机待验清单**,不为它把 e2e 拖成分钟级。
12. **并发写入者的一致性语义(快照版本/水位)** —— 说得对,但那是**上游协议不提供的东西**,
    在我们这一侧无法凭空造出。本单只做到"迟到的历史响应不许覆盖重连后到达的实时事件"
    (这条已在判据里),再往上是 nanobot 侧的活。
