# Proposal: opendesign-open-front-v2

- Date: 2026-07-25
- Status: open

## Goal

「打开文件夹」在 Windows 上**真的**把资源管理器窗口提到前台;做不到时,至少让日志说清
卡在哪一步。

## Motivation

0.44.0 已经装到用户家里的机器上,**真机反馈:还是不能在最前面**。这正是那一单
verify.md 里 UNTESTED on target 那条兑现了 —— 我当时只能证明"决策逻辑与失败姿态对",
证明不了窗口真的到前面。

## 真问题(第一性)

- 用户原话:「资源管理器还是不能在最前面」
- 真正要解决的**两件事,顺序不能反**:
  1. **0.44.0 失败了什么都不说** —— 异常全吞、成功失败都不落日志、返回值只表示
     "调用过了"而不是"真到前台了"。于是真机上只剩猜:是没找到窗口?找到了被系统拒?
     还是 ds_web 根本没更新?**先把可诊断性补上,否则下一轮还是猜。**
  2. 温和手段(SwitchToThisWindow)显然不够 —— Windows 的前台权规则会拒绝后台进程,
     需要按标准做法借一次前台权。
- 我在这中间翻译了什么:用户说"还是不行",我译成"**先让它会说话,再让它更用力**"。
  没有第 1 步,第 2 步做完还是不知道成没成。

## Scope

- in:`bin/ds_web.py` 的 `_win_activate`(激活升级 + 诚实返回)与 `_win_focus_folder`
  (每次尝试落一行诊断);`tests/test_ds_web_open_front.py` 补判据;版本号 0.45.0。

## Non-goals

- 不伪造按键、不改系统的前台锁定超时设置(那类脏招会被杀软盯上,也会改用户的系统设置)。
- 不碰 `_open_folder` 的任何安全闸、不碰 rel(开单文件)分支。
- 暂不做 COM(Shell.Application)按真实路径匹配窗口 —— 若日志显示是"没找到窗口"
  (Win11 标签页/标题对不上),那才是下一步该做的,现在做属于猜。
