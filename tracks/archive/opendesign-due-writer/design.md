# Design: opendesign-due-writer

- Change: opendesign-due-writer
- Status: draft(主 agent 第一遍,未跑 panel)

> 不是开放架构分叉,不花 panel-explore:分叉只有两个(改说明书 / 加写口参数),
> 而且**哪个对是可测的** —— 考卷跑一遍就知道两步调用靠不靠谱。
> 花一轮发散去猜一件能测的事,是把 panel 当占卜用。

## 动手前核过的五个事实(2026-08-02,读源码/读依赖,不是推测)

1. **`append_change` 没有 `due` 参数**(`bin/ds_tools.py:183`,签名只有
   `project/content/ds_root/today/space/batch_title`)。上一单 tasks.md 里
   "已有 due 能力"那句是错的。截止日的唯一写口是 `set_due_date`(工具 4.1b)。
2. **`append_change` 的返回里有编号**:`{"ok": True, "change_id": "C7", "line": ...}`
   (`ds_tools.py:228`)。所以助手记完能拿到 `C7` 去调 `set_due_date` ——
   **两步调用在机制上成立**,剩下的只是模型愿不愿意、会不会做。
3. **助手知道今天几号**:nanobot 每轮往上下文注入
   `Current Time: 2026-08-04 10:30 (Tuesday) (Asia/Shanghai, UTC+08:00)`
   (`nanobot/agent/context.py:143` → `utils/helpers.py:250 current_time_str`)。
   ⇒「这周五之前」这类相对期限**助手自己能算成 `YYYY-MM-DD`**,不需要工具帮它。
4. **`workspace/AGENTS.md` 通篇没有"截止日"三个字**,工具表里也没有 `set_due_date`。
   助手对这件事的**唯一信号**是那条 docstring:「设/清一条变更的截止日。」——
   一句被动的功能描述,没说"什么时候该主动用"。**这就是空一栏的根因。**
5. **部署缺口(本单最容易漏的一条)**:`bin/install.ps1` Step 8 才把
   `workspace/AGENTS.md`+`SOUL.md`+`skills/` 拷进 `%USERPROFILE%\.nanobot\workspace`;
   `bin/start.ps1` **一个字都不拷**,install.ps1 结尾还写着"以后更新:git pull"。
   ⇒ **改了 AGENTS.md 而不重装,运行中的助手看不到。**
   本机现存的证据:`~/.nanobot/workspace/AGENTS.md` 是 **7-12** 的 5KB 旧版,
   仓库里是 **7-25** 的 16KB 新版 —— 已经飘了三周没人发现。

## Approach

**三件事,一件都不新开写口:**

### A. 职责说明写进 docstring(**主要载体**,因为它随 `git pull` 就生效)

MCP 工具的 docstring 是助手每轮都看得见的东西,而且 `ds_tools.py` 是
gateway 直接从仓库路径加载的(`config/nanobot.config.jsonc:51`)⇒
**改 docstring = git pull + 重启就到位**,不受事实 5 的部署缺口影响。

- `set_due_date_tool`:从"功能描述"改成"**职责描述**" —— 业主话里出现期限
  (几号前、这周五、下周、月底)就在记完这条变更后立刻调;`due` 只收
  `YYYY-MM-DD`,**相对说法自己按上下文里的 `Current Time` 算**;
  **业主没给期限就别设** —— "尽快""赶紧"不是期限,**编一个日期比空着更糟**
  (空着只是没信息,编的会让待办页把不存在的死线排到最前面)。
- `append_change_tool`:在已有的 batch_title 段后面加一句衔接 ——
  这条带期限的话,记完拿返回里的 `change_id` 接着调 `set_due_date`。
  (与 T4b 同一个位置、同一种口气:说明书级软约束,不是代码闸。)

### B. 操作契约 `workspace/AGENTS.md` 补齐(**冗余载体**)

工具表加 `set_due_date` 一行;「操作契约」段在第 1 条(业主提改动 → 立刻
`append_change`)后面加一条:**期限也是信息,业主说了就一起记下来;没说不许编**。
这一份是给"整体行为"定调的地方,docstring 是给"这一次调用"定调的地方,两边都写
不是重复 —— 但 A 是硬载体、B 是软载体,**考卷两边一起喂**(见 oracle)。

### C. 补上部署缺口:`start.ps1` 每次启动同步 workspace

在 start 模式最前面加一段:把 `workspace\AGENTS.md`、`SOUL.md`、`skills\*`
拷进 `%USERPROFILE%\.nanobot\workspace`(与 install.ps1 Step 8 **同一套动作**,
只是从"装机一次"变成"每次启动幂等做")。

- 只覆盖这三样 —— 都是我们的产物,用户不会去编辑它们;运行目录里的
  `memory/`、`sessions/`、`cron/`、`config.json` **一个都不碰**。
- 防御性:拷贝失败只 `Write-Warning` 不中断启动(`$ErrorActionPreference="Stop"`
  在这个文件里是全局的,必须显式 try/catch,否则同步失败会连带把启动打死)。
- 启动日志打印一行"已同步助手契约",给"运行中的目标自己报状态"留个抓手。

## Key trade-offs / risks

- **最大风险:两步调用不可靠**。助手可能记完就忘了第二步,或者把 `C7` 记串
  (一批 5 条时更容易)。这正是考卷要测的东西,**测不过就升级到"加 `due` 参数"**
  (单独一单,full lane)。先试轻的,理由是 non-goals 里那条:加参数动的是全项目
  最热的写路径,为一件能先测出来的事去动它,风险换反了。
- **考卷判的是"模型会不会",不是"模型每次都会"**。LLM 行为有方差,一次全绿
  不等于真机上条条都写。→ 缓解:考卷用 `temperature=0`,且**真正的验收信号是
  用户真机上跑几天后待办页硬轨里有没有东西**,写进 tasks.md 的待验清单。
- **C(start.ps1)在 Linux 上测不了**。这个文件头上本来就写着 UNTESTED 草稿。
  → 缓解:动作与 install.ps1 Step 8 逐字同形(有真机跑过的先例)、包 try/catch、
  失败不阻断启动;**真机首跑要用户看一眼那行"已同步"**。
- **A/B 两份说明书会飘**(改了 docstring 忘了改 AGENTS.md)。→ 接受:考卷同时喂
  两份,内容矛盾时考卷会先红;不为此加同步机制(那是又一把锁)。

## Alternatives considered

- **给 `append_change` 加可选 `due` 参数(一次调用搞定)** —— 没选,但**没被否决,
  只是排在后面**。它更可靠(原子、不用记 `C7`),且与 T4b 的 `batch_title` 完全同形;
  代价是真写口改动 → full lane 四腿全审。**决策规则先定死在这里,防止事后自我说服**:
  考卷里 `due` 相关用例**只要有一条计分用例挂**,就立刻起第二单加参数,不在本单
  反复调说明书的措辞去凑绿 —— 调措辞凑绿 = 把考卷调成"我这次的写法能过",
  就是 [[oracle 改考卷让自己及格]] 的自己版。
- **工具帮着解析相对日期(`due="下周五"`)** —— 没选。事实 3 说明助手已经知道
  今天几号,解析器是重复能力;而且解析歧义("这周五"在周日说指哪个)要么写死一套
  规则(= 锁),要么猜错写进档案。让助手算 + 让它说出来给设计师看,是更好的位置。
- **代码闸:没有 due 的变更不许落库 / 自动补默认 due** —— 直接违背用户定调,不考虑。
- **只改 AGENTS.md 不改 docstring** —— 没选:事实 5 说明它到不了真机,
  而且 docstring 才是"这一次要不要调这个工具"的最近信号。

## gpt-5.6-sol 单腿发散的对账(2026-08-02,用户点名要的第二意见,主 agent 仲裁)

brief 在 `/root/aiwork/tasks/due-param-explore.md`,日志
`/root/aiwork/logs/due-param-explore-gpt56.log`。**反锚定**:我的方向已先 commit,
且 brief 里明令它不许读本 track 的 design/verify/proposal。

**✅ 采纳(它这一轮最值钱的东西,而且不是它的结论,是它对我判卷的挑刺)**:
我的考卷只收集「整份档案出现了哪些日期」,**从不查日期挂在哪一条上**。
模型把「这周五」挂到窗帘那条而不是效果图那条,照样绿 —— 而待办页会拿着这条错挂的
日期一脸自信地展示,**比偶尔漏设更危险**。已当场补强(见 `dated_lines`),加锚不删断言。
> 这正是 [[panel-review-trust-calibration]] 反复应验的那条:**真漏的根因在我的规格/夹具**,
> 而不是实现;而且 08-01 我刚记过"判据要加锚断言防两边一起错",转头又犯。

**✅ 采纳(记进 T5/后续,不在本单做)**:
- **时间锚点错位**:设计师贴的是**昨天/上周的**微信记录时,「这周五」该相对**业主说话
  那天**算,不是相对录入时间。现在两边都按录入日算,静默错一周。
- **外部承诺 ≠ 内部完成日**:业主说"8/10 看效果图",设计师真正要的可能是 8/8 动手。
  一个 `due` 字段表达不了两者。**这是产品语义问题,不是参数问题。**

**🟡 记下但不采纳为本单动作**:它主张"加可选 `due` 但把成功标准升级"。
方向我认,**但它的证据基础和我的一样弱**——它自己也写明"仅凭三次每次八题的数据,
统计证据并不强;我的赞成主要来自领域模型和故障形状"。而我随后跑满五遍 + 补锚断言后,
**病 A(记了但日期没落档)一次都没再现**。⇒ 现在加参数是**为一个考卷里已消失的病
动最热的写路径**,不划算;等真机数据。

**❌ 驳回**:它顺手提的 `record_changes([...])` 批量工具 —— 它自己也说不做,同意。

## Test strategy (oracle)

**`tests/evals/due_writer_eval.py` —— 行为考卷,主 agent 亲自写,先 commit、先红。**

照 `resolver_eval.py` 的形状,**复用它的炉灶**(`import` 它的 `extract_tools` /
`call_mimo`,不复制第二份),但问的问题不同:resolver 问"选哪个工具"(单选),
本卷问"**你打算按什么顺序调哪些工具、参数填什么**"(调用序列 + 参数)。

- 喂给模型的东西 = **与真部署同源的三件**:`workspace/AGENTS.md` 全文 +
  `SOUL.md` + 三个 MCP 文件 AST 抽出的工具清单,外加一行固定的
  `Current Time: 2026-08-04 10:30 (Tuesday) ...`(与 nanobot 注入的格式一致)。
  **日期固定成 2026-08-04(周二)**,相对期限才有唯一正确答案
  (选周二不选周日:周日说"这周五"中文本身就有歧义,不拿歧义题当计分题)。
- 输出契约:JSON 数组 `[{"tool": "...", "args": {...}}, ...]`。
- 计分用例(每条一句设计师的话 → 断言):
  1. 明确日期「8 月 10 号之前要看到效果图」→ 序列含 `append_change`,
     且含 `set_due_date(due="2026-08-10")`。
  2. 相对期限「这周五之前改好」→ `set_due_date(due="2026-08-07")`。
  3. 相对期限「下周五」→ `due="2026-08-14"`。
  4. **反例·不许编**:「业主催得急,尽快改」→ 序列里**不许出现** `set_due_date`。
  5. **反例·没期限就是没期限**:普通一条修改意见 → 只 `append_change`,无 `set_due_date`。
  6. **一批多条只有一条带期限**:三条意见、只有"效果图周五前"那条有 →
     `append_change` 出现 3 次(带同一 `batch_title`)、`set_due_date` 恰好 1 次。
- 探针(不计分,只记录):「月底前」(→ 2026-08-31)、「下个月初」(本身就模糊)。
- 退出码沿用 resolver_eval:0=全过 / 1=有失配 / 2=环境或上游不可用。
  **不进 pytest**(要网络 + MiMo key),跟 resolver_eval 一样靠人跑。

**先红的证据**:改任何说明书之前先跑一遍,把输出存进 verify.md。
预期红在 1/2/3/6(现在的 docstring 根本没让它主动设),4/5 可能本来就绿
—— **本来就绿的用例要标注出来,不许当成本单的功劳**(T4b 栽过:
夹具里混进本来就成立的断言 = 那条等于没判)。

**这个 oracle 能被什么骗过?**

- **骗法一:考卷绿了,真机上助手照样不写。** 考卷是"单轮、干净、一句话就是一条任务"
  的理想题面;真机上设计师贴进来的是一大段口语微信,中间夹着闲聊、改口、
  "算了还是不改了"。断言全绿而真机空白,长这样:**待办页硬轨还是空的**。
  接得住这种错的只有**真机上跑几天后看硬轨有没有内容** —— 已写进 tasks.md 待验清单,
  本单不能靠考卷宣布成功。
- **骗法二:模型编日期,考卷抓不到。** 用例 4 只覆盖"尽快"这一种说法;真机上
  "过两天""赶在开工前"都可能诱它编。→ 探针里放模糊说法只记录不计分,
  真机验收时**顺手抽查一条硬轨的 due 是不是业主真说过的日子**(写进待验清单)。
- **骗法三:C 部署那半根本没生效,而考卷压根不测部署。** 考卷读的是**仓库里**的
  AGENTS.md,`start.ps1` 拷没拷是另一回事。→ 只能靠**真机启动时那行"已同步助手契约"
  + 打开运行目录看 AGENTS.md 的日期**。盘上和运行时对不上 = BLOCK,不是警告。
