# Proposal: inbox-accepts-docs

- Date: 2026-08-06
- Status: open

## Goal

收件箱不再只收图片:**PDF / DWG 及分类规则已经认识的其余格式**都能拖进去。

## Motivation

用户原话:「收件箱肯定要覆盖别的格式的 **特别是 pdf 和 dwg**」。

现状(已核实):`config/taxonomy.default.json` **早就给这些格式定好了归宿** ——
`.pdf/.doc/.xls/.ppt/.txt/.csv` → `01-资料`(auto)、`.dwg/.dxf` → `03-CAD`(suggest,
人工确认才动)、`.skp` → `04-SU`、`.max` → `05-3DMAX`、`.psd` → PS源。
也就是说**收进来之后的路早就通了**,堵死的只有入口那一道闸:
`bin/ds_web.py:322` 的扩展名白名单写死取 `IMG_EXTS`(5 种图片),
`web/src/inboxDrop.ts:10` 的前端过滤同样只认那 5 种。

## 真问题(第一性)

- 用户真正要的是:**把手上的东西丢进收件箱这个动作,对所有工作文件都成立**,
  而不是"图片有个快捷口子、别的还得开资源管理器"。
- 我在这中间翻译了什么:把"覆盖别的格式"翻译成**"分类规则认识什么,入口就收什么"** ——
  入口与归宿用同一张表,免得以后两边各长各的(那正是本机反复记账的那种债)。
  风险:白名单**不能从 `taxonomy.json` 推导** —— 那是用户可改的数据配置,
  推导等于让用户能给自己开安全闸(现有注释 `ds_web.py:244` 已经把这条钉死)。
  所以要**硬编码一份 + 判据钉住它与默认分类表不漂移**。

## Scope

- in: 上传口白名单(扩展名 + 内容校验 + 体积上限)、前端拖放过滤与提示语、
  收件箱卡文案;判据。

## Non-goals

- **聊天的 `+` 附件仍然只收图片**:助手现在读不了 PDF(内置文件工具是特意关掉的,
  读文档要等 anydoc 那条线)。让它能"附一个 PDF 发出去"= 让界面撒谎。
- 不改 `IMG_EXTS`(图墙读出面):PDF/DWG **不是图片**,不该出现在图墙。
- 不做超大文件上传:收件箱本来就是机主机器上的**真文件夹**,
  几百 MB 的 max/skp 直接拷进去更快 —— 超限时给这句话,而不是干瘪的"失败"。
