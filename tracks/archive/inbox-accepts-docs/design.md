# Design: inbox-accepts-docs

- Change: inbox-accepts-docs
- Status: draft

> 不是开放架构分叉:方向由"分类表已经认识这些格式"直接指定。不花 panel-explore。
> **是写口放宽 = 安全面**,所以 verify 走 full,且下面每条放宽都要说清"凭什么敢放"。

- 规划双出: 不适用 —— 不是新写面,是把**已有写口**的白名单从 5 项扩到 N 项;
  方向没有分叉余地(分类表是既定的),风险全在"怎么校验"而不是"往哪走"。

## Approach

### 1. 白名单:硬编码一份,判据钉住它不与分类表漂移

`ds_web.py` 现在的白名单直接取 `ds_workspace.IMG_EXTS`。改成一张**上传口自己的表**
`_INBOX_UPLOAD`:每个扩展名给三样东西 —— 允许的 MIME 集合、**magic bytes**、体积上限。
**绝不从 `taxonomy.json` 推导**(用户可改 = 让用户能给自己开闸,`ds_web.py:244` 已钉死)。
但**判据要求它覆盖 `config/taxonomy.default.json` 的全部扩展名**:
以后往分类表加格式却忘了开入口,判据当场红(反过来入口多出一项也红)。

### 2. 内容校验:MIME 不可信,改看 magic bytes

图片那套"data URL 的 mime 必须与扩展名同族"对文档**不成立**:
浏览器给 `.dwg` 的 mime 常常是空或 `application/octet-stream`,给 `.dxf` 也不稳定。
所以:
- 有稳定签名的按签名判:PDF `%PDF-`、DWG `AC10`..`AC10xx`、DXF 文本头、
  OOXML(docx/xlsx/pptx)`PK\x03\x04`、老式 doc/xls/ppt `\xD0\xCF\x11\xE0`、
  PSD `8BPS`、SKP `SketchUp`、MAX 同为复合文档 `\xD0\xCF\x11\xE0`。
- `.txt/.csv` 没有签名 ⇒ **按扩展名收,但要求内容能按 UTF-8/GBK 解码**(挡住"改名成 txt 的二进制")。
- mime 仍然查,但改成"给了就必须同族,没给(空/octet-stream)也放行" ——
  **签名才是判据,mime 只是加分**。

### 3. 体积:分档 + 超限时给一句有用的话

图片沿用 8MB。文档 32MB,CAD 64MB,SU/MAX/PSD 128MB。
超限**不是干瘪的失败**:收件箱是机主机器上的真文件夹,提示直接说
「这个文件 210MB,超过网页上传上限;直接拷进 `<收件箱绝对路径>` 更快」。

### 4. 前端

`inboxDrop.ts` 的 `OK_EXT` 跟着扩到同一组;拒绝提示改成列出**收什么**而不是"只收图片";
收件箱卡的文案同步。聊天 `+` 附件**不动**(仍 `accept="image/*"` 那一组)。

## Key trade-offs / risks

- **放宽写口本身就是风险**:多收一种格式 = 多一种"落到机主盘上的字节"。
  缓解:签名校验 + 体积上限 + 文件名闸(既有的 `PROJECT_NAME_RE`/NTFS 流/保留名那套原样复用)。
- **magic bytes 会误杀**:老版本 DWG(AC1006 之前)、被 zip 加密的 OOXML……
  误杀的代价是"拖不进去",用户还能拷文件夹;放行的代价是收下一个伪装文件。**选误杀**。
- **不碰 `IMG_EXTS`**:图墙、缩略图、参考图库读出面全靠它,PDF 进去会炸一片。

## Alternatives considered

- **从 taxonomy 推导白名单**:最省事,但等于让用户可改的数据配置变成安全配置 —— 明确否决。
- **只加 pdf/dwg 两项**:够用户这次的话,但下次加 dxf 又要动一次代码。
  按"分类表认识什么就收什么"一次做齐,并用判据锁住同步。

## Test strategy (oracle)

python 判据(`tests/test_ds_web_upload.py` 或就近扩现有上传判据):
1. **白名单与分类表同步**:硬编码表的键 == 默认分类表全部扩展名(两边任一漂移即红)。
2. 每种新格式:**签名对 ⇒ 收**、**签名错(改名的伪装文件)⇒ 拒**、**超限 ⇒ 拒且提示里带绝对路径**。
3. `.txt` 二进制内容 ⇒ 拒(没有签名的那一类靠解码兜)。
4. **既有图片行为一条不许退化**:svg 仍拒、mime 与扩展名不同族仍拒、文件名闸原样。
5. 前端:`inboxDrop` 的过滤与提示(node 判据里已有上传相关用例的话就近加)。

**这个 oracle 能被什么骗过?**

- 它验的是"服务端会不会收下",**验不了"收下之后整理流程真的把它放对地方"** ——
  那条链路(taxonomy → ds_organize → 人工确认)有自己的判据,但两者从没在**同一条 e2e**
  里跑通过。真实失败形态:PDF 收下了,却因为项目 token 判定不到而卡在收件箱里 ——
  用户眼里就是"我拖进去了,然后呢?"。**这一条只有真机/e2e 能接住,列进 tasks。**
- 也验不了 Windows 上的真实 mime:浏览器给 `.dwg` 到底送什么,只有真机知道。
  所以签名才是主判据、mime 只加分 —— 就是为了让这条不确定性伤不到人。
