# Proposal: opendesign-owner-review-0808

- Date: 2026-08-08
- Status: open

## Goal

业主(用户)本轮验收 agent 时发现两类问题,本 track 一次性修:
1. agent 建档前不核对已有项目,把已建档的"秀北小区"又新建了一次。
2. 单条待办/变更没有删除能力,agent 用"标完成"悄悄顶替用户说的"删除",且没开口确认。
   —— 借这次机会把"删除"补成正式功能(软删除/回收站式,可恢复),并让 agent 在
   工具做不到用户要求的动作时必须先问,不许自己挑一个动作顶上。

## Motivation

08-08 用户真机验收对话暴露的两个行为缺口,都属于"操作手册没写清楚 / 缺一个工具",
不是代码逻辑错误。放着不修,下次真业主项目上再犯,写进档案的错误状态会被当成
真相一直用下去(唯一真相源 = 本地 Markdown,agent 不会怀疑自己读到的文件)。

## 真问题(第一性)

- 用户原话(问题1):"刚刚我跟agent对话，原话是：秀北小区业主想改主卧背景墙，但是agent
  自己给我新建了一个，尽管项目列表已经建档了秀北小区你用第一性原理查一下什么原因，
  是llm不聪明还是bug"
- 用户原话(问题2):"他建错之后我跟他说建错了 他更正过来了，然后我这个只是实验的话
  所以我删掉这个待办 但是发现没有手动的删除按钮，所以我跟他说先把这个待办删掉
  我说错了，然后他直接把这个待办弄成了完结，我想说的是，如果他也没有删除的权限的话，
  这句话是我说错的，之后难道会出现记忆的错乱"
- 用户原话(问题2 追问):"他告诉我不能删除了，我就是觉得既然是为了可逆，之后会不会把
  我错误的信息记成做过的" / "删按钮我觉得还是需要有的，但是删除前会弹一个确定和取消
  防止误触就好了吧"

- 真正要解决的是:
  1. agent 判断"是不是新项目"时没有核对步骤,靠自己是否精确重复项目名这道弱闸,
     不靠语义匹配、也不靠先查一遍列表——本质是操作手册漏了一步。
  2. 系统现在只能"防丢"(状态只进不删,永远留痕),但防不住"一开始就记错"——
     一旦某条状态被误设,它在文件里和"真的完成/关闭"长得一模一样,以后所有读它的
     地方(list_todos、read_project)都会把错的当真的。要堵这个口子,一是给"删除"
     一个正式、明确的入口(而不是被 agent 拿"完成"顶替),二是 agent 在工具做不到
     用户要求的动作时必须先问清楚要哪个替代方案,不能自己悄悄选。

- 我在这中间翻译了什么:
  用户说的"确定/取消弹窗防误触"是前端交互层面的要求;我把它连带翻译成了"要给
  单条变更加一个正式的软删除能力(回收站式,可恢复)",而不是只加个 UI 二次确认——
  因为如果只做 UI 确认、底层还是"标完成"顶替,没解决"错误记录长得像真记录"这个
  根问题。这个翻译已经在对话里跟用户确认过(软删除 vs 真删除,选了软删除),
  这里是把决策落成 scope。

## Scope

- in:
  1. `workspace/AGENTS.md` 补一条规则:建/改档案前遇到"这可能是已有项目"的情况,
     先 `list_projects`/`read_project` 核对,不确定就问,不许凭消息里的项目名
     直接断定是新项目。
  2. `workspace/AGENTS.md` 补一条规则:工具做不到用户要求的动作(比如"删除"目前
     没有对应工具)时,必须明确告诉用户做不到、并问清楚要哪个替代动作,不许自己
     悄悄选一个动作顶上再报"做完了"。
  3. 后端新增 `delete_change(project, change_id)` 工具:软删除单条变更/待办
     (标记为新状态,如 `已删除`,不物理删行、不破坏"永不删变更行"的账本语义),
     从 `list_todos`/正常展示中隐藏,但文件里留痕、能恢复。
  4. `ds_tools_server.py` 注册新工具;`AGENTS.md` 工具表补充说明。
  5. 前端(ds-web)待办卡片加删除按钮 + 确定/取消二次确认弹窗。
  6. 对应单测(python 侧 delete_change 行为 + web 侧删除按钮/弹窗)。

## Non-goals

- 不做"物理删除"(彻底从文件抹掉这一行)——和现有账本语义冲突,且用户已经选了
  软删除方向。
- 不做批量删除、不做删除后自定义保留期/自动清空回收站——保持和 `delete_project`
  一致的最小实现,复用同一套"删了能捞回"的心智模型即可,更多花活等真需求出现再加。
- 不改 `set_change_status` 现有四个状态(待确认/进行中/已完成/已关闭)的语义或
  转换规则,只新增一个独立的 `已删除` 出口。
