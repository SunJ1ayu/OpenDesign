# T4b 设计:助手记录时给这一批起个名

主 agent 第一遍设计(panel 是第二意见,不能替代这一遍)。

## 先回答一个问题:「一批」到底是什么

用户的用法是「**复制一大段微信丢给助手**」——那一刻助手手里握着全部原文,
起名零成本。所以**一批 = 一次记录动作**,不是"一天"。

这条区分是本单的地基,因为三个候选答案里两个是错的:

| 候选 | 判定 | 为什么 |
|---|---|---|
| 一批 = 一个日期 | ❌ | 业主上午说三条(效果图)、下午又说两条(水电),同一天两批。按日期存名字,下午那批会**改掉上午那批的名字**。 |
| 一批 =(项目, 日期) | ❌ | 同上,只是把跨项目的混淆修掉了,同日两次记录仍然打架。 |
| **一批 = 一段连号的 C 编号** | ✅ | `append_change` 每次取 `max+1`,**同一次记录动作产生的变更号天然连续**。上午 C4–C6、下午 C7–C8,两批各自成段,永不互相覆盖。 |

「一次贴入业主反馈 = 一批」这句话其实早就写在 `todo.ts` 的 `groupByDate` 注释里了
——当时用日期近似它,现在把它做实。

## 存哪儿

新增可选段 `## 批次`,一行一批:

```markdown
## 批次
- C4-C6 2026-07-28 效果图修改
- C7-C8 2026-07-28 水电改动
```

**为什么另起一段,而不是塞进现有格式**:

- **变更行不能碰**。SCHEMA 明写「⚠️ ds-todo 解析此格式,勿改前缀」,
  `CHANGE_RE` 是 collect 与 changes 端点的共同真相源,加字段 = 动全局。
- **不挂在沟通日志上**。那条 `- 日期 业主原文(来源):` 确实是这一批的源头,
  但**只有在业主贴了原文时才存在**;助手也会在没有原文的场合记变更(口述、现场)。
  把名字挂在一个可能不存在的锚上,等于让"起名"随机失效。
- 新段是**纯增量**:旧档案没有这段 = 一条批次都没有 = 前端走 T4a 的兜底标题,
  零迁移、零回归面。

## 写口:`append_change` 加一个可选参数,不新开工具

`append_change(project, content, space="", batch_title="")`。

**为什么是参数而不是第二个工具**:用户要的是「**顺手**起名」。助手记一批要连调 N 次
`append_change`,每次带上同一个 `batch_title`,**零额外调用**;新开一个 `name_batch`
工具意味着助手要多记一步"记完还得起名",而
[[field-needs-a-writer-before-ui]] 的教训正是:**多一步的写口 = 迟早没人写**。

**上卷规则(本单最容易写错的地方)**:带 `batch_title` 追加一条时——

- 若 `## 批次` 最后一行的标题**相同**、且其区间末尾 + 1 **正好等于**本次新号
  → **把区间末尾延一格**(C4-C5 → C4-C6)。这是"同一次记录动作的第 2、3 条"。
- 否则 → **新起一行** `- C{n}-C{n} 日期 标题`。
- 不带 `batch_title` → **一行不写**(前端走兜底)。

连续性是硬条件:标题相同但号不连(中间被别人插了一条)也必须新起一行,
否则区间会把不属于这批的变更吞进来。

## 读口:每条待办自带它的批次

`ds_todo.collect` 解析 `## 批次` 段,给每个 open item 附
`batch: {"id": "C4-C6", "title": "效果图修改"} | null`。
`/api/todos` 原样下发(它直接返回 collect 的结果,不用改端点)。

前端 `groupByDate` → 按 **(日期, 批次 id)** 分组:同一天里
**有名字的各自成组、没名字的合成一组**(保持今天的行为)。
标题:有名字用名字(仍带「等 N 条」),没名字走 T4a 的兜底。

## 安全面(新写口必答)

`batch_title` 与 `content`/`space` 同一条消毒链:`sanitize_field` 折换行
(单行契约的物理保证)→ 剥 `【】`(防伪造空间前缀)→ **剥 `-`/`[` 开头**
(防伪造成一条变更行或段头)→ 截 24 字。
批次行本身以 `- C\d+-C\d+ ` 开头,**不会被 `CHANGE_RE` 命中**(它要求 `- [状态]`),
所以即使有人手写坏了,最坏后果是这行被忽略,不会污染变更解析。

## 动手前核过的三个事实(2026-07-29,读源码不是推测)

1. **`sanitize_field` 只折换行,不剥 `-`/`[`**(`ds_common.py:49`)。所以"防伪造成变更行"
   必须像 `append_change` 剥 `【】` 那样**显式写**,不能指望消毒函数代劳。
2. **批次行不会被误认成变更行**:`ds_tools._CHANGE_RE` = `^- \[(?P<status>[^\]]*)\]\s+C(\d+)`,
   要求 `- [状态] C号`;`- C4-C6 2026-07-28 标题` 缺 `[状态]`,命中不了。
   `ds_todo.CHANGE_RE` 同理(要求 `- [状态词]`)。**安全面结论成立。**
3. **另起一段有现成先例**:`## 变更历史`(edit_change 的留痕段)就是"故意不匹配
   `_CHANGE_RE` ⇒ 不成待办"的第二段,注释里写明了。所以 `## 批次` 不是新发明的形状。
   位置:与沟通日志同策略——**没有就补建到页脚 `---` 之前**,别插在变更记录中间
   (`append_change` 找插入点时以下一个 `## ` 为界,插错位置会让新变更掉进批次段)。
4. **C 编号不会被回收或重排**:`edit_change` 原地改、SCHEMA 规定"不删变更行,取消用
   `[已关闭]`",所以**区间一旦写下就永远指向同一批**。这是"用连号当批次身份"能成立的前提。

## panel-explore 三份方向的对账(2026-07-29,主 agent 仲裁)

三条腿各出一个方向,**没有一条推翻"名字要有独立落点"这个地基**,分歧全在
「落在哪 / 谁写 / 怎么和变更行关联」。逐条:

### ① subdeepseek:独立工具 `set_batch_name` + 标记行 `[batch: X]`,按顺序关联

**采纳它的一条,驳回它的两条。**

- ✅ **采纳的**:它的 Blind spot #1 是三份里最锋利的一句——
  「批次是否严格等于一次 log_communication?**还是可以更细(一次通信内拆出两个独立
  任务批次)**?」这正是真实场景:业主一段微信里同时说了效果图和水电两件事。
  **这一条反过来加固了我的选择**:连号区间天然支持"一次原文拆两批"(中途换个标题就
  新起一段),而任何"按日期/按原文条目"存名字的方案都做不到。**已加进判据。**
- ❌ **驳回"标记行 + 按顺序关联"**:它假设新变更总是追加在标记行之后。但
  `append_change` 的插入点是**「本段最后一条变更行之后」**(`ds_tools.py:168-173`),
  标记行不是变更行 → 新变更会插到标记**前面**,关联当场反向。要让它成立必须改
  `append_change` 的插入语义 —— 那是全项目最热的写路径,为了省一次区间运算去动它,
  风险换反了。**区间方案不碰插入逻辑一个字。**
- ❌ **驳回"独立工具"**:见下 ③ 的同一条理由。

### ② subglm:HTML 注释 `<!-- batch-name: X -->`

**驳回,但收下它的 Blind spot。** 注释行同样是"按顺序关联",继承 ① 的插入点问题;
且 HTML 注释在 markdown 里对人不可见,违背这个项目"档案是人能读能改的"的立身之本
(设计师打开文件应该看得懂每一行)。
- ✅ **收下的 Blind spot**:「**没说批次名怎么改**」。我的方案确实没有改名路径——
  再传一个不同标题只会新起一段,不会重命名。**记成 accepted deviation**:
  档案是纯文本,设计师可以直接改那行;网页端改名不在 T4b 范围。

### ③ submimo:名字写进 `## 沟通日志`,由 `log_communication` 顺手带

**驳回,理由它自己写出来了。** 它坦白核心权衡是「**按日期聚合批次名(同日不同项目会串)**」
——这正是我在设计里判掉"按日期"的原因,它自证了这条路的边界。
另一条更硬的:**名字挂在沟通日志上 = 只有业主贴了原文才有名字**;助手在口述/现场记录
的场合照样要记变更,那时名字凭空消失。**没有写口的字段会变永久摆设**
([[field-needs-a-writer-before-ui]]),而"时有时无的写口"是同一个病的轻症。
- ✅ **收下的**:它点破"批次名与业主原文天然同源"。我的方案**主动放弃了这条链接**
  (批次行不指向原文条目)。记成**刻意省略**:真要溯源,同一天的沟通日志就在隔壁段,
  人眼一看就有;为一个还没人要的链接加字段,是又一个"没有读侧的写侧"。

### ④ 三份都没说、但对账时自己发现的真问题(本轮最值钱的一条)

**标题漂移**:助手记一批要连调 N 次 `append_change`,每次带同一个 `batch_title`。
如果它第 2 次把「效果图修改」写成「效果图调整」,按"标题相同才延段"的规则,
**一批会被劈成两批**。

- 不改成"只按连号延段、忽略标题变化":那会把**背靠背记录的两个不同批次合并**,
  丢的是真信息(比劈开严重)。
- **定案**:保留"同标题 + 连号才延段";在工具说明里写清「**同一批的每一条都用完全相同的
  标题**」。这是**说明书级的软约束,不是代码闸** —— 合乎用户定的调子
  (「不要给 llm 设置太多的锁」),且失败后果温和(两个近义名字的批次,不丢数据)。
- **这条恰好是 T6 那种"助手行为考卷"该测的东西**,记进 T6 的账。

### 合并后的定案(与开工前的设计一致,新增三条)

地基不变:**一批 = 一段连号 C 编号**;存 `## 批次` 段;写口 = `append_change` 的可选
参数。新增:
1. 判据必须覆盖「**一次原文拆两批**」(同日、同项目、连号,中途换标题 → 两段)。
2. accepted deviation:**无改名路径**(改档案文本即可,网页端不做)。
3. accepted deviation:**批次不指向沟通日志条目**(刻意,避免造无读侧的字段)。
4. 工具说明写明"同批用完全相同的标题",并记进 T6 考卷的用例池。
