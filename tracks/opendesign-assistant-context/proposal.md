# Proposal: opendesign-assistant-context — 助手记录时带上下文(时间锚点 + 旧事项冲突)

- Date: 2026-08-04
- Status: open
- 上游:`tracks/archive/opendesign-due-picker`(T6 挂在那儿一直没做)+
  `tracks/opendesign-due-writer`(「时间锚点」是 gpt-5.6-sol 发散留下的后续账)

## Goal

助手在**记业主意见**这一刻,多看两样它现在完全没看的上下文:

1. **这段话是什么时候说的**(时间锚点)—— 设计师贴的是**上周/昨天**的微信记录时,
   「这周五」得相对**业主说话那天**算,不是相对**他把记录贴进来那天**算。
2. **这个项目现在还挂着什么**(旧事项冲突)—— 第一天「大理石用蓝色」,第二天「改红色」,
   第一天那条不该还挂在待办上。

## Motivation

两条都是**静默错**:不报错、不崩、页面照常好看,错了没人会发现。

- 时间锚点:现在 AGENTS.md 契约 1c 写死「相对说法自己按上下文最上面那行 `Current Time` 换算」。
  设计师周一把上周三的聊天记录贴进来,业主原话里的「这周五」指的是**上周五**(已经过去了),
  助手会把它算成**这周五** —— **整整错一周,而待办页会拿着这个错日期一脸自信地排序**。
- 旧事项冲突:`list_todos` 会一直把作废的那条当未办结事项报出来,设计师照着做 = 返工。

## 真问题(第一性)

- 用户原话(07-30,提 T6 时):
  > 「就是看 llm 自己领悟了,聪明的大模型应该会问一下对吧,**我们不要给 llm 设置太多的锁**,
  > 不然等模型发展起来我们还得改」
- 用户原话(08-04,本次排队时我的转述得到「那你先继续吧」):时间锚点那条我报的是
  「会静默错一周,而且没人会发现」。
- 真正要解决的是:**助手记的东西要经得起事后翻账**。日期错一周、旧条目跟新条目打架,
  两者都会让设计师**照着错的信息干活**,而这个产品的全部价值就是「不忘事、不记错」。
- 我在这中间翻译了什么:
  用户对 T6 说的是「llm 自己会问一下」,我把它翻译成**在职责说明里写清楚"记之前先看一眼现有事项"**。
  ⚠️ 这个转译有风险:用户的意思可能是「什么都别写,靠模型自己聪明」。
  我判断不是 —— 他紧接着那句是「不要给 llm 设置太多的**锁**」,锁 = 代码闸/死规则,
  职责说明不是锁。**但这一条我在验收时要当面跟他确认口径。**

## Scope

- in-A **时间锚点**:AGENTS.md 契约 1c 增补锚点规则 —— **先认这段话是什么时候说的,
  再算相对日期**;设计师没交代时间、原话里又出现相对期限时,问一句。
- in-B **旧事项冲突**:AGENTS.md 增补一条职责 —— 记新意见前先看这个项目现有未办结事项,
  发现打架**跟设计师说一声**。
- in-C **考卷**:`tests/evals/due_writer_eval.py` 加时间锚点题;冲突题的断言形状与它不同
  (判的是"有没有说出来 / 有没有乱关",不是"档案里有没有日期"),**单独一份 eval**。

## Non-goals

- ❌ **不写代码闸、不写死规则、不自动关旧条目**(用户 07-30 定死,见上)。
  助手只负责**说一声**,关不关由设计师定,走既有 `set_change_status ... 已关闭`。
- ❌ 不动 `append_change` / `set_due_date` 的函数签名与写口语义(不加参数、不改档案格式)。
- ❌ 不做「外部承诺 ≠ 内部完成日」(业主要 8/10 看图 vs 设计师 8/8 动手)——
  那是**产品语义问题**,一个 `due` 字段表达不了两件事,**得先问用户他想看哪个日期**,
  不在本单。
- ❌ 不碰 `list_todos` 的排序/展示。

## 成功标准

1. 考卷里**时间锚点那题从红转绿**:题面明说「这是上周三收到的消息」,
   业主原话里的「这周五」被算成**业主说话那周的周五**,不是录入那周的。
2. 冲突考卷:助手记新意见时**主动把打架的旧条目点出来**,
   且**没有**自作主张调 `set_change_status` 关掉它。
3. 既有考卷(due_writer 8 题 + resolver 全卷)**不许因为这次改说明书而掉绿** ——
   契约越写越长最容易压垮别的行为,**这条护栏比两道新题都重要**。
