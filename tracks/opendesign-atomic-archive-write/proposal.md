# Proposal: opendesign-atomic-archive-write

- Date: 2026-09-15
- Status: open

## Goal

业主的档案(项目档案、客户备忘、索引、参考图库索引、风格词表)写入时,**任何时刻被强杀或断电,盘上要么是写之前的完整旧内容,要么是写之后的完整新内容**,绝不留下空文件或半截文件。

## Motivation

2026-09-15 应用内更新那一单的切片评审里,GPT 整体腿 #3 指出并用真 `locked_rw()` 在 Linux 上复现:在截断之后、写完之前杀掉进程,文件 28 字节 → 0 字节。
我核实 `bin/ds_common.py:333-343`:`open(path, "r+")` + 排他锁 → 读 → `truncate()` → `write()`。**这是早就存在的普遍风险**:托盘退出、崩溃、断电、应用内更新收摊都走同一条强杀路径,更新只是多了一个时机。
同一形状的还有:`ds_refs.add_style`(风格词表)、`ds_tools.rename_project` 改写客户备忘/索引/档案正文(这三处连锁都没拿)。

## 真问题(第一性)

- 用户原话:(业主选项)「发完就开一单修 —— 改成『写到临时文件,写完再替换』,强杀或断电时要么是旧档案、要么是新档案,不会变空。」
- 真正要解决的是:**业主的资料不能因为软件在错误的一瞬间被关掉而丢失**。"原子写"是手段,不是目标。
- 我在这中间翻译了什么:把"不会变空"翻成了"写入原子化 + 刷盘";断电场景要求刷盘(fsync),只做 os.replace 不刷盘在断电时仍可能得到空文件。
  另外"替换文件"在 Windows 上会引入一个**新的失败方式**(目标被别的程序开着时替换失败),这是这次改动要当心的反面。

## Scope

- in:
  - `ds_common.locked_rw`(12 个调用点)改为:旁路锁 + 同目录临时文件 + 刷盘 + 替换(Windows 上目标被短暂占用时重试)。
  - `ds_refs.add_style` 走同一套。
  - `ds_tools.rename_project` 对客户备忘 / index / 档案正文的原地改写改走同一套(并补上锁)。
  - 保持现有语义:`box["write"] = False` 时文件原封不动(mtime 也不碰);换行、编码、权限位与原来逐字节一致。
  - Windows 真机半:一个 Windows runner 上跑这份判据的探针(msvcrt 锁 + Windows 的 replace 语义本机验不了)。
- 顺带:`_replace_with_retry` 从 `ds_tools` 挪到 `ds_common` 作唯一来源(workspace.json 已在用)。

## Non-goals

- 不改"新建文件"那几处(`create_project` 的 `open(x)`、`_ensure_vocab/_ensure_index` 首次模板):那里没有旧数据可丢。
- 不改日志追加、收件箱上传(已是临时文件 + 独占创建)、已经原子写的配置/凭据/计划文件。
- 不做"启动时从临时文件恢复"之类的日志式恢复:替换是单步提交,不需要。
- 不给 `.locks` 目录设 Windows 隐藏属性(可以,但与"不丢数据"无关)。
