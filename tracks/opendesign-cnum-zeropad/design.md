# Design: opendesign-cnum-zeropad

- Change: opendesign-cnum-zeropad
- Status: draft

- 规划双出: **不适用 —— 这单派给执行腿**(codex gpt-5.5)⇒ 由 `delegate-codex --attack-log`
  那道闸接管:攻题记录 = 本文件「六、我自己先攻这份题」+ `evidence/probe-repro.txt`(机器跑的)。
  也不是开放分叉:方向只有一个说得住的(见「三、考虑过没选的」)。

## Approach

**一句话:变更号是个数,写侧也按数认。**

1. **入口归一**。三个写口(`set_change_status` / `set_due_date` / `edit_change`)已经各自
   把入参解析成 `num`(容差 `3` / `"3"` / `"C3"`),但解析出来的是**原样字符串**。
   改成 `num = str(int(...))` —— 传 `"03"` 和传 `3` 从此是同一件事。
2. **锚点按数匹配**。四处定位正则里的 `C{num}\b` 改成 `C0*{num}\b`:
   - `ds_tools.py` 三处主变更行锚 `^(- \[)(?P<old>[^\]]*)(\]\s+C{num}\b)`;
   - `ds_todo.note_line_re()` 备注行锚 `^- C{num} 备注[:：]` → `^- C0*{num} 备注[:：]`。
   `\b` 保住原有的防误伤(`C3` 不碰 `C30`),`0*` 只往"更多前导零"这一个方向放宽。
3. **写回一律规范形式**(不带前导零):
   - 备注 upsert 命中 `- C03 备注:老` ⇒ 整行替换成 `- C3 备注:新`,重复行照旧归一掉;
   - 留痕行 `- C{num} 改于 …` 本来就是新写的,天然规范。
4. **主变更行的 C 号字节不动**。改状态/截止日走的是 `line_re.sub(...\g<3>)`,
   第 3 组原样回填 ⇒ 手写的 `C03` 留在原地。**这是故意的**:铁律 BLOCK-2 要求
   改正文/状态时"状态/C号/日期逐字节不变",这一单不借机破例。

## Key trade-offs / risks

- 🔴 **放宽匹配 = 有可能匹配到本不该动的行。** 这是本单唯一的真风险。
  防线:`0*` 只加在 `C` 与数字之间,后面的 `\b` 一个字都没动 ⇒
  `C0*3\b` 能命中 `C3`/`C03`/`C003`,**碰不到** `C13`(0* 吃不掉 1)、
  `C30`(\b 在 `3|0` 之间不成立)、`C3x`。判据里为这三条各钉一枪(N1–N3)。
- **档案里同时存在 `- [x] C3 …` 和 `- [x] C03 …`**(业主手抄重号):
  锚点会命中两行 ⇒ 三个写口现有的 `len(hits) != 1` 判断直接返回 `ambiguous_change`,
  **不写**。这是正确行为(fail closed),判据 A4 钉住。`ds_lint` 那边本来就把它们
  算作同号重复、会报出来。
- **同一条变更留下两行备注**(前导零一行 + 规范一行)是**现存档案里已经可能有的脏数据**
  (bug 期间写出来的)。修完之后第一次改备注就会把它归一掉;不做一次性迁移脚本
  ——业主档案不归我改,静默批量重写档案违反本项目的只读铁律精神。
- **`num` 归一用 `int()`:超长数字**(`C007` 没问题,`C` 后跟 300 位数字)理论上
  `int()` 照吃不误,不构成 DoS(正则先限了它得是 `\d+`,且档案是本地文件)。不设上限。

## Alternatives considered

- **只修备注那处正则**(待办池原话的修法)。否掉:探针证明主变更行那条更严重
  (整条待办动不了),只修备注等于留着三处同根同源的洞,而且下次还会有人来"再打一次补丁"。
  业主 08-11 刚说过「那其实现在的修法是在打补丁吗」。
- **读侧改成不归一**(把 `C03` 当成另一个号)。否掉:那会让手写档案里的 `C03`
  凭空多出一条待办,且与 `ds_lint` 的"编号唯一"检查打架。读侧是对的那一半。
- **一次性迁移脚本把所有 `C0N` 重写成 `CN`**。否掉:动业主真实档案,收益只有"好看"。
- **在读侧渲染时告诉业主"这行写歪了"**(lint 提示)。不否,但**不在这一单**:
  那是另一个产品面(要不要在界面上唠叨业主的档案写法),得他点头。

## Test strategy (oracle)

判据全部落在 **`tests/test_ds_cnum.py`(新文件)**,纯 python 单元层,不起服务:
这一单的行为在 `ds_tools` / `ds_todo` 两个模块里就能完整问出来,起服务只会让判据更慢更钝。

**三个复现形状(修之前必红)**:
- `A1` 备注行手写 `C03`,改备注 ⇒ 档案里**只剩一行**备注且是新值(现在是两行)。
- `A2` 备注行手写 `C03`,清空备注 ⇒ 档案里那行**没了**,且 `changed_fields` 含 `note`
  (现在:静默 no-op、`ok:True`、行还在)。
- `A3` 主变更行手写 `C03` ⇒ 改状态 / 改正文 / 改截止日 / 加备注**四个写口都成功**
  (现在全部 `change_not_found`)。
- `A4` 档案里 `C3` 与 `C03` 并存 ⇒ 返回 `ambiguous_change`,且**档案一个字节没变**。

**不许误伤**:
- **修之前就绿的(防的是修过头)**:`N1` 不碰 `C13`;`N2` 不碰 `C30`;
  `N2b` 清 C3 的备注不许删掉 `C30` 的备注(备注锚点有自己那份正则,单独问一枪);
  `N5` 读侧 `parse_change`/`parse_history` 行为不变(这一单不动读侧)。
- **修完才答得出的(和 A3 成对,单有 A3 是假绿)**:`N3` 认得 `C003`(`0*` 不是 `0?`);
  `N4` 改状态后主变更行**除状态词外逐字节不变** —— 手写的 `C03` 不许被"顺手规范化"。
  ⚠️ **08-12 首跑纠正**:这两条我原先写成"修之前就是绿的",实测是红的
  (现状 `C003`/`C03` 根本够不着,写口直接 `change_not_found`)。工件不许说假话。

**首跑实测:15 条里 11 条红**(A1/A1b/A2 + A3×5 + A4 + N3/N4),4 条绿(N1/N2/N2b/N5)。

**回归**:`tests/test_ds_todo.py`、`test_ds_tools.py`、`test_ds_note*`、
以及 `tests/run-all.sh` 全套(含 e2e 总跑)。

**机械化**:判据先单独 commit 且必须红(`redcheck` 钉在 A2 那条断言上);
修完跑变异测试证明判据咬得动(至少把 `0*` 拆掉、把 `int()` 归一拆掉两处靶子)。

**这个 oracle 能被什么骗过?**

- **业主真实档案的歪法不止前导零。** 我的题面是我自己造的干净 markdown;
  他那份两年的档案里可能是 `- C3备注:`(少空格)、全角 `Ｃ`、`C 3`。
  这几种我**明确不修**(non-goal),但判据全绿 ≠ 他的档案能用。
  接得住这件事的只有**真机 + 他自己的档案**,不是我的考卷。
  ⇒ 真机清单里要有一条:**让他去翻一条他手改过的备注**。
- **判据全绿但界面仍然坏**:所有断言都在 python 层,`/api/todos` → 前端那一段
  没被问到。挡这个的是 `tests/e2e/` 总跑(已有的),不是本单新写的断言。
- **A3 的四个写口我可能只测成功、没测"写对了什么"**:比如改状态成功但把
  `C03` 写成了 `C3`(破 BLOCK-2)。所以 N4 必须和 A3 成对存在,单有 A3 是假绿。
