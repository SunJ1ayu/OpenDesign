# Design: 启动可观测性

- Change: opendesign-startup-observability
- Status: draft

- 规划双出: **要做** —— 本文件是我**派发前先落盘**的那一版(反锚定)。
  之后让 `gpt-5.6-sol` 对同一份需求独立出一版(明令不许读本 track 工件),再对差异。
  触发理由不是"新写口",是下面 R1:**误报阈值定错会天天骚扰业主,而我对他机器上的
  启动耗时零数据** —— 这正是"我出方案、它来审"照不到的死角。

## Approach

四件观测 + 一件行为,行为那件的取舍由 CI 数字定。

### O1 日志时间戳补全(两个日志)
`ds_shell.py:106 log()` 现在是 `%H:%M:%S`,**没有日期**;`工作台.log` 连时间都没有。
两处都换成完整日期时间。
> 那行 `%H:%M:%S` 是 08-14 真机红补上的(注释里写着"一个 strftime 换的是一趟真机")
> —— 这次是同一笔账的下半截:**跨天的日志现在对不了账**。

### O2 启动分阶段计时
一个极小的计时器:记开机时刻,每到一个阶段写一行「阶段名 + 距开机多少秒」。
阶段就用**已经存在**的那几个点,不新造流程:
进程起 → 单实例锁 → 后端起 → 网关通 → `create_window` → `shown` → 前端首帧。
> 反屎山:**不引入新的"启动管理器"抽象**。就是一个 `t0` 和一个 `mark(name)`,
> 十几行。启动路径已经够挤了,这里加一层框架就是给下一个人挖坑。

### O3 修一条假信息
`ds_shell.py:1214` 的 `log(f"窗口打开:...")` 写在 `webview.start()` **之前** ——
它报的是"我要开了",不是"开了"。搬到 `shown` 回调里(那个回调已经存在,
`shell.window.events.shown` 上已经挂着 `ensure_native_styles`)。

### O4 界面到底画出来没有(白屏检测)
**走现成通道,不新搭机制**:前端已有 `window.pywebview.api`(`WindowApi`,
`ds_shell.py:372`),0.91 那单还已经把"注入比页面晚"的坑填过了(`pywebviewready`)。

- 前端:工作台**第一帧真内容**画出来时,叫一次 `api.ui_ready()`。
- 外壳:`shown` 之后起一个计时。到点还没等到 ⇒ 日志写明 + **弹一句人话**
  (「界面没能显示出来,多半是网页内核刚更新过,请重开软件试试;日志在 …」)。

**为什么用前端回叫,而不是截图/像素判断**:我们要抓的失败恰恰是"前端没跑起来"
—— 那种情况下它**天然不会回叫**,信号是直给的。截图判白要在产品里塞图像处理,
是典型的屎山。

### B1 `storage_path`(行为改动,取舍由数字定)
`ds_shell.py:1215` 的 `webview.start()` 什么都不传 ⇒ 每次现建临时 WebView2 档案。
补一个固定目录(在我们自己的 app 目录下,坏了能自建)。
**先不下结论它省不省时间** —— 08-30 我就是在这件事上把推论说成了事实。
A/B 在 CI 上做(见 proposal),两组数字进 evidence 再定。

## Key trade-offs / risks

- **R1(最大的)白屏检测的阈值。** 定短了 ⇒ 业主机器慢一点就天天弹框,
  **误报比没有更坏**(本项目多次实证);定长了 ⇒ 真白屏时他已经等烦了。
  已知的唯一硬数据:云端冷启虚机 **20~40 秒**才出界面 —— 那是虚机,不是他的机器。
  ⇒ **我对"多少秒算白屏"没有可靠依据。这是双出要攻的第一个点。**
  当前倾向:阈值取一个明显宽的值(如 90s),宁可漏报也不误报;
  **并且第一版可以只写日志、不弹框**,等收到他机器的真实数字再决定要不要弹。
- **R2 新链路自己坏了没人知道。** `ui_ready` 若因为注入时机根本没被调用,
  表现和"白屏"一模一样 ⇒ 会造出稳定误报。必须有一条判据钉住"正常情况下它一定被叫到",
  而且**这条只能在真浏览器里验**(Linux 单测拿假对象一定绿)。
- **R3 动的是最热的启动路径。** 改坏 = 业主打不开。⇒ impact=high,外部评审 2 腿;
  收口必须有 CI 端到端截图,不接受本机绿。

## Alternatives considered

- **截图/像素判白**(CI 探针现在就是这么干的):产品里不做。CI 里合适,产品里是屎山。
- **接 `NewBrowserVersionAvailable`**(微软官方那个"内核换过了"事件):**这一单不做**。
  它要够到 WebView2 那一层,和自带内核那单是同一个技术前提 ⇒ 并到那一单去,
  免得同一件事在两处各写一半。
- **自动恢复(检测到白屏自动重载/重启)**:不做。现在做是猜;先拿一版数据。
- **给 storage_path 加开关**:不做。业主 08-24 已点过这个毛病。

## Test strategy (oracle)

主 agent 写,先红后绿,判据单独 commit。

| # | 判据 | 在哪跑 |
|---|---|---|
| s1 | `log()` 写出的行含**完整日期**,不只是时分秒 | Linux 单测 |
| s2 | `工作台.log` 也带时间戳(现在零) | Linux 单测 |
| s3 | 阶段计时:给定假时钟,每个阶段都写出「名字 + 秒数」,且秒数**单调不减** | Linux 单测 |
| s4 | 「窗口打开」这行**不许**在 `webview.start()` 之前发出(结构闸,钉死 O3 不被改回去) | Linux 单测 |
| s5 | 没等到 `ui_ready` ⇒ 到点必须**真的**写告警行;等到了 ⇒ **一行都不许写**(反误报) | Linux 单测 |
| s6 | `webview.start()` 的 `storage_path` 落在我们自己的 app 目录下,且目录不存在时能自建 | Linux 单测 |
| s7 | **真浏览器里 `ui_ready` 一定被叫到**(钉 R2) | e2e |
| s8 | CI Windows:装→启动→截图里有界面,且日志里读得出各阶段耗时 | Windows CI |
| — | 红检:每条判据都要有能咬动它的变异 | — |

## 这个 oracle 能被什么骗过?

**最可能的假绿:s1~s6 全绿,业主装上去之后每次开机都弹一次"界面没显示出来"。**
机制:s5 用的是假对象/假时钟,`ui_ready` 在单测里当然会被叫到;
真机上它可能因为注入时机、打包后路径变化、或前端某个分支根本没走到那行而永不触发
—— **这正是 0.91 栽过的那个坑(注入比页面晚)**,而它在单测里是照不出来的。
接得住它的只有 **s7(真浏览器)+ s8(CI 真截图)**,不是任何数量的单测。

**第二种:日志格式全对,但答不出"慢在哪"。**
断言只问"有没有写出秒数",不问"这些阶段切得够不够细"。
真实失败长这样:业主发回日志,我一看 —— 从 `shown` 到首帧 38 秒,
**中间什么都没有**,还是不知道慢在哪。
⇒ 接住它的不是断言,是**先在 CI 上真读一遍自己打的日志**,问"这份日志回答得了那个问题吗"。
s8 必须包含"人真的读一遍",不能只验文件非空。

**第三种(最阴):storage_path 那件事我又把推论当事实。**
s6 只证明"参数传对了",证明不了"它让启动变快了/它是白屏的原因"。
⇒ **A/B 两组数字进 evidence 之前,不许在任何文档里写它的因果。**
