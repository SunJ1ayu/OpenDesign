结论：先不猜白屏根因，也不承诺提速。我要把一次启动变成一条可核对的证据链，使下一次能明确停在“后台、WebView2、静态资源、React、还是 Windows 合成绘制”中的哪一段。整个实施拆成独立发布刀次，避免一次改两个行为变量。

## 1. 做什么

### 第一刀：只增加观测能力，不改启动策略

1. 在 [bin/ds_shell.py](/root/.openclaw/workspace/projects/design-studio/bin/ds_shell.py:106) 改造现有 `log()`：

2. 给 [Supervisor](/root/.openclaw/workspace/projects/design-studio/bin/ds_shell_core.py:374) 加一个可选 `event_sink`，在 `_spawn()`、`_wait_ready()` 记录每条腿的：

   - `service.port_listening`

   “工作台就绪”复用已经存在的 `Service.ready_probe`，真正请求 `/api/health` 并核对版本，而不是只看端口有人监听。现有机制已经准备好了，只是 [工作台 Service](/root/.openclaw/workspace/projects/design-studio/bin/ds_shell.py:291) 尚未接上。

3. 修正服务日志的时间锚：

   - [bin/ds_web.py 的 `log_message()`](/root/.openclaw/workspace/projects/design-studio/bin/ds_web.py:873) 给每条请求加完整时间并立即 flush。

4. 在 [main()](/root/.openclaw/workspace/projects/design-studio/bin/ds_shell.py:1164) 记录准确的外壳阶段：

   - `lock.acquired`
   - `backend.ready`
   - `window.create_called/returned`
   - `webview.loop_entered`
   - `window.shown`
   - `window.loaded`
   - `webview.loop_exited`

   现有“窗口打开”写在 `webview.start()` 前面，改名为“准备进入图形循环”，不能继续冒充窗口已经显示。

5. 复用现有 `window.pywebview.api` 通道：

   - 在 [WindowApi](/root/.openclaw/workspace/projects/design-studio/bin/ds_shell.py:372) 增加 `report_startup(event, detail)`。

   - [web/src/main.tsx](/root/.openclaw/workspace/projects/design-studio/web/src/main.tsx:1) 在模块最早阶段安装：
     - `error`

   - pywebview API 尚未注入时先缓存在内存，复用项目已经正确处理的 `pywebviewready` 机制进行补发。

     - `frontend.bundle_started`
     - `frontend.react_committed`
     - `frontend.frame_submitted`

   最后一项只能表示浏览器提交了帧，不能命名成“用户已经看见”；真实像素仍由 Windows 截图证明。

6. 如果启动后一段宽裕时间仍没有 `frontend.frame_submitted`，只写一次诊断快照，不弹报警、不重启：

   - 两条腿的进程状态和退出码
   - 已到达的最后一个里程碑
   - 复用现有 `_log_frame_diagnostics()`，记录窗口、客户区、WebView2 子窗口数量和尺寸
   - 前端已经上报的第一个异常

7. 在现有托盘菜单 `Shell.run_tray()` 增加“导出本次启动诊断”：

   - 用 Python 标准库打一个 zip，包含本次时间线、三份日志的有限尾部、版本清单。
   - 明确排除配置、key、WebView2 profile、用户资料和截图。
   - 导出后打开日志文件夹。即使主窗口全白，托盘仍然可以操作。

下一次故障就能按最后一个可信里程碑分流：

| 最后证据 | 可以先判定的范围 |
|---|---|
| 工作台未 `identity_ready` | 子进程、端口、配置、迁移或杀毒扫描 |
| 健康端点已通，但没有请求 `/` | WebView2 创建或导航 |
| `index.html` 200，JS/CSS 未请求或返回 4xx | 静态资源、缓存或安装包不一致 |
| 资源均 200，但无 `bundle_started` | JS 引擎执行或资源内容异常 |
| `bundle_started` 后无 React 提交 | 前端初始化异常 |
| `frame_submitted` 已到，但真实截图仍白 | WebView2 合成、子窗口或原生窗口交互 |
| 全部最终到达 | 看相邻时间差，慢在哪一段就查哪一段 |

### 第二刀：单独固定 WebView2 数据目录

只改 [当前 `webview.start()`](/root/.openclaw/workspace/projects/design-studio/bin/ds_shell.py:1215)：

```python
webview.start(storage_path=str(_app_dir() / "WebView2"))
```

并把实际路径写进启动清单。

这不能和第一刀一起发。`storage_path` 会改变缓存、LocalStorage 和 profile 生命周期，本身可能使现象消失或出现；混在观测改造里，就无法知道是哪件事造成差异。

固定后不自动删除、不自动“修复”。它的价值是：

- profile 位置稳定、可核对；
- 冷 profile 和既有 profile 可以做单变量对比；
- 重启电脑不会顺手销毁现场；
- 若以后确认是 profile 问题，也能先保留原目录再实验，而不是直接清空证据。

### 第三刀：把现有 Windows 探针升成真正的反馈环

修改 [.github/scripts/windows-package-probe.ps1](/root/.openclaw/workspace/projects/design-studio/.github/scripts/windows-package-probe.ps1:164) 和对应 [workflow](/root/.openclaw/workspace/projects/design-studio/.github/workflows/windows-package-probe.yml:26)：

- 通过 PID、窗口标题和 HWND 精确找到 OpenDesign 窗口，截图只裁它，不数整个桌面。
- 在 `frame_submitted` 之后连续截三张；同时保存完整阶段耗时。
- 正确判据必须同时满足：
  1. `/api/health` 自报版本等于安装包版本；
  2. 同一个 `run_id` 到达 `frontend.frame_submitted`；
  3. 精确窗口截图连续多张不是近全白。
- 单跑一次“冷 profile”，再用相同 profile 跑一次“温启动”，分别记账，绝不混成一个数字。
- 云 runner 的 20～40 秒目前只记为基线，不立刻设“超过多少秒就红”的性能门槛。先积累稳定分布，再定阈值。

故障注入也一次只改一项：JS 返回 404、模块开头抛错、工作台延迟监听、React 提交后故意铺白。每个注入都必须让对应阶段的判据变红；否则报警器本身不可信。

## 2. 怎么证明它是对的

### Linux 可以证明

- 日志有日期、时区、毫秒、同一 `run_id`，相对耗时单调不倒退。
- `Supervisor` 的阶段顺序和失败分支，可用假时钟、短命子进程和临时 HTTP 服务验证。
- 端口有人监听但 `/api/health` 身份不符时，不能报工作台就绪。
- 前端错误缓冲、`pywebviewready` 补发、事件去重和字段限长。
- 真 Chromium/Playwright 中模拟资源延迟、404、同步异常、Promise 拒绝，检查 React 标志和 DOM 尺寸。
- 诊断包只包含白名单文件，并验证配置、key、profile、用户数据绝不会被打进去。
- `工作台.log` 请求行确实带完整时间并及时落盘。

Linux 不能证明 WebView2 真创建了、pywebview 真完成注入、WinForms 子窗口尺寸正确，也不能证明用户屏幕上有像素。

### 必须在真 Windows/真浏览器证明

- 真安装包安装后，从双击到每一个里程碑均出现在同一 `run_id`。
- `storage_path` 目录确实被 WebView2 使用；同一路径二次启动能读到第一次写入的 LocalStorage canary。
- `shown`、`loaded`、`pywebviewready`、React 提交的实际顺序。
- 精确 HWND 截图不是白屏，且截图发生在前端完成信号之后。
- 故意让前端“返回成功但仍铺一层白色”，必须由像素判据抓住。
- 冷、温启动分别计时，云机数据不外推成业主机器结论。

业主机器只负责提供机器特有证据：以后每次启动已经自动计时，因此他再说“今天好慢”时，不需要自己掐表；导出该次诊断包即可。

## 3. 最大的风险，以及怎么压住

最大的风险是观测层改变启动时序，或者制造一个看似精确、实际上仍是假绿的结论。

压法是：

- 第一刀不改 WebView profile、窗口框架、WebView2 版本、超时和启动顺序。
- 启动事件只有十几条短记录，不开启常驻 Chromium verbose logging。
- 观测失败必须吞掉，不能阻止窗口启动。
- `frame_submitted` 永远不等同于“屏幕已经显示”，必须与 Windows 实际截图联合判定。
- 第一版缺事件只记事实，不弹窗、不自动重启、不清缓存。
- CI 像素规则先用全白、延迟、假成功等 mutation 证明能抓错，再用多次正常样本证明不误报，之后才允许成为发布门。
- `storage_path` 独立发布；后续任何真正修复仍一次只改一个变量。

## 4. 明确不做什么

- 不先做“提速优化”。目前连业主机器的真实耗时都没有，优化只会掩盖阶段。
- 不用增加 `Sleep`、扩大超时或自动重启来“修”白屏；这些会丢失现场。
- 不自动删除 WebView2 profile、缓存或 LocalStorage。
- 不在同一版里升级/降级 WebView2、改窗口动画、改原生边框逻辑。
- 不把 `/api/health` 成功、`webview.start()` 未抛错、React 回调成功中的任何一个单独当成画面正常。
- 不自动截业主桌面，不上传遥测，不收配置、key 或项目资料。
- 不根据云机 20～40 秒直接设业主机器的“慢启动”报警阈值。
- 不做常驻、会反复弹出的“启动太慢”报警器；在量出稳定基线前，它只会重演误报问题。

**如果这一版做完了，业主装上去，他会感觉到什么变化？** 正常打开应当几乎没有变化，也不承诺立刻变快；托盘会多一个“导出本次启动诊断”，下次白屏或觉得慢时，他不必重启碰运气，只需导出一个文件就能让我们定位卡在哪一段。
