## ⚠️ 自我更正(panel 派发之后、**读任何输出之前**落盘)

用户问了一句我没想到的:「后期会给别人用,写死的话对别人有没有影响」。
去翻代码,**我的约束描述说重了两处**:

1. **路径不是写死的**:config 里是 `${DS_ROOT}/bin/ds_tools.py`,`${DS_ROOT}` 是启动时
   展开的变量 ⇒ 别人装在任何盘/任何目录都能跑。**写死的只是文件名那一截。**
2. **新用户完全不受影响**:用户的 `~/.nanobot/config.json` 是**装机时由仓库模板生成的**
   (`install.ps1` Step 7 → `bin/ds_merge_config.py` 合并四段,先自动备份)。
   ⇒ 改文件名后,**新装机的人自动拿到最新模板,根本不会知道我改过**。
   受影响的只有**已装机的存量**,而存量此刻只有机主那两台。
3. **迁移比我写的便宜**:我在 proposal/brief 里写"他要重装或手改 config",
   但 `ds_merge_config.py` 是**幂等可重跑**的 ⇒ 存量迁移 = 再跑一次装机脚本,
   不是手工编辑。

**这直接削弱了方向 M 的存在理由。** M 的全部价值就是"绕开 config 不能改"这条约束;
现在这条约束比我以为的软得多 —— 为了绕开它而把 `ds_tools.py` 的业务代码大规模搬家,
代价反而更高(海量调用点 + 名字撒谎)。

⇒ **我的倾向从 M 转向 R(修根因:入口统一,config 改一次以后不用再动)。**
但**不立即定稿** —— 我刚犯的错正是"凭印象判断没去翻代码",不该马上换个方向再犯一次。

⚠️ **这个更正会影响 panel 的可信度**:我发出去的 brief 里带着被夸大的约束,
**可能把各腿往 M 带偏**。读他们答案时按这个折算:
若某腿**自己翻代码发现了 `ds_merge_config.py` 或模板生成机制**、并据此主张修根因,
**那一腿的分量要加重**(它穿透了我的错误前提);反之若某腿只是复述我的约束,
其"支持 M"不构成证据。

## 现状(实测,不是印象)

三个业务模块各自兼职当 MCP 登记处,**且各自是一个独立进程的入口**:

| 文件 | 业务代码 | 登记 | server 名 | 被谁拉起 |
|---|---|---|---|---|
| `ds_tools.py` 1537 行 | 项目/客户档案 CRUD、变更、待办、workspace.json 读写+锁 | 17 个 | `design-studio` | config `args:[bin/ds_tools.py]` |
| `ds_organize.py` 396 行 | 暂存/校验/冲突/快照/approve 硬闸 | 7 个 | `design-studio-organize` | 同上 |
| `ds_refs.py` 434 行 | 参考图索引 | 5 个 | `design-studio-refs` | 同上 |

登记处用 `FastMCP` + `@server.tool()`,`_run_mcp()` 里 `.run()` 起 stdio server。
`mcp` 包是**函数内延迟导入**(有意:未装 mcp 时纯 Python 核心与 tests 照常可用)。

**环的机制**:登记处要把别的业务模块的能力也挂上去(如 `ds_organize` 的登记处挂
`ds_adopt.adopt_scan`),于是 `ds_organize → ds_adopt`,而 `ds_adopt → ds_organize`
是真实的业务依赖(采纳引擎要用 `stage_plan` 这个唯一写面)⇒ 成环。

## 主 agent 的方向(**读 panel 之前落的**):方向 M「反转入口文件」

**核心赌注:config 钉死的是*文件名*,不是文件里的内容。** 那就别搬登记处,
**搬业务代码** —— 让 `ds_tools.py` 从"业务模块 + 兼职登记处"变成"**纯登记处 + 进程入口**"。

- `ds_tools.py` 的业务函数搬到新模块(按语义切,如 `ds_project_files.py` /
  `ds_wsconfig.py`),`ds_tools.py` 只剩 `_build_server()` + `_run_mcp()` + `__main__`。
- `ds_organize.py` / `ds_refs.py` 同法。
- 依赖方向变成单向:**登记处 → 业务模块**,业务模块之间不再需要反向边。
- **`~/.nanobot/config.json` 一个字不用改,两台 Windows 不用重装。**

**它最可能错在哪(我自己先说)**:
1. **调用点海量迁移**。`ds_web` 里 `ds_tools.X(...)` 满天飞,`ds_lint`、`ds_adopt` 也用。
   一次改几十处,每处都是"纯改名"但总量大 —— 而第①②刀的教训是:
   **纯位移的大 diff 正是闸③最挡不住的形态**。判据必须是机械的(逐字节 + 工具表快照)。
2. **命名会撒谎**:`ds_tools.py` 里不再有 tools,名字变成历史包袱。
   而"名字撒谎"是这个仓库反复记账的病(`.gallery-link` 那次)。
   ⇒ 若选 M,必须在文件头写清"这个名字为什么不能改"(被 config 钉住)。
3. 它把"config 不能改"当成了不可动摇的前提。**也许那才是真正该修的东西** —— 见方向 R。

## 我看到的其他方向(**不塌缩,留给 explore 铺开**)

- **方向 R「修根因:让 config 不再钉死文件路径」** —— 比如入口统一成
  `bin/ds_mcp.py <server-name>`,config 改一次、以后再不用动。
  代价:两台 Windows 要重装/改 config,且 `git pull` 修不好 → 一旦漏做,助手工具全废。
  **但它把"入口契约"这件事一次性做对**,而 M 是永远绕着它走。
- **方向 S「原地拆:登记处留在原文件,只把跨模块那几个工具挪到它该在的模块」**
  —— 环的成因是"登记处挂了别人的能力"。`adopt_workspace_tool` 挂在 `ds_organize`
  的 server 上,但它是 `ds_adopt` 的能力。若工具能按**归属**重新分配到三个 server,
  跨模块引用自然消失。代价:**动 server 归属 = 动 config 里工具的可见性**,
  且可能改变助手看到的工具集合 —— 撞 Non-goals。
- **方向 N「不做」** —— 4 个环现在跑得好好的,延迟 import 是 Python 生态的常规手法。
  "环 = 坏"是我的默认信念,不是实测出来的成本。真实成本可能远小于这一单的风险
  (动的是助手工具链,坏了用户当场没法用)。
  **这条必须被认真对待,不是礼貌性陪衬。**

## Key trade-offs / risks(选型前就看得见的)

- **最大风险不是代码,是部署面**:三个 MCP server 是助手能力的全部来源。
  搞砸 = 用户机上助手"什么都不会做了",而且是他下次用的时候才发现。
- 判据必须能**离线证明工具表不变**:29 个工具的 `name + 参数签名 + docstring`
  逐字节快照,改一个字都要红。docstring 尤其重要 —— 它是喂给模型的规格,
  改它等于改产品行为。
- `mcp` 包在测试环境可能没装(现有代码用延迟导入正是为此)⇒ 判据要能在**没装 mcp**
  时也跑(或明确 skip 并在真机补验),否则判据自己会变成摆设。

## Test strategy (oracle)(方向定了再细化,但这两条不论选哪个方向都要)

1. **工具表快照闸**:枚举三个 server 的全部工具,取 `name + 入参 schema + docstring`
   算哈希,与**改动前**的快照比对,**逐字节不变**。基线在动手前生成并单独 commit。
2. **入口可运行闸**:对 config 里那三条 `args` 指向的文件,断言它们仍能作为
   `__main__` 起一个 MCP server(至少能 import 并构建出 server 对象)。
   ⇒ 这条直接对着"用户机上会不会废"这个真实风险。

**这个 oracle 能被什么骗过?**

- 快照绿 + 入口绿,但**用户的 `~/.nanobot/config.json` 里是旧路径**(他装机那次的)
  —— 我这边一切正常,他机器上全废。**判据在仓库里,风险在仓库外。**
  ⇒ 不论选哪个方向,验收都必须有"用户机上助手真的调用一次工具成功"这一条,
  和第①②刀的 G3 同性质。
- 我可能把"环消失"当成了目标,而真正的目标是"改动时不牵一发动全身"。
  **环归零但每个模块都要 import 六个新模块,可能更难改** —— 这条机械判据完全挡不住。


## panel-explore 合成(2026-08-02,三腿跑了两腿)

日志 `/root/aiwork/logs/panel-mcpreg-20260802.*`。subglm 死于智谱额度(非意见)。
**两腿方向正好相反 —— 分歧本身就是产出,不塌缩。**

### subdeepseek:剥出 `ds_*_server.py`(比我的 M 更好的 M)

**它的核心洞察比我准**:环不是"登记"造成的,是**组合点选错了位置**。
`ds_organize` 的 server 上挂 `adopt_workspace_tool`,是**产品决策**
(`test_ds_organize.py:290` 把那 7 个工具的集合钉死了),这个组合**必须存在**。
⇒ 要移的是组合的**位置**,不是组合的**存在**。

**它的方案严格优于我的 M**:我想搬**业务代码**(海量调用点 + 名字撒谎),
它搬**登记层**(3 个新文件 + 3 处测试调用点),config 同样一字不动。**我认输,采纳它的形。**

**但它的成功标准我实测证伪了**:它说"白名单缩到空、`test_02b` 从 ≤3 收紧为 ==0"。
我搭了个最小复现喂进 `_find_cycles`:入口文件 `if __name__` 块里的
`from ds_a_server import run` **仍然算一条边** ⇒ 会产生 3 个新的
`入口 ⇄ 自己的 server` 环。**环数不会归零,只会从"跨模块缠绕"变成"本地一跳"。**
⇒ 收益的正确说法不是"消灭环",是**"把跨业务模块的纠缠降级成入口壳的本地自环"**。
这仍是真收益,但和它承诺的不是一回事。

它的 5 条 blind spot 里 **#1 与 #4 我没想到且成立**:
- #1 死线该写成"入口必须始终**可直接运行**",不只是"路径不变" —— 路径没变但
  launcher 被顺手改坏,后果一样;
- #4 **`mcp` 延迟导入是这单最容易被顺手改坏的承重墙**:业务模块要能在没装 mcp 时
  照常 import。一旦被"提升 import"破坏,而本机恰好装了 mcp,**测试永远绿、隐患上线**。
  ⇒ 判据必须加一条:业务模块在无 mcp 环境仍可导入。

### submimo:「不做」

**它的 blind spot #1 是本轮最有价值的一击,直指我的前提**:
> 「brief 把循环依赖等同于问题,但没证明它造成了任何实际损害……
> brief 似乎把工具的输出当成了事实,而不是问这个工具的判断标准对不对。」

**这一条成立,而且更难看的是:那个"4 个环"的数字是我自己写的判据吐出来的。**
运行期不炸、行为正确、用户零感知 —— 唯一的"证据"是我自己造的尺子在报红。
⇒ 本单是**维护性投资,不是修 bug**;它该排在所有用户可见的事情之后。

它的 blind spot #3 也命中:brief 没量化"用户愿不愿意跑一次 setup 脚本"——
而我在派发后已独立发现答案(`ds_merge_config.py` 幂等可重跑),见上方自我更正。

**但它的"最小第一步(加白名单)"已经做完了** —— `KNOWN_REMAINING` 就是白名单,
第①②刀那单已经建好。所以 submimo 的"不做"实际等价于**维持我现在的状态**。

### 主 agent 合成裁决

- **形态上采纳 subdeepseek**(搬登记层,不搬业务代码),**放弃我自己的 M**;
- **收益说法按我的实测修正**(不归零,是降级成本地自环);
- **要不要做,采纳 submimo 的框架**:这是维护性投资,不是 bug。
  加上方向 R(改 config 一次到位、真能归零)现在也比我原以为的便宜。
- ⇒ **三选一交给用户**,因为代价与收益都落在他身上,不是技术问题:
  R 一次做对(要他两台机各跑一次装机脚本)/ D 绕着走(他零操作,留 3 个本地自环)/
  N 不做(现状,零风险零收益)。**我的推荐是 N 或 R,不推荐 D** —— 理由见 tasks.md。
