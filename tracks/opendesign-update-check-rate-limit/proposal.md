# Proposal: opendesign-update-check-rate-limit

- Date: 2026-09-15
- Status: open

## Goal

业主开着 VPN 点「检查更新」要真的查得到新版;查不到时界面说清为什么。

## Motivation

业主 09-15 夜装着 0.98.4,点「检查更新」一直显示「查不到更新」。他从本机取回的原文:

```
{"current": "0.98.4", "update_available": false, ..., "error": "查更新失败:HTTPError: HTTP Error 403: rate limit exceeded"}
```

## 真问题(第一性)

- 用户原话:「我这里点检查更新查不到」「我一直开着vpn的」。
- 真正要解决的:**查更新只靠一个按出口 IP 限次数的来源**(未登录 GitHub API,每 IP 每小时 60 次)。
  商用 VPN 出口很多人共用,额度被别人用光 ⇒ 业主点多少次都查不到。这是我们的设计缺陷,不是业主网络坏了。
  ds_update.py 的注释早就写着「限流的样子恰恰是"查不到新版本"」—— 当时只防了"自己问太多"(6 小时缓存),没防"别人把同一个出口用光"。
- 我在这中间翻译了什么:
  - 「查得到」翻成:API 被限流(或别的失败)时还有第二条查法,且一键更新仍拿得到可信 sha256。
  - 「显示原因」是我加的:界面只写「查不到更新」,这次靠业主开浏览器/PowerShell 才拿到原文,来回三轮。
  - 同一条查询路径上还有一个确定的 bug(不是这次的元凶):`fetch_releases` 用进程级缓存的 urlopen,代理只在第一次联网时读 ——
    t30b 修了下载那条,查更新漏了。一并修。

## Scope

- in:
  - 查更新的第二来源(方向见 design.md,经 panel-explore 发散后定)。
  - 界面「查不到更新」处显示真实原因(人话,不甩栈)。
  - 查更新时代理当场读(t30b 同类)。
  - 发版流程随之要多做的事(比如多传一个文件),写进发版步骤并在下一版执行。
- 版本号 bump 与发版:这单完成后连同自动更新那单一起问业主。

## Non-goals

- 「打开软件发现新版 ⇒ 倒计时自动更新」—— 业主已定,**另开一单**,依赖本单。
- 让 0.98.4 自己绕过限流(旧客户端的代码改不了):业主这次靠换 VPN 节点或手动下载 0.98.5。
- 代码签名、自建更新服务器。
