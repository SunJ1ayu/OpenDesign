已读 `tracks/opendesign-zcode-model-settings/` 的 proposal / design / tasks(未读实现代码,黑盒)。以下是我的设计方向。

Direction: **「钱与模型身份」为主线、以运行中目标自报为判据的旅程式测试设计**——把每条 P0 用例的判据从「界面上显示什么」改写成「这一次请求实际发给了谁、用哪把 key 扣的钱、后台真的加载了什么」,界面结构断言退为第二条腿。

Core bet: 这次重做的失败模式几乎全是**界面说的与扣钱的不一致**——选了小米 v2.6-pro 却因为路由没认它而回落/串家、自定义供应商的 Base URL 与内置撞端点导致账单走错、存了 key 但网关还没重启所以「选了没生效」。因此只要每条 P0 用例都强制存在一个**运行中目标自己打印身份**的观测点(加载的端点 + key 尾号 + 当前模型 + 目录条目),像素级「照 ZCode」比对就只是人工亲看的补充,而不是主线。我押的是:**这次重做的钱上风险,用界面截图和 DOM 断言都抓不到。**

How it works:

**三条腿**
1. **身份回显腿(唯一 P0 判据来源)**:每次换模型 / 存 key / 加模型之后,向运行中的后台要一份「我现在加载了什么」的自报(端点、key 尾号、模型名、目录内条目数),与界面显示逐条对。做法照仓库已有的 `check-gateway-version` 那条路数——让目标自己说,不听自述。
2. **界面结构腿**:ZCode 保真度只做**结构断言**(左栏两组 + 状态点三态、右详情行内 测试/编辑/删除、内置模型无删除、两级弹框的 ✓ 位置与底行「管理模型」直达该厂商),不做像素/配色断言——那条交给 T5 人工亲看截图。
3. **回归腿**:`update-status / update-check / update-retry / update-restart / update-badge` 与 `settings-toggle` 钩子原样沿用,老 e2e 条目逐条移植后一条不丢。

**用例按「用户旅程」编排,不按控件罗列**——控件的正确性只有在旅程里才有钱上的意义。

用户故事(骨架):
- **S1**(业主原话那条):Given 我填好了小米 key、小米页能看到模型列表;When 我点「添加模型」填 `mimo-v2.6-pro` 并测试通过,然后去聊天框右下角选中它;Then 我发一句话得到回答,而且这次回答**确实从小米扣的钱**。
- **S2**:Given 我想用一家没内置的厂商;When 我「添加供应商」填名称/Base URL/key/至少一个模型;Then 它出现在换模型菜单里,选中后能聊,账单走这个 Base URL。
- **S3**:Given 我正在用小米 v2.6-pro;When 我试图禁用小米或删掉 v2.6-pro;Then 我被告知要先换到别的,且我当前的东西一点没变。
- **S4**:Given 我正在用 A 家的模型;When 我在 B 家页换了 key 并保存;Then 我当前的模型仍然是 A 家那个,只是几秒内后台重启,重启完 B 家也能立刻用。
- **S5**:Given 我用 0.98.11 装了软件、填过 key、选好了模型;When 我升级到 0.98.12;Then 我的 key 还在、我选好的模型没被换掉、聊天照常,侧栏那个「重启以更新」还在原地。

探索式测试任务(3~5):
- **E1 摊着 ZCode 截图当业主走一遍**:目标——排版与信息密度经不经得起「用户自己看」;重点看状态小圆点三种状态是否一眼可辨(而不是要读文字才知道)。
- **E2 带着真钱来回切**:用真 key 在小米/DeepSeek/自定义供应商之间来回切 + 加一个真新模型;重点抓「界面说 A、实际扣 B」和漏发给旧厂商。
- **E3 粗心输入大会**:Base URL 撞车、模型 ID 带空格/斜杠/大小写变体/重复添加、供应商名超长/纯中文/纯 emoji;重点看是拒绝得清楚,还是悄悄存进去之后在别处爆炸。
- **E4 断网 / 慢网 / 错 key 下的「测试」**:重点看能不能区分「key 不对」与「网断了」——分不清就等于把用户推向乱改 key。
- **E5 重启窗口连打**:存 key 后立刻连点换模型/发消息;重点抓用户撞得到的那个不可见中间态。

Best at: 把「界面照不照 ZCode」这个容易变成审美争论的问题,降级成第二条腿;把真正的钱上风险(串家、回落、没生效)变成可执行的机械判据。也天然承接本仓「交付物跑在你改的仓库之外时,以运行中目标回显为准」这条既有规矩。

Sacrifices: 不产出逐控件的穷举用例表(控件覆盖靠结构腿 + 探索式兜);不做像素/配色/间距比对,视觉问题只报不断;不测「手改配置文件才有的形状」和「有人拿锤子砸墙」类。另外它对纯前端评审(视觉对不对)给不出强判据——那是这套设计的真空白,得靠 E1 人工亲看补。

Blind spots in the brief:
1. **「状态小圆点」的「能用」没有定义**:是「key 非空」还是「测试过且通过」?这直接决定用户会不会看到一个绿点、以为能用、选它、然后聊天失败——而绿点正是这套 UI 里用户唯一的信任信号。
2. **规则自相矛盾**:「API Key 可显示/隐藏」与「key 在界面上永远只显示首尾几位,不显示原文」冲突。已保存的 key 点眼睛看到的是什么?如果显示原文,破了规矩;如果显示掩码,这个眼睛就是摆设。必须拍板。
3. **「测试」按钮是否花用户的钱**:brief 只字未提。对 MiMo 套餐 / GLM 套餐,测试失败重试算不算消耗、测试会不会因为把套餐额度打满而影响正事?「扣错钱」是 P0 的定义之一,这条不该留白。
4. **重启窗口是一等用户状态,却没人写**:「几秒」期间用户看到的界面是活的,消息走谁?老网关还是新网关?这是最容易出「第一次用就是坏的」的窗口。
5. **「在用的不能禁用」只写了厂商一侧**:在用的那家的 **key 能不能清空/删掉**?在用的那个模型写了不能删,但 key 一侧没写——清掉正在用的 key 是什么后果(brief 里 D3 说禁用不动 key,但清 key 不在其中)。
6. **老装法(源码跑)的用户体验被写成技术限制,没写成界面症状**:五家全列出来但四家不可能配好——用户看到的是「一个能用的设置页」还是「一个骗人的设置页」,brief 只说了「加不了自定义供应商」。
7. **「刷新」按钮的语义没写**:刷新什么?会不会把用户刚加的模型冲掉?这个按钮如果语义不清,用户点了会害怕。
8. **升级期望的边界没钉死**:「老配置升级后原样出现」——但源码装法只有一个 key 变量,升级后是「五家里只有一家配好」还是别的东西?这个「原样」需要被写成可判的句子。

Smallest first step: 先建那条**身份回显观测点**——一条能在运行中的目标上打印「当前加载的模型 / 端点 / key 尾号 / 目录内条目」的命令(做法照 `/root/aiwork/bin/check-gateway-version`),然后手工走一遍 J1-01(小米加 `mimo-v2.6-pro` → 测试 → 选中 → 发一句)并把红点记下来。这条观测点建不起来,后面所有 P0 用例都会退化成「看界面猜」,整套方向就不成立——所以它必须先于任何用例表定稿。
