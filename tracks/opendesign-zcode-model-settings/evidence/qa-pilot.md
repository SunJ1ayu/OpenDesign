# 试点:测试员角色参与(业主 09-24)

业主原话:「现在大多数情况aiwork的流程是不是都在审查边缘情况，真实的软件工程是不是需要一个专门测试的人员呢，
我在想我们的多模型审查步骤要不要再来一个多模型先参与测试」→「可以，试一次，你要参考一下实际软件工程团队配合的模式来让他们参与测试试试看」。

事实依据:评审 = 读代码对规格,后期多在挖边角;业主装机后发现的问题(选不到 v2.6、启动横幅多余、图标不像 ZCode)没有一条是评审抓到的。

| 真实团队 | 本单 |
|---|---|
| 产品负责人(需求、UAT 签收) | 业主 |
| 需求评审阶段 QA 参与,写验收标准与用例(左移) | QA-设计:两家不同家族(DeepSeek、Grok),黑盒,只读 `evidence/20260924-qa-test-design-brief.md` |
| 三方对齐(PO / Dev / QA 过用例) | 主裁合并去重、定优先级;产品歧义问业主 |
| 开发 + 自动化验收 | 主裁把 P0/P1 写成 e2e / node 判据(oracle 仍由主裁写) |
| 测试执行:用例 + 探索式测试,提缺陷(步骤/期望/实际/严重度) | QA-执行:界面建好后让模型真操作运行中的界面 + 看截图,按用例与探索任务提缺陷 |
| 缺陷分级会 | 主裁按严重度裁;「锤子砸墙」类不修 |
| UAT | 业主用新版 |

评估(归档时填):QA 设计 / 执行各找出几条**用户层面**的问题、其中几条是代码评审也会找到的、多花了多少时间;没有数据写 unknown。
