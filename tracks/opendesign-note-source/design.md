## Approach

一句话:**备注的真相只有一处(档案文件),"变没变"的判断也只有一处(后端)。**

> ⚠️ **本节已按双出对差修订**(修订处标 🔁)。原始版本见 commit `dd05720`/`a92860c`,
> 对差记录在下面「双出对差」一节 —— 我改了主意的地方都写了为什么。

### 1. 读侧:`## 变更历史` 的解析挪进 🔁 `ds_todo`(不是 `ds_common`)

今天 `parse_history` 和那两条读侧正则住在 `bin/ds_tools.py`,而待办页要的载荷由
`bin/ds_todo.py` 产出 —— **`ds_todo` 不能 import `ds_tools`**:`ds_tools` 已经
import 了 `ds_todo`(`bin/ds_tools.py:39`,`list_todos` 直调),反向再连就是环,
`tests/test_no_import_cycles.py` 会红(上一单 `ds_consent ↔ ds_tools` 刚被它抓过)。

把 `## 变更历史` 段的**读模型整块搬进 `ds_todo`**:

- `HISTORY_HEADER` / `HISTORY_EDIT_RE` / `HISTORY_NOTE_RE`
- `history_bounds(lines)`(段边界)
- `parse_history(text)`(`{cnum: {note, history[]}}`)
- `note_line_re(num)`(**写侧**那条按 cnum 定位备注行的锚)

🔁 **为什么是 `ds_todo` 而不是我原来写的 `ds_common`**:`ds_todo` 已经是**档案的读模型**
(`parse_change` 五状态单一真相源、`parse_batches` 批次段都在这儿),而 `/changes` 和
`/api/todos` 两个读端点本来就各从 `ds_todo` 取一半、从 `ds_tools` 取另一半 ——
把读侧凑齐在一个模块,依赖方向天然是 `ds_web → ds_tools → ds_todo → ds_common`,
**一条直线,没有环**。塞进 `ds_common` 也能编译,但那会让它继续长成杂物间
(格式常量在 `ds_common`、解析函数在 `ds_todo` 已经分家了,再加一份只会更乱)。

**写侧的锚也一起搬**,否则就又变成"读侧在 A、写侧在 B" —— 那正是 0.83.0 刚修掉的
病(写侧改第一条、读侧最后一条获胜)。`ds_tools` 的四个写函数
(`_upsert_note`/`_delete_note`/`_append_history_entry`/`_create_history_section`)
留在原地,只是改成用 `ds_todo` 的锚;`ds_web:934` 的调用点改成 `ds_todo.parse_history`,
**不留 `ds_tools.parse_history` 别名**(一个东西一个名字,别名会让人以为有两份)。

### 2. `/api/todos` 带上持久 `note`

`ds_todo.collect` 里每个 open 条目加 `note` —— 取自 `ds_common.parse_history(text)`
按 cnum 分桶的结果,**与 `/changes` 完全同源**(同一个函数,不是两份解析)。

**约定与 `/changes` 保持一致:有备注才带 `note` 键**(没有就没这个键)。
> 为什么读侧允许"缺席"、写侧不允许:**缺席的歧义只存在于有"动作"含义的地方**。
> 写侧的 `note` 缺席意味着"这次不动它",空串意味着"我要它变成没有" —— 两种意思,
> 所以必须分得开。读侧只有一种意思:**没这个键 = 这条没有备注**。不给读侧发明
> `note: null`,也就不用回答"null 和缺席差在哪"这种自找的问题。

### 3. 待办页:删掉 `noted` 会话映射

`TodoPage` 里 `const [noted, setNoted] = useState<Record<string, string>>({})` 整个删除:

- 显示:`it.note`(服务端来的)有值就渲染 `.note-tag`;
- 编辑预填:`startEdit` 用 `it.note ?? ""`,不再查会话映射;
- 保存后的乐观回显**整段删掉** —— `save()` 末尾本来就调 `reload()`,
  服务端现在带 note,乐观回显是多余的第二个真相源。
- `OpenItem` 类型加 `note?: string`。

业主能看见的变化:**在待办页写的备注,刷新页面、换台电脑打开,都还在**
(今天是刷新就没)。

### 4. 写口:前端不再判"变没变",只描述"你想要的最终样子"

`buildEditRequest` 去掉全部等值比较与 `dirty` 累加,也去掉 `originalNote` 参数:

| 字段 | 今天 | 改后 |
|---|---|---|
| status | 有效且 `!== item.status` 才带 | 🔁 **用户碰过就带**(有效性仍校验) |
| text | 非空且 `!== item.text` 才带 | 🔁 **用户碰过就带**,空串照发(后端回 `empty_text`) |
| note | `!== originalNote` 才带 | 🔁 **用户碰过就带**(trim 后,空串=删除) |
| 返回 | 没有任何"改动"→ `null` | 恒为请求对象(cnum 缺失仍 `null`) |

🔁 **判定标准从"值变没变"换成"用户碰没碰过这个输入框"** —— 这不是把判断换个地方,
两者性质不同:**"碰没碰过"是意图,只有前端知道;"变没变"是事实,只有档案说了算。**
前端报意图、后端判事实,各说各知道的那一半。落地:`draft` 从"打开编辑框时预填好值"
改成**空对象**,输入框显示 `draft.x ?? it.x`,`onChange` 才往 `draft` 里写。

🔁 **顺带堵住一个我原方案会捅出来的洞**:如果按我原来写的"把预填的字段全发回去",
业主在编辑框里发呆的这段时间里别人(或助手)改了同一条,他一保存就**连没碰过的字段
一起盖掉**。而"陈旧编辑保护"这一单业主明确说先不做 ⇒ **在它落地之前,更不该
主动把覆盖窗口开大**。只发碰过的字段,窗口维持现状。

**保留的和去掉的要分清**:去掉的是**"变没变"的判断**;保留的是**校验**
(`cnum === null` 不可寻址 → 返回 `null`;非法状态词剔除)。
🔁 **空正文改成照发**:后端本来就有 `empty_text` 这个错误码(`ds_tools.py:571`,实查),
前端悄悄吞掉等于"清空正文后点保存,什么也没发生也不报错"——那是把错误藏起来,不是校验。

### 5. 🔁 后端补两处(双出抓到的,我原方案漏了)

- **状态也要同值比较**。今天 `if new_status is not None: … changed = True` 是**无条件**的
  (`ds_tools.py:594-596`,实查)。前端不再预判之后,点一下"还是原状态"就会**假 bump
  页脚** —— 与 0.83.0 刚修的 LOW-1 一模一样的形状,只是换了个字段。
- **`edit_change` 返回 `changed_fields`**(锁内、与盘上当前值比过之后才产生)。
  理由是前端有一处**真的需要知道"到底改了没有"**:待办页的「改过·看原文」
  (`edited` 映射)今天靠 `req.new_text !== undefined` 判断,改成"碰过就发"之后,
  **原样保存也会被标成"改过"**。有了 `changed_fields`,它就以事实为准。
  > 这条是双出替我接住的:我原方案会引入一个业主看得见的假标记。

### 6. 🔁 web 层:缺省 / 空 / null 三者必须分得开

`_edit_change` 今天用 `body.get("note")`,**JSON 里没这个键**和**显式 `null`** 都变成
`None` = "不动"。改成:

- **键不在 body 里** → 不传给核心(= 不动);
- **值是字符串**(含 `""`)→ 传给核心;`""`/纯空白 = **删除这条备注**;
- **值是 `null`** → **400**(三个字段 `new_status`/`new_text`/`note` 统一这条)。

🔁 双出主张改成"`null` 才是删除、`""` 回 400"。**我不采纳**,理由:
① 本仓已有先例 —— `ds_refs.update_ref` 的 note 就是"空串即清空"(上一单四审的
DeepSeek 还专门引它论证过);两个写口说同一种语言,比单个写口的"域纯洁"更值钱,
而**分裂正是这一单要消灭的东西**。
② 真正的缺陷是"**缺省与空分不开**",它由 `"note" in body` 结构性地解决,
**与选哪个 token 当空态无关**。
③ 但采纳它的内核:**一个状态只准有一个拼法** ⇒ 显式 `null` 从"静默当成不动"
改成 **400**,不再是第二个拼法。
> 这条我拿不准到会想让四审专门盯一眼:**如果 refs 那条先例本身就该改**,
> 那"保持一致"就成了把错误抄第二遍。写在这儿当靶子。

连带:`save()` / `quickSetStatus()` 里的 `if (!req) …` 分支消失。
点了编辑又原样保存 ⇒ 发一次 PUT ⇒ 后端判定 no-op ⇒ **文件逐字节不动、页脚不 bump**,
回 `{ok:true, cnum, line}`。多一次请求换一处判定,值。

> **实测过,不是推演**(`scratchpad/probe_noop.py`):对一条带备注的变更,
> ① 只给 `project`+`cnum`、什么字段都不带 ⇒ `ok:true`,文件逐字节不变;
> ② 正文和备注都传**与现状相同的值** ⇒ `ok:true`,文件逐字节不变。
> 后端这一侧 0.83.0 就已经做对了,所以前端那道判断确实是纯冗余。
> 注意 `write` 只是 `locked_rw` 的内部开关,**不出现在响应体里** ——
> 前端无从、也不需要知道有没有真写盘(它保存完就 `reload()`)。

## Key trade-offs / risks

- 🔴 **我们要推翻 `test_workbench_p4.mjs` 里六条现在是绿的断言**(不是一条)。
  它们都是同一个形状:「没有实质改动 ⇒ 返回 `null`」。这**正是"改考卷让自己及格"
  长的样子**,所以规矩加严,不许含糊:
  1. **每一条都换成更强的断言,一条都不许只是删掉**。旧断言只说"是 null",
     新断言要说清"返回的请求里到底有什么、没有什么"(见 Test strategy §3 的对照表)。
  2. **红检要证明新断言在旧实现下是红的**(旧实现返回 null ⇒ 新断言必红)。
  3. **推翻的理由要单独写进 verify**,并且四审要专门盯这一格。
  当时那六条是对的 —— 那时后端还不保证 no-op 不写文件。0.83.0 补上"同值不 bump"、
  且我这一单实测过"空请求/同值请求文件逐字节不动"之后,前端那道判断就从
  "必要的保险"退化成"第二个判官"。**理由变了,断言才跟着变;不是反过来。**
- **多一次无谓 PUT**:碰过输入框但改回原样、或点同一个状态 pill,会真发请求。
  代价是一次锁 + 一次读改写判定,**没有写盘**(已实测)。可接受。
- 🔁 **`changed_fields` 是新增的返回字段**:响应体变宽了。它只喂"改过·看原文"这一个用途;
  **不许**让前端拿它当"要不要 reload"的依据(那又是把判断挪回前端)。
- **搬家的爆炸半径**:`parse_history` 有 `/changes`(工作区整列)和新的 `/api/todos`
  两个调用方,搬错=两个页面同时哑。缓解:搬家是纯移动(函数体一字不改),
  且既有 1001 条 python 判据里已有大量 `## 变更历史` 用例压着;另加一条**同源断言**
  (同一份档案文本,`/changes` 与 `/api/todos` 对同一条 cnum 给出的 note 必须相等)。
- **`collect` 变慢**:每个项目文件多跑一次 `parse_history`(整文一次线性扫)。
  待办页本来就是每请求现读、零缓存;项目数是几十量级,可忽略。**但要在判据里
  钉住"每文件只解析一次"**(别写成对每条变更行各解析一遍 —— 那是 O(n²))。
- **`note` 进了待办页载荷 = 多一处会显示业主原话的地方**。已经在工作区显示,
  不新增数据出口(同一台机器的同一个前端),不构成新面。

## 双出对差(读了 `gpt-5.6-sol` 那版之后)

日志:`/root/aiwork/logs/note-source-plan-sol.log`(它禁读本 track 的工件,方向独立出的)。
**我的原版已 commit(`dd05720`/`a92860c`)在读它之前,反锚定成立。**

**它抓到、我原方案确实错的(已折进上面,标 🔁)**:

- 🔴 **`new_status` 无条件置 `changed`**。我原方案让前端"照发状态",而后端这一支根本
  没有同值比较 ⇒ **点一下原状态就假 bump 页脚**。我实查了 `ds_tools.py:594-596`,
  它说的是对的。**这是 0.83.0 LOW-1 的同一个形状换了个字段** —— 我刚修完那个,
  转头在同一个函数里踩了它的兄弟。
- 🔴 **「改过·看原文」会变成假标记**。改成"碰过就发"之后,`req.new_text !== undefined`
  不再等于"正文真的改了"。它给的解法(后端回 `changed_fields`)比我能想到的都干净,
  且顺带给判据一个机器可断言的 no-op 口径。
- **"只发碰过的字段"而不是"把预填的全发回去"**。我原方案会在没有陈旧编辑保护的情况下
  **主动扩大覆盖窗口**。这条我读到时的第一反应是"影响面小" —— 而"影响面小,记账不修"
  正是上一单四审教我的那个坑(F1→F10),所以照收。
- **`body.get("note")` 把缺省和 `null` 合并**:我原方案只说了"用 `"note" in body`",
  但没说 `null` 怎么办 ⇒ 会留下第二个拼法。已补成 400。
- **同源相等题是假绿**:`test_01_todos_matches_collect` 这种"响应 == collect()"的断言,
  **两边一起漏掉 note 它照样全绿**。判据必须断言档案里那条备注的**具体值**。
  这条直接改了我的判据设计。
- **冷启动 e2e** 比我写的 `reload()` 更强:档案里**预先就有**备注,浏览器第一次打开
  待办页就该显示 —— `reload()` 只证明"这次会话的写入活过了刷新",冷启动才证明
  "显示的是档案"。已换成两条都要。
- `batchEditRequests` 也有一处前端同值跳过(`todo.ts:170`),我漏了;
  `ChangesColumn` 那侧同样要改成"碰过才发",我原方案只写了待办页。

**它提了、我判定不采纳的(理由写下来,免得下次重议)**:

- **`note: null` 当删除、`note: ""` 回 400**:见 Approach §6 的三条理由。
  **保留分歧**,并已写进四审要盯的清单。
- **`edit_change` 返回体加 `changed_fields` 之外还回整包新值**:没提,但顺路说清 ——
  不加。前端保存后一律 `reload()`,回显整包等于第二条读路径。

**我原方案里它没提、我自己保留的**:`ds_web:934` 那个调用点要改名到新家且
**不留别名**(它只说"删掉旧的 `ds_tools.parse_history`",没说别名的事,但结论一致)。

## Alternatives considered

- **让 `ds_web` 自己把 note 拼进 todos 载荷**(不动 `ds_todo.collect`):最省事,
  但 `collect` 的 docstring 自称"结构化核心(唯一真相源):render 与 /api/todos 都吃这个"
  —— 在 web 层旁路拼装等于再造一个真相源,与本单的目的正相反。不选。
- **搬进 `ds_common`(我的原版)或新建 `bin/ds_history.py`**:两者都能编译、都无环。
  不选的理由见 Approach §1 —— 读模型该凑齐在 `ds_todo`,而不是再多一个"格式知识在哪儿"的答案。
- **读侧也改成 `note: string | null` 恒有键**:我一度想统一成"状态型载荷",
  但那会让 `/changes` 和 `/api/todos` 的既有约定分裂,或者逼我一起改 `/changes`
  (工作区那侧的读契约,不在本单范围)。理由见 Approach §2。不选。
- **保留前端等值判断,只补一条注释说明"后端也判"**:那是把今天的病写成文档。不选。

## Test strategy (oracle)

主 agent 亲写,执行腿逐字节 off-limits。**红检先行**(判据先单独 commit)。

1. **核心(pytest,`tests/test_ds_todo.py` / `test_ds_tools.py`)**
   - `collect` 的 open 条目:有备注 ⇒ 带 `note` 且**等于档案里那行的具体内容**
     (🔁 写死期望字符串,不许写成"等于 parse_history 的结果" —— 见下"能被什么骗过"第①条);
     无备注 ⇒ **没有该键**。
   - 备注行**夹在留痕行中间**、邻居 cnum(C1 / C12)各有备注 ⇒ 不串桶;
     🔁 **两个项目各有 C1 且各有备注 ⇒ 不跨项目串号**;`cnum=None` 的残缺行 ⇒ 不认领任何备注。
   - 端到端一小步:`edit_change` 清空备注后再 `collect` ⇒ 该条 **没有 `note` 键**
     (0.83.0 修的"存得进去"与本单修的"读得出来"接上了)。
   - 搬家后的回归锚:`ds_tools` 的写侧用例(⑤系列 + e01–e09)一条不许退。
   - 环闸:`tests/test_no_import_cycles.py` 已有,搬家后必须仍绿(**ds_todo 不许 import ds_tools**)。
   - 🔁 **`changed_fields` 的四条**:三字段全给同值 ⇒ `[]` 且文件逐字节不动、页脚不动;
     只改备注 ⇒ `["note"]` 且**正文不留假留痕**;只改状态 ⇒ `["status"]`;
     **状态给同值 ⇒ `[]` 且页脚不 bump**(这条今天必红 —— `new_status` 分支无条件置 changed)。
   - 🔁 归一重复备注行**本身**算 `note` 真改动(⑤j 的延伸,防"归一被算成 no-op")。
2. **HTTP 面(`tests/test_ds_web_api.py`)**
   - `/api/todos` 载荷带 `note`,**断言具体值**;清空后该键消失。
   - **跨端点同源**:同一条 cnum,`/api/todos` 与 `/api/projects/<key>/changes` 的 note 一致
     (🔁 这条**只当加固**,不当主断言 —— 两边一起漏 note 它照样绿)。
   - 🔁 **三态分得开**:body 里**没有** `note` 键 ⇒ 既有备注不动;`note: ""` ⇒ 删除;
     `note: null` ⇒ **400 且文件逐字节不动**(`new_status`/`new_text` 同样各一条)。
   - 🔁 响应体带 `changed_fields`;同值请求 ⇒ `[]`。
3. **前端纯逻辑(`node --test tests/test_workbench_p4.mjs`)**
   六条旧断言**逐条换成更强的**,对照表(左=今天,右=改后;**右边每一条都比左边多说了事**):

   | 场景(draft = 用户碰过的字段) | 今天的断言 | 换成 |
   |---|---|---|
   | 碰了状态、值==原状态 | `=== null` | 返回请求,`new_status === "进行中"`(照发,后端判 no-op) |
   | 状态非法(`"done"`) | `=== null` | 返回请求,**不含** `new_status` 键(**校验保留**) |
   | 碰了正文、值==原正文 | `=== null` | 返回请求,`new_text === "客厅吊顶改平顶"` |
   | 🔁 碰了正文、清空了 | `=== null` | 返回请求,`new_text === ""`(**照发**,后端回 `empty_text`) |
   | 碰了备注、值==原备注 | `=== null` | 返回请求,`note === "业主确认"` |

   | 🔁 一个字段都没碰(`draft={}`) | — | 返回请求,**只有** `project`+`cnum`,不含三个可写键 |

   - **不动的锚**:`cnum === null` ⇒ 仍返回 `null`(不可寻址,这是校验不是判定)。

   - 旧断言在同一个 commit 里替换掉并写明理由,**不是留着让它红**;
     红检要显示这些新断言在旧实现下**全红**。

   - 🔁 **I4 跨面**:工作区改了备注 → 切到待办页 → 看到的是**新值**(两个页面同一个真相源)。

**这个 oracle 能被什么骗过?**

- 🔴 **第①条(双出替我抓到的,原来我没写):同源相等题是假绿。** 形如
  「`/api/todos` 的响应 == `collect()` 的结果」或「`collect` 的 note == `parse_history` 的 note」
  这种断言,**两边一起漏掉 note 时照样全绿**。⇒ 主断言一律**写死档案里那条备注的具体字符串**,
  同源相等只当加固。(我原方案把同源相等写成了主断言之一,已改。)
- **最可能的假绿**:我在判据里造的档案都是"备注写在 `## 变更历史` 段里"的**规范档案**,
  而业主机器上的老档案可能有**手写的、格式歪一点的**备注行(全角冒号已覆盖,
  前导零 `C03` 已知不覆盖、上一单记了账)。判据全绿 ≠ 他那份两年的档案里每条都读得出来。
  **接得住的只有真机**:验收清单让他挑一条**很久以前**写的备注看还在不在。
- **第二种**:e2e 的 `reload()` 证明了"刷新后还在",但**没有证明"换一台电脑还在"** ——
  这两件事在实现上是同一件(都从档案读),但只有真机能验第二件。写进验收清单。
- **第三种**:前端判据只测 `buildEditRequest` 这个纯函数,**测不到"点了保存到底发没发请求"**。
  如果 `save()` 里还留着别的短路(比如 `draft` 为空就 return),纯函数全绿而页面依旧不发。
  ⇒ I 组 e2e 用**磁盘内容**做锚,不看返回值;并且**读一遍 `save()` 的全部提前 return**
  (闸③人眼,写进 verify)。
