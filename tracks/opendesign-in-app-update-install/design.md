- 规划双出: **已跑**,结论追加在本文件末尾;全文 `evidence/dualplan-gpt56sol.md`

## 这一单的硬约束(读出来的,不是推的)

🔴 **跑更新的那段代码,不能住在 `$INSTDIR` 里。**

Windows 上正在运行的 `.exe` / `.dll` / `.pyd` 被文件系统锁着,安装器覆盖不了。而:

| 谁 | 住哪 | 更新时的处境 |
|---|---|---|
| `OpenDesign.exe`(外壳) | `$INSTDIR\` | 锁着自己 |
| `python\python.exe`(所有后端腿) | `$INSTDIR\python\` | 锁着自己 |
| `ds\bin\*.py` | `$INSTDIR\ds\` | 被上面那个 python 打开着 |

⇒ **软件不可能在自己活着的时候更新自己。** 这不是取舍,是这一单所有方案的共同前提。

第二条,来自 `OpenDesign.nsi:92` 那句自己写的注释:程序在跑时 `RMDir /r` 删不掉会
**悄悄跳过** ⇒ 边跑边装 = 一半新一半旧、一声不吭。**所以"收摊收干净"必须是可判定的
前置条件,不是"尽力而为"。**

第三条,读源码确认的两件好事(省掉两个我本来以为要做的动作):

- `InstallDirRegKey HKCU "Software\OpenDesign" "InstallDir"`(`.nsi:50`)
  ⇒ 静默安装会自己定位到已装位置,**不用我们猜路径**(仍然显式传 `/D=` 兜底)。
- `CheckDirEmpty` 是 `MUI_PAGE_CUSTOMFUNCTION_LEAVE`,**静默模式下目录页不跑 ⇒ 它根本不执行**;
  且哨兵 `ds\bin\ds_shell.py` 在,覆盖安装本来就放行。
  ⇒ 更新不会被那道"目录非空"拦截挡住。

## Approach:三段接力,接力棒放在 `%TEMP%`

> ⚠️ **本节 09-08 19:5x 重写过。** 原文写的是「备份整棵树 → 就地覆盖 → 失败从备份拷回」,
> 那一套在同一天的第一性原理复盘里被换掉了(理由在本文件末节)。**改的是形态,不是方案** ——
> 三段接力、接力棒放 `%TEMP%` 都没变。之所以回来改这一段而不是只在末尾追加:
> 一份 spec 同时讲两套机制,下一步就是照着错的那套写判据。
> (这正是本单已经抓到两次的同一种病:**把事实复制到第二个地方,只更新其中一个**。)

```
段①  旧版软件(还活着,python,可单元测试;界面照常能用)
     查到新版 → 业主点「更新」→ 下载到 %TEMP% → sha256 对 GitHub 的 digest
     → 静默装进 ...\Programs\OpenDesign.new(/S /UPDATE /D=…)
     → 查新树完整(哨兵 ds\bin\ds_shell.py + 版本号文件 == 期望版本)
     → 写接力脚本 → 脱离启动它 → 调 shutdown() 自己退干净
     ⇒ **到这一步为止,活树一个字节没被碰过**;任何失败 = 删掉 .new,当无事发生
                                              ↓
段②  接力脚本(住 %TEMP%,只依赖 System32:cmd.exe / curl.exe)
     等锁真松开、确认端口和进程真没了(**收不干净就删掉 .new 收工,绝不换名**)
     → 两次改名:OpenDesign → OpenDesign.old,OpenDesign.new → OpenDesign
     → 拉起 → 问 /api/health(带一次性 nonce、绕开系统代理)
     → 认出新版本号 = 成功,删 OpenDesign.old │ 失败 = 改名换回来、重起旧版
                                              ↓
段③  新版软件
     正常启动。**它在 /api/health 里报出的那个版本号(且答得出 nonce),
     就是这一单的收口判据。**
```

**危险窗口 = 两次改名之间(毫秒级)**,不再是整个安装过程(数十秒)。

**为什么接力棒必须换手**:段① 住在 `$INSTDIR` 里,它必须先死,安装器才动得了文件;
而它一死就没人验收、没人回滚了。所以中间必须有一个**不住在 `$INSTDIR`、且能活过段①之死**
的东西。这就是段② 存在的全部理由。

**为什么段② 用 `.cmd` 而不是别的**:见下面 Alternatives。

**判据在哪一段**:段① 全部可单元测试(python);段② 靠 Windows CI 真跑
(`e1` 真更新成功 / `e2` 改坏一个字节要拒装);段③ 是回显,只认 `/api/health` 的版本号。

## 死线(不是目标,是死线)

🔴 **更新前后,`%LOCALAPPDATA%\OpenDesign\Data\` 与 `UserData\` 逐字节不变。**

⚠️ **这条比 tasks.md 里写的窄一层,是我故意收窄的**:那里写的是整个数据根
`%LOCALAPPDATA%\OpenDesign\` 逐字节不变,但 `Logs\` 就在这个根下面,**更新过程本身
就在往里写**(外壳记自己的关机日志、段②记更新日志)。照字面写,这条判据**永远绿不了**;
而一条永远红的判据,下一步一定会被我自己调松 —— 那就是"改考卷让自己及格"。
⇒ 收紧到真正要守的两层:`Data\`(项目档案、客户备忘、参考图库)和 `UserData\`。
`Logs\` 明确豁免,**并且在判据里写明豁免的是哪一个目录**,不许用通配符糊过去。

## Key trade-offs / risks

1. **段② 是这一单唯一"Linux 上验不了"的部分。** `.cmd` 语法坑多、错误处理弱,
   而本项目已经为"Windows 独有、写反了没有闸看得出来"栽过
   (`.nsi` 里那句 `IfFileExists 0 ok` 就是被四审点名的不可验控制流)。
   ⇒ 压法:**把判断尽量前移到段①**(python,可测),`.cmd` 只做五个动作:
   等 / 装 / 起 / 问 / (失败则换回)。**不在 `.cmd` 里做任何决策分支之外的计算。**
   ⇒ 并且 Windows CI 必须真跑它,不许只做静态检查。

2. **回滚只能由段② 做,而段② 自己也可能死。** 段② 死了 ⇒ 业主看到的是"软件关了没再打开"。
   ⇒ 兜底:段② 全程往 `%LOCALAPPDATA%\OpenDesign\Logs\更新.log` 记流水
   (`Logs\` 正是上面豁免的那个目录),至少下次能查得动。
   **这是明账:我们没有"更新守护进程",段②死了就没人管了。不假装有。**

3. **信任根仍然只有一条**:HTTPS 到 github.com + GitHub 给的 `digest`(sha256)。
   挡得住"下坏了/下半截/中间人换包",**挡不住"GitHub 账号被盗后换了资产"** ——
   没有代码签名证书。第一刀就是这么记的账,这一刀**代价变实了**(真的会执行那个 exe),
   但结论不变:明账,不假装有。

4. **`.new` / `.old` 放哪**(重拍后取代了原来那条「备份放哪」):都放 `$INSTDIR` 的同级
   (`...\Programs\OpenDesign.new` / `.old`),**不放数据根**(会踩死线)、
   **不放 `$INSTDIR` 里**(会被安装器一起覆盖)。成功即删 `.old`;失败留着,日志写清它在哪。
   ⚠️ 同级目录得先确认可写、且空间够 —— 这里放的是整棵树不是增量差分。

5. **`pick_latest` 不放宽**(继承的账 D,本单重拍):第一刀时 `asset` 字段没有消费方,
   放宽与否无所谓;第二刀**真的要下载它** ⇒ 指向一个没有安装包的 release =
   下载必然失败。**收紧的理由从"洁癖"变成了"不然会真炸"。**

6. **版本化布局 + 指针:不做**(开工前第 1 块板)。它服务的是增量更新,
   而增量在 proposal 的 non-goals 里。先把全量装对。**这条写下来是为了下次有人问
   "为什么还是平铺覆盖"时,答案是"拍过板"而不是"忘了"。**

## Alternatives considered

- **A. 让安装器自己等(改 `.nsi` 加试锁循环)。** 少一个组件,NSIS 有 `FileOpen` 试锁的惯用法。
  **没选的原因**:它解决不了验收和回滚 —— 装完之后谁去问 `/api/health`?谁在起不来时换回去?
  而且把逻辑塞进 `.nsi` = 塞进本项目**最验不动**的那个文件。
- **C. 打一个独立的 `updater.exe`(PyInstaller 单文件)。** 能用 python 写、能单元测试,
  比 `.cmd` 干净得多。**没选的原因**:多一条构建产物 + 多一条供应链 + 体积 +10MB,
  而且**它自己也需要被更新**(住 `$INSTDIR` 就同样被锁,住别处就成了装不掉的残留)。
  ⇒ **如果段② 的 `.cmd` 在 Windows CI 上被证明扛不住,这是第一顺位的退路**,不是被否决的方案。
- **D. 自动静默更新(开机自己换掉软件)。** proposal 明确 non-goal —— 必须他点。

⚠️ **`t6` 和 `t17` 咬的是段② 的行为,而段② 是 `.cmd`、只有 Windows 上跑得起来。**
在 Linux 上给 `.cmd` 写个模拟器然后断言模拟器 —— 那是**证明不了任何事的绿**,
正是本节下面「最像绿其实错」警告的那一类。⇒ 拆成两半,两半都要有:

- **python 侧**:接力脚本是我们**生成**的 ⇒ 断言生成出来的那段文本里,
  收摊闸在任何一次改名**之前**、失败分支真的删 `.new`、回滚分支真的把 `.old` 换回来。
  这是**机械契约**,不是注释级契约 —— 形状照抄本单已经做过的 `t12a/t12b`(commit `46c0c90`)。
- **Windows CI 侧**:`e3`/`e4` 真跑(见下)。**行为的收口在那里,不在 python。**

### 段②/③(Windows CI,真跑)

- `e1` 装旧版 → 走完整更新 → 断言 `/api/health` = 新版本号 **且截图里窗口在**
- `e2` 把下回来的 exe 改坏一个字节 → 断言拒装,**且旧版还打得开**
- `e3` 造一个赖着的进程/占着端口 → 断言**没换名、`.new` 被删、旧版照常能用**(`t6` 的行为半)
- `e4` 在两次改名之间打断 → 断言能换回来且旧版起得来(`t17` 的行为半)

### 这个 oracle 能被什么骗过?

**"用户眼里的成功"= 他点一下,过一会儿软件自己回来了,东西都还在,右下角写着新版本号。**
我的断言离它还差:

1. **`/api/health` 报新版本号 ≠ 界面能用。** 本项目栽过一模一样的:0.94 那次
   `/api/health` 一切正常而**窗口全白**(React 卸了整棵树)。
   ⇒ 所以 `e1` 必须**带截图断言窗口在**,不能只信 HTTP 返回。这条是从史料抄来的,不是我想出来的。
2. **CI 上的成功证明不了他家那台机器。** CI 没有杀软(会把下回来的 exe 秒删)、
   没有他家那条网(下 43MB 可能超时)、没有 VPN。
   ⇒ 这两件**结构上只有业主验得到**,写进真机清单,**不假装 CI 覆盖了它们**。
3. **最像绿其实错的那一种:更新成功了,但档案没了。** 断言全绿(版本号对、窗口在),
   而业主打开发现项目都不见了。⇒ 这就是 `t7` 死线存在的理由,
   而且它必须比对**真实文件内容**,不是"目录还在"。
4. **段② 死在半路,断言根本跑不到。** 测试会看到"超时",而业主看到的是"软件关了没回来"。
   ⇒ `e1` 的失败必须区分**"装错了"和"没装成"**,两种在日志里长得不一样。

## 它打穿的三处(全部核实成立,不是措辞)

### 🔴 一、我把一句推论写成了事实

我在上面写:「`OpenDesign.exe`(外壳)…… 锁着自己」。**假的。**

`installer/launcher.nsi:50-51` 的注释白纸黑字:

> `; Exec 而不是 ExecWait:起完就退,别让启动器一直挂在任务管理器里。`
> `Exec '"$EXEDIR\python\pythonw.exe" "$EXEDIR\ds\bin\ds_shell.py"'`

⇒ `OpenDesign.exe` 拉起 python 之后**立刻退出**,根本不常驻,也就谈不上"锁着自己"。
真正占着文件的是 `python\pythonw.exe` 和它打开的 `ds\bin\*.py`。

**结论(软件不能在自己活着的时候更新自己)仍然成立,但我给的理由是假的。**
自检句照旧:**这个「因为」是读来的还是推来的。** 我上面那张表里三行有一行是推的。

### 🔴 二、最值钱的一条:我立的死线,安装器自己就做不到

上面写:「更新前后 `Data\` 与 `UserData\` 逐字节不变」。

`installer/OpenDesign.nsi:143` 在主安装 Section 里 `Call ProvisionConfig`,
而 `OpenDesign.nsi:245` 那一行是:

> `nsExec::ExecToLog '"$INSTDIR\python\python.exe" "$INSTDIR\ds\bin\ds_provision.py"`
> `  --home "${DATA_ROOT}\UserData" --ds-root "$INSTDIR\ds"'`

⇒ **每一次安装(静默也一样)都会往 `UserData\` 里写。** 我那条死线**结构上就绿不了** ——
不是有 bug,是我要求了一件安装器本来就做不到的事。
`bin/ds_shell_core.py` 的 `patch_config` 是第二个写口(shell 启动时改 nanobot 配置)。

⚠️ 这一条最难看的地方在于:**我上面刚刚才因为同一种病收窄过一次死线**
(把 `Logs\` 从"逐字节不变"里摘出去),理由写的就是"永远红的判据下一步会被我自己调松"。
**然后我在同一段话里又立了一条永远红的。**

⇒ **修正后的死线**(这才是能守住、且守得对的那条):

| 目录 | 口径 | 谁在写 |
|---|---|---|
| `Data\` | 🔴 **逐字节不变**(项目档案、客户备忘、参考图库) | 更新过程中**没有任何合法写口**,变了就是事故 |
| `UserData\` | **只允许 provisioning 碰它自己那几个具名字段**,其余逐字节不变 | `ds_provision.py` / `patch_config` |
| `Logs\` | 豁免(具名,不许用通配符) | 外壳、更新器自己 |

并且 `UserData\` 那一格的正确做法不是"把判据放松到能过",而是
**给安装器加一个 `/UPDATE` 档:更新时不跑 provisioning**(它是给首装用的)。
判据照旧要求 `UserData\` 逐字节不变 —— **改的是实现,不是考卷**。
(这条同时消掉了 gpt 提的"更新模式必须禁止 provisioning"那条风险。)

### 🔴 三、装完之后问"你几版",可能是**旧进程**在回答

我上面写「新起来的进程自己在 `/api/health` 报出新版本号才算成功」,

去问 health 拿到的是它。版本号不同这次会判失败(侥幸),

⇒ 采纳:**一次性 nonce**。更新器生成随机串,通过启动环境交给新进程,

⇒ 一并采纳:**问 health 时绕开系统代理**。业主机器上跑着 VPN,
而 0.98.1 修的正是"就绪探针走了系统代理 ⇒ 死等 60s ⇒ 启动失败"。
**CI 上没有代理,这个坑在自动判据里永远暴露不出来。**

## 它提了、我核过、但**不采纳**的

- **常驻 `UpdateHost`(每次启动都经过它,能在断电后回滚未提交事务)。**

  从另一个方向把复杂度加回来。⇒ 维持一次性接力脚本 + 事务日志;
  **"段② 死在半路就没人管了"仍然是明账,不假装有。**

# 接线:谁来关停,以及怎么把"该交棒了"传过去(2026-09-08 夜,开工前落盘)

上面那三段写的是**做什么**,这一节补的是**接到哪儿** —— 而它有一个我原先没写、
差点接错地方的事实:

## 🔴 关停整套软件的能力不在 `ds_web` 手里

`Supervisor.shutdown()` 住在**外壳**(`ds_shell.py` 起的那个进程)里,
它才是持有全部子进程、能把 nanobot / ds_web / 三个 MCP 一起收干净的那个。
`ds_web` 是它的孩子,**手上没有任何通往外壳的东西** —— 我 grep 过。

⇒ 所以「段① 收尾调 shutdown() 自己退干净」这句话里的"自己",**不是 ds_web,是外壳**。

**也不能让 `.cmd` 去暴力杀。** 收摊那一刻业主的档案可能正在被写(PKB 是 markdown,
写到一半被 kill 就是半个文件)。而 `Data\` 逐字节不变是这一单的死线 ——
**用暴力杀去满足"收摊干净",等于为了过一条判据去踩另一条。** 收摊必须是优雅关停。

## 传导走哪条路:复用已有的单实例锁通道,不新造 IPC

这条路**已经在生产里跑着**:业主填完 key 之后,`ds_web` 就是这么请外壳重启网关的。

- 外壳把锁端口写进 `DS_SHELL_LOCK_PORT` 交给孩子(`ds_shell_core.child_env`);
- `ds_web` 连上去发 `LOCK_HELLO + <动词>`,外壳回一个**点名了动词的** OK;
- 现有动词:`RESTART-BACKEND`。**新增:`UPDATE-HANDOFF`**。

沿用它自带的两条好性质,一条都不改:

1. **认不出的动词一律退回 SHOW**(把窗口叫到前台)。老外壳收到新动词只会闪一下窗口,
   不会乱来 —— 版本错配时是"没反应",不是"半路死掉"。
2. **只有点名了动词的应答才算数**(`_restart_verdict` 那条纪律)。裸 `OK` = 老外壳收下了帧
   但做的是别的事。**报成功就必须是真的。**

## 顺序是这一节最要紧的一件事

```
① ds_web:准备(下载 → 校验 → 装 .new → 查新树 → 写接力脚本)   ← 已完成,t4~t18
② ds_web:**起接力脚本(脱离)**,确认它真起来了
③ ds_web:再请外壳 UPDATE-HANDOFF
④ 外壳:stop_backend() 收干净 → 自己退
⑤ 接力脚本:等到端口/进程真空了 → 两次改名 → 拉起 → 问 health(带 nonce)
```

🔴 **② 和 ③ 的顺序反了会出这一单最怕的那个形态**:外壳先把 `ds_web` 杀了,
而接力脚本还没人起 ⇒ **业主看到的是"软件关了,没再打开"**,并且没有任何东西会去回滚。
⇒ 判据 `t22` 钉这个顺序。

## 失败即安全(每一步都往"当无事发生"塌)

| 哪一步没成 | 结果 |
|---|---|
| 准备阶段任一步 | 删 `.new`,活树没动过,界面报错误 —— 已由 `t4/t5/t16` 钉住 |
| 接力脚本起不来 | **不发 `UPDATE-HANDOFF`**,软件照常活着 |
| 外壳不认这个动词(老外壳) | 接力脚本的收摊闸永远等不到端口空 ⇒ 超时 ⇒ **自己删掉 `.new` 收工** |
| 外壳收了但没关干净 | 同上,收摊闸不放行 ⇒ 不换名 |

⇒ **`ds_web` 一律照抄 `ds_shell_bridge_restart` 那条纪律:任何一步不确定,就报"没能自动更新"。**
宁可让业主多点一次手动安装,也不要一句会撒谎的"更新已开始" —— 那句话之后他会关掉浏览器等着,
而实际上什么都没发生。

|---|---|
| 在真仓库发一个测试用 release | 🔴 **业主的软件也会看见它**。不做 |
| 给产品加个"更新源地址"环境变量 | 🔴 等于给更新通道开一个改向口(谁能设环境变量,谁就能让软件去装任意 exe)。**不为测试改产品** |
| 绕过查更新,直接调 `apply_update()` | 不走端点 ⇒ `check → apply → 交棒 → 外壳收摊` 这条接线等于没测 |
| ✅ **只在那台用完就扔的 runner 上**:hosts 把 `api.github.com` / `github.com` 指到本机,本机起一个 HTTPS 替身,替身证书的 CA 导进这台机器的受信根 | 产品代码零改动,走的是真的 DNS→TLS→urllib 那条路。内嵌 python 3.12 的 `load_default_certs` 在 Windows 上读系统证书库 |

替身给出的 releases JSON **必须是真产品代码认的形状** ⇒ 本机判据直接拿它喂 `ds_update.decide()`,
证书链拿本机 python 按 `api.github.com` 真握一次手。**这两件在 CI 之前就能判,不花 Windows 那一趟。**

## 新旧两个包从同一个 commit 打

旧版必须**带着更新代码**(0.98.3 没有这个按钮),所以两个包都从当前 commit 打:
旧 = 仓里的 `VERSION`,新 = 同一份代码只把 `VERSION` 改成 `0.98.900`(纯 CI 用,永不发布)。
在 ubuntu job 里跑真的 `installer/build-installer.sh`(和发给业主的是同一条流水线)。

## 五个场景(每个场景前**重装旧版**,互不污染)

驱动方式:和界面按钮一样调 `GET /api/update/check?force=1` → `POST /api/update/apply`。
按钮本身的接线由 `u27~u37` 管,这里不点界面。

| id | 注入 | 必须看到 |
|---|---|---|
| `e2` | 替身把安装包翻一个字节 | `stage=verify`、活树不变、没有 `.new`/`.old`、旧版照常在答 |
| `e3` | 占住活树里的哨兵文件(`FileShare.None`)= 赖着不走的东西 | 接力脚本放弃:活树不变、`.new` 删掉、没有 `.old`;放手后旧版起得来 |
| `e4` | 新树装好后占住 `.new` 里一个文件 ⇒ **第二次改名必然失败** | 回滚:活树换回旧版、没有 `.old`、**旧版被接力脚本自己拉起来** |
| `e5` 🆕 | 新树装好后把 `.new` 里 `ds_web.py` 的版本号改掉 ⇒ **新版起得来但收口认不出它** | 回滚:活树是旧版、在答的是旧版、没有 `.old`、旧树没被塞进新树里 |
| `e1` | 无 | 在答的是新版、活树版本号文件是新版、`.old`/`.new` 都清掉、窗口在、档案标记逐字节不变 |

**`e5` 是我加的**:`t17` 那句"换名中断/**新版起不来** ⇒ 改回名字"的后半句,e1~e4 没人问。
读代码时怀疑:回滚段 `move "%LIVE%" "%NEWT%"` 之前**没有先关掉正在跑的新版** ⇒ 活树被占着移不走 ⇒
下一句 `move "%OLDT%" "%LIVE%"` 在 LIVE 已存在时会把旧树**塞进**新树里。**这是怀疑,由 e5 答,不先修。**

同样是怀疑、由 e1/e3/e4 顺带答的:收摊闸的文件锁检查查的是 `ds_shell.py`,而 python 跑起来后
**并不锁着 .py 文件**(锁着的是 `pythonw.exe` 和 `.pyd`)⇒ 可能端口一空就去改名、而进程还没退完 ⇒
第一次改名失败 ⇒ `exit /b 3` ⇒ **软件关了、没再打开**。

## 注入必须打中,否则算红

e4/e5 的注入要赶在"新树装好"和"第二次改名"之间。打晚了,更新就走成功路径 ——
**那不是"回滚正常",是这个场景没测到**。所以注入方落一个"我在第几秒打中"的事实,
判定器看到"没打中"一律 FAIL,不许当绿。

## 事实在 pwsh 里采,判定在 python 里下

照 `windows-package-probe` 付过学费的结构:本机没有 pwsh,写在 `.ps1` 里的判断谁都验不了。
⇒ `.ps1` 只采事实,判定是 `.github/scripts/update_e2e_verdict.py` 的纯函数,本机有行为判据守着;
退出码收据 `verdicts.tsv` 由 workflow 里**另一步**独立复核,且**五个场景一个都不许缺席**
(缺席 = 没跑到,不是没问题)。

## 不假装覆盖的

- **接力脚本本身在两次改名之间被杀**(断电/杀软):没有东西会去恢复 —— 这是 design 上面写明的明账,
  e4 测的是"第二次改名失败"这条**有人处理**的路。
- runner 是英文 Windows、业主是中文 Windows:接力脚本按 GBK 写出,英文机器上中文日志文件名会乱码。
  e1~e5 判的是**目录与进程的事实**,不依赖那份日志。
- 杀软、他家的网、VPN:只有真机答得了(真机清单)。
- 活树比对**排除 `__pycache__`**:python 运行时会往 `ds\bin` 写字节码缓存,那不是安装器管的文件;
  其余任何差异都进事实、会让场景红。
