# Proposal: opendesign-note-clear

- Date: 2026-08-11
- Status: open

## Goal

让「把备注清空」真的能清掉:业主在待办/工作区把备注框里的字删光再保存,
那条备注就该从档案里消失 —— 而不是原样留着、还回一个"保存成功"。

## Motivation

业主 2026-08-11 真机报的 bug。这是**写口的一个静默失败**:界面关了、没有报错,
业主有理由认为存上了,实际盘上一字未动。备注是给人看的判断依据(「业主还在犹豫」),
留着一条**已经作废的**备注比没有备注更坏 —— 它会让人按过期信息做决定。

## 真问题(第一性)

- 用户原话:「我原本待办事项里备注的 我去修改删掉原来的备注但是还是之前的备注」
- 真正要解决的是:**备注这个字段只能加和改,不能删** —— 三层里有两层各自把
  "空备注"翻译成了"你这次没打算改备注",于是清空这个动作在两处都被吃掉:
  - `web/src/todo.ts:210` `if (n && n !== originalNote.trim())` —— 清空 ⇒ `n===""`
    ⇒ 整个 note 字段不进请求体;若这次只改了备注,`buildEditRequest` 返回 `null`,
    **前端连请求都不发**就把编辑框关了(看起来像存了)。
  - `bin/ds_tools.py:568` `if note_s:` —— 即便请求带了 `note:""`,核心也当没给,
    旧的 `- Cn 备注:…` 行原样留着,**还回 `{"ok": True}`**。
- 我在这中间翻译了什么:业主说的是"修改删掉",我**一开始只读成"清空备注"这一个动作**,
  并据此收了范围。规划双出(`gpt-5.6-sol` 独立方案)点出还有第三个根因,我自己复现证实了:
  - **档案里若有两行同一 cnum 的备注**(纯文本档案,手改/助手写都造得出来),
    写侧 `_upsert_note` 只替换**第一条**、读侧 `parse_history` 却是**最后一条获胜**
    ⇒ 改了备注、读出来还是旧的。实测:盘上变成
    `['- C3 备注:业主刚说的新备注', '- C3 备注:后来的旧备注']`,读侧给出「后来的旧备注」。
  ⇒ **业主那句话的两种读法各对应一个真 bug,两个都在这一单里修。**
  仍然只有他能答的那一格:他当时点的是哪个界面的哪个框 —— 交付时请他按原动作复验。

## Scope

- in: 核心 `edit_change` 支持 `note=""` = 删除该 cnum 的备注行(无备注可删 = 纯 no-op,
  文件逐字节不动);前端 `buildEditRequest` 把"清空"当成一次真改动发出去;
  待办页乐观回显同步清掉(不留一个空的「备注:」标签)。
- in(双出加的):**备注行归一** —— 写备注时把该 cnum 的重复备注行收敛成恰好一条
  (留第一条的位置),清空时**一条不剩**,让写侧与读侧"哪条算数"不再相反。

## Non-goals

- 不动备注的**存储格式**(仍是 `## 变更历史` 段里的 `- Cn 备注:…`)。
- 不做备注的历史留痕/回收站(删了就没了,与正文改动留 `原:X` 不同 —— 备注本就是
  可覆盖的便签,现在的"改备注"也不留痕,这一单不扩张语义)。
- 不碰参考图备注(`/api/refs/update`,那条路的 `note=""` 早就是清空,行为已正确)。
- 不新开写针孔:仍走既有的 `/api/changes/edit`。
