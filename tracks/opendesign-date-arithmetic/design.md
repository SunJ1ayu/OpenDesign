## Approach

### 切面:模型管"听懂",代码管"算"

| 这件事 | 谁干 | 为什么 |
|---|---|---|
| 听懂「上周三」= 上一周的星期三 | **模型** | 语言理解,它的强项 |
| 从 2026-08-02(周日)数到上一周的周三 | **代码** | 算术,实测 6 遍错 3 遍 |
| 把「7/22(星期三)」讲给设计师听 | **模型** | 让错误看得见 |

新增**纯只读、零副作用**的工具:

```
resolve_date(expr: str, anchor: str = "") -> dict
  expr   业主原话里那个说法,原样传(「上周三」「这周五」「月底前」)
  anchor 锚点日 YYYY-MM-DD(= 业主说话那天,见契约 1c);留空 = 今天
  →  {"date": "2026-07-22", "weekday": "星期三",
      "anchor": "2026-08-02", "anchor_weekday": "星期日", "expr": "上周三"}
  或 {"error": "unknown_expr", "expr": "...", "recognized": [...]}
```

**认识的说法(有界词表,穷举可测)**:

1. `今天 / 明天 / 后天 / 大后天 / 昨天 / 前天 / 大前天`
2. `N天后 / N天前 / N天内`(N 为阿拉伯数字或一~十)
3. `{这|本|该}周X / 上周X / 上上周X / 下周X / 下下周X`,X ∈ 一二三四五六日/天
4. `月底 / 月末 / 本月底 / 这个月底 / 下月底 / 下个月底`
5. `M月D号 / M月D日`(取锚点的年份)

**故意不认的(报错,不猜)**:`月初`、`下个月初`、`这周末`、`过几天`、`尽快`。
理由:它们**本身就不精确**,而契约里已经写死「编一个日期比空着更糟」。
报错回去,助手照 §5 问设计师一句 —— 这正是我们要的行为。

### 「上周三」的两读:必须选一个,并且让设计师看得见

中文里「上周三」有两读,根子是**周日算哪一周**:
- 按 ISO(周一为首、周日为末):今天 08-02 是周日,属 07-27~08-02 那一周
  ⇒ 本周三 = 07-29,**上周三 = 07-22**
- 若把周日当作新一周的开始 ⇒ 上周三 = 07-29

`resolver_eval` 现在两个都认(考卷可以模糊),**但工具不行** —— 确定性函数
必须给一个答案。

**决定:采用 ISO,周一为一周之始。** 理由:与「下周三」对称、与 `date.isoweekday()`
同源、可穷举证明。

⚠️ **代价必须写在明处**:设计师若是另一读,工具会给出差 7 天的日期。
**这就是为什么返回里必须带 `weekday` 且契约要求助手复述** ——
「上周三 = 7 月 22 日(星期三)」摆在他眼前,他一眼能纠正。
**这不是把风险消掉,是把风险从看不见挪到看得见。**

### 契约改口(in-B)

`AGENTS.md` 契约 1c(上一单刚改过的那段)再加一句,`set_due_date` /
`set_stage` 的工具说明同步:

> 相对说法**一律先调 `resolve_date`,不许自己心算**。你算得不稳:实测同一道
> 「上周三」连答六次错了三次,每次错的日子还不一样。拿到返回的 `date` 再传给
> `set_due_date` / `set_stage`,并把 `expr = date(weekday)` 讲给设计师听。

## Key trade-offs / risks

- **最大的风险不是函数算错,是助手不调它。** 函数有穷举判据,基本不可能错;
  而"要不要调工具"是行为,只能抽样。⇒ `resolver_eval` 必须加**验它真调了工具**
  的参数题,且**连跑 3 遍**才算数(成功标准 2)。
- **多一次工具调用 = 多一次出错机会**(传错 anchor、传错 expr)。
  接受:错在这一步是**可见**的(返回里带 weekday,助手要复述),
  比现在心算错**不可见**强。
- **词表有界 = 一定会遇到不认识的说法。** 这是设计意图不是缺陷:
  报错 → 助手问设计师 → 比编一个日期好。但**如果真机上频繁报错**,
  说明词表定小了,回来补;补词表是加法,零风险。
- **ISO 两读那条**(见上):已知会在某些设计师那里差 7 天,靠"复述+人眼"兜。

## Alternatives considered

- **让 `set_due_date` 直接收「上周三」** —— 否。那是**动写口语义** ⇒ full lane,
  而且解析失败时错误埋在写口里、中间那一步不可见。现在这样多一次调用,
  但换来一个**看得见的中间结果**。
- **给模型传结构化参数**(`week_offset=-1, weekday=3`,代码只做加减)—— 否。
  多个数字旋钮,模型填错的花样比传一个原话词更多;而且**原话词能原样回显**,
  数字旋钮回显出来设计师看不懂。
- **在上下文里塞一张小日历**(「本周一=…、上周一=…」)—— 否。要动 nanobot 的
  注入(非目标),而且日历再全也挡不住"数格子"这一步。
- **修 `resolver_eval` 让它重复跑取多数** —— 否,**这是把报警器调钝**。
  08-04 已想清楚并写进 proposal 的 Non-goals。

## Test strategy (oracle)

**两层,强度天差地别,别混为一谈:**

1. **纯函数层(强,能焊死)**:`tests/test_ds_dates.py`,pytest 穷举。
   给定锚点 `2026-08-02`(周日)逐条钉死每个说法的唯一答案;
   跨月/跨年边界(`月底` 落在 1/31、`下月底` 从 1/31 出发 → 2/28)、
   闰年(2028-02-29)、不认识的说法必须 `unknown_expr`。
   **这是本单最值钱的部分:日期算术是少数能被证明的东西。**
2. **行为层(弱,只能抽样)**:`resolver_eval` 参数题,验助手**真的调了
   `resolve_date`** 而不是心算,且把返回值传对。**连跑 3 遍**。

### 这个 oracle 能被什么骗过?

- **穷举全绿但助手根本不调它** —— 这是本单最可能的失败方式,而纯函数判据
  对此**完全是瞎的**。只有行为层接得住,而行为层是抽样。⇒ 已定"连跑 3 遍"。
- **助手调了、但传错锚点**(把录入日当锚点)—— 函数会忠实地算出一个错日期,
  **两层判据都判绿**。接不住。⇒ 只有真机 + 助手复述那句话能兜。
- **词表覆盖不到真实说法** —— 穷举判据只能证明"我列的这些是对的",
  证明不了"我列全了"。真机上才知道设计师和业主到底怎么说话。
- **ISO 两读** —— 判据会永远判我选的那一读为对,**规格错了判据也会齐声说对**。
  这是典型的"过审只证明合乎规格,不证明规格对"。⇒ 靠真机 + 复述。
