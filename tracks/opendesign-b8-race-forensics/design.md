# Design: opendesign-b8-race-forensics

- Change: opendesign-b8-race-forensics
- Status: draft

## Goal-to-design check

- **当前行为 → 拟改变的行为**:业主那边**什么都不会变**(本单只动判据 `test_b8`,不动产品代码)。
  变的是我下次看见这条红时手里有什么:现在是一行 `0 != 1` 加两个端口号,
  要靠事后推理分辨"判据自己污染"还是"业主双击两下一个窗口都不开";
  改完是**当场分型**——段内本来有人就红在前置断言上(判据环境脏),
  段内本来无人却 0 份赢才是产品缺陷,且红的那一刻把现场打出来。
  业主付出的:无(判据改动,不进安装包)。
- **检查深度与触发事实**:先做**最小实验**(已做,见下),因为两个假设的处置完全相反
  (①改判据 / ②产品缺陷),猜错任一边都是灾难性的:把 ② 当 ① 处理就是"调钝报警器"。
  实验做完再上独立腿,问的不是"机制对不对"(已有收据),而是"你这次改断言是不是放水"。
- **关键前提**(可证伪的主张 → 证据):
  1. 「`acquired=False` 必须有一个真 InstanceLock 在段内应答」——
     `bin/ds_shell_core.py:_acquire` 只有两条返回 False 的路径:`_scan` 命中、
     `_someone_ahead_of` 命中;两条都走 `_send_show`,它要求 `recv_line == b"OK"`
     逐字节相等(`ds_shell_core.py` `_send_show`)。⇒ **假设 ② 的"没有任何实例在跑
     却都误判"与实现自相矛盾**,当前实现下不可达。
  2. 「① 能造出那条读数的**确切形状**」—— 已造出。`probes/crossround.py` E1:
     段内放一个真锁 ⇒ `0 份赢`,且两份 `port` 同值、等于占位端口,
     与 09-20 的 `[{'acquired': False, 'port': 40305}, {...同值}]` 逐字段同形。
     收据 `evidence/crossround-run1.txt`。
  3. 「① 在 b8 现有结构里**自然可达**」—— `LOCK_CHILD` 的赢家 `time.sleep(120)` 不退,
     而 6 轮共用一个 `addCleanup(self.reap, p)` ⇒ **前面轮次的赢家全程活着并持续监听**;
     每轮 `base = free_port()` 是 32768–60999 里的随机值,段宽 6 格
     (`_ports()` = `range(base, base+span+1)`)。E3 轮5 当场抓到现行:
     `段内前轮存活=[50779] => 0 份赢`,两份 port 都是 50779。
  4. 🔴「污染源**不止 b8 自己前几轮**」—— 这条是实验给的,proposal 里我写窄了。
     E3 轮3 段内存活账本是空的却也 0 份赢,port=42495 = **E2 的赢家端口**:
     进程里**任何**还活着的 `sleep(120)` 赢家都算。在真判据里 b1~b7 的赢家由各自用例
     的 cleanup 收掉、不跨方法,所以同进程只剩 b8 自己那 5 个;但修法不能只针对"前几轮",
     前置断言必须问"段内现在有没有人",不是"我记账的那几个在不在段内"。
     🔴 2026-09-21 外审(subdeepseek F5b)又补了**进程之外**的一支:开发机上真在跑的
     OpenDesign、或另一个并发会话的实例,落进段内同样造出两份同值的读数。
     ⇒ 09-20 那次是本用例自己的跨轮残留、还是外来实例,**分不出**(见"未解决项");
     修法不变(前置断言两种都抓得住),但话不能说成"那次就是跨轮残留"。
- **完全实现仍可能失败**:改完之后 b8 仍然可能红,而我**仍然**分不清
  ——如果取证块本身在红的那一刻拿不到现场(权限不够读不到监听者 PID、
  `ss` 不在、子进程已退出 stderr 被关)。那就退回今天的处境:一行数字、事后全靠推理。
  ⇒ 取证块必须**自带降级**且降级要出声(打印"取不到,因为 X"),不许静默空白。
  🔴 2026-09-21 补:光"出声"还不够 —— 取不到的时候**连分型都不许下**
  (原来的实现会把查不出归属的应答者默认算成"环境残留",等于在猜;见 trade-off 末条)。
- **独立意见与核实**:实验是我自己做的;E3 轮3 那条**推翻了我 proposal 里的表述**
  (我写的是"落进后面某轮的锁位段"这一种,实际是任意存活赢家)。改窄的话已在前提 4 认账。
- **未解决项**:09-20 那一次 `40305` 上**究竟**是谁,证据没了、不可能再取。
  本单**不宣称**"那次就是 ①";成立的是两句更小的话:② 在当前实现下不可达、
  ① 是已知唯一能产生该形状的机制。这条写进 verify,不许在收口时说大。

## Approach

改 `tests/test_ds_shell_core.py::test_b8` 三处,**不动产品代码**:

1. **每轮末尾收掉本轮的两个子进程**(读完两份输出之后再收)——消掉污染源本身。
   赢家 `sleep(120)` 的存在理由是"读输家输出时它得还活着",读完就不再需要它。
2. **开轮前的前置断言**:段内 6 格必须**没有真 OpenDesign 锁在应答**(自己发一次
   协议级握手,收到逐字节 `OK` 才算数),否则当场红在这里
   (消息说清"判据环境脏,不是产品缺陷")。这是**新增的、会自己红的**断言。
3. **失败当场取证**:两条断言(前置 / 恰好 1 份赢)红的那一刻,打印段内每格谁在监听
   (PID + 进程名)、本用例自己还活着的子进程及其端口、两份子进程的 stderr。

断言从「恰好 1 份赢」变成「**段内本来无人** 且 恰好 1 份赢」——**更强,不是更松**。

## Key trade-offs / risks

- 🔴 **最大的风险是这一单本身长得像"改考卷让自己及格"**。防线是红检 R2:
  变异产品代码造出**真的** ②(让两份都让位),新 b8 必须**仍然红在"0 份赢"那条**
  且取证块打印"段内无人"。没有这条收据,本单的所有改动都不作数。
- 前置断言问的是**协议级应答**(握手回 `OK`),不是"有没有人在 listen"。
  ⚠️ 2026-09-21 外审两腿都点出这里原来写的是 connect 探测,而实现从一开始就是握手 ——
  **文档写的不是它跑的东西**,已按实现改写。两者的取舍:connect 更严(陌生程序占位也红),
  但那是 b3/b4 的题;b8 要问的是"段内有没有另一份 OpenDesign 在应答",握手正好问这个,
  而且陌生程序占位时产品**本来就该**照常拿到锁,connect 版会把那一轮误判成环境脏。
  代价:段内坐着一个真 OpenDesign(别的会话/业主自己开着的)时 b8 会红 —— 那正是该红的。
- 取证要读监听者 PID:`ss -ltnpH` 不一定在(或非 root 时看不见 pid),降级问 `lsof -t`。
  ⚠️ 原文这里承诺的是 `/proc/net/tcp` + `/proc/*/fd`,**那条降级从来没实现过**
  (外审 F4 点名);而"两条都拿不到"当时也只是"打印原因",不够 ——
  2026-09-21 补上真正要紧的那一半:**查不出归属就不许分型**,
  取证打印"归属查不出的格子"并直说"先别下结论"(外审 F1,红检 r2d-no-tools 钉住)。
  理由:两种病的处置完全相反,猜一个等于掷硬币,而笃定的错话比沉默更贵。

## Alternatives considered

- **重复跑取多数 / 放宽成 `<=1` / 加 skip**:这是"改考卷让自己及格",不做(proposal 已写死)。
- **只加取证、不消污染**:红仍然会以"0 份赢"的形状出现,每次都要人去读取证块分型。
  报警器照响假警,不如把假警源头消掉、让它只在真事上响。
- **给 b8 固定一段专用端口而不用 `free_port()`**:躲不掉——固定段一样会被自己前几轮的
  存活赢家占住(而且更确定地占住)。根因是赢家不退,不是端口怎么选。
- **动产品代码**:实验把结论钉在 ①,② 不可达 ⇒ 无据可动。

## Test strategy (oracle)

主 agent 亲自写。本节最初只列了三条;实际做出来是 **8 个情景**,这里按实现写
(文档漂移那一课已经上过一次,见 trade-off 里的 ⚠️)。每条都要有收据,
夹具不只问红绿,**还钉红在哪条断言上、分型结论句落在哪一支**:

- **R1(① 场景)**:段内人为放一个真 InstanceLock ⇒ 新 b8 必须红在**前置断言**,
  消息里说得出"段内本来有人"。(旧 b8 在这里红成 `0 != 1`,是本单要消灭的歧义。)
- **R2a/R2b/R2c(② 场景,承重墙)**:变异 `bin/ds_shell_core.py` 造出三种真缺陷
  (让位方向坏 / 扫描恒误判 / 握手恒真)⇒ 新 b8 必须**红在"恰好 1 份赢"那条**,
  取证认定"环境残留:没有",结论句落到"一个窗口都不开"。
- **R2c-lazy(对照)**:把前置探测换成复用产品 `_send_show` 的偷懒版 ⇒ 它**必须**被
  握手恒真骗到、红在前置断言。证明"探测必须独立"不是嘴上说的。
- **R2d(红的第三种长相)**:让位仲裁整个失灵 ⇒ **两份都赢**,业主双击两下开出两个窗口。
  这也是唯一能考取证的场景:两份赢家红的那一刻还在监听,取证必须认出"这是我自己"。
- **R2d-no-ss / R2d-no-tools(降级)**:藏掉 `ss`、或 `ss` 与 `lsof` 都藏掉。
  前者必须仍认出自己;后者必须承认"归属查不出"并**先别下结论**。
- **R3(正常)**:未变异的树上,新 b8 连跑多遍全绿(旧 b8 同样条件下也全绿——
  它平时就是绿的,所以 R3 只证明"没把绿改红",R1/R2* 才是本单的承重墙)。

**这个 oracle 能被什么骗过?**

用户眼里的成功是「业主双击两下,恰好开出一个窗口」。我的断言离它差了**平台**:
这份考卷跑在 Linux、两个 python 解释器、回环 socket 上;业主那台是 Windows、
两个真外壳进程、WebView2 起得慢得多。R2 证明的是"在 Linux 上这条断言抓得住让位缺陷",
**不证明** Windows 上双击两下真能开出恰好一个窗口——那要真机(`_someone_ahead_of`
注释里那段 1~2ms 窗口的测量也只在 Linux 上做过,已写在产品代码注释里)。
全绿而结果仍然错的具体样子:Windows 上两份的 acquire 耗时比 Linux 长一个量级,
双向让位窗口跟着变宽 ⇒ 业主双击两下**一个窗口都不开**,而这份考卷全绿。
接得住那种错的只有真机一趟。**本单不承诺它**,也不许拿本单的绿给它背书。
