# Proposal: opendesign-chat-reconnect

- Date: 2026-08-04
- Status: open

## Goal

聊天连接断掉之后**自己活过来**:指数退避自动重连,重连成功后**重拉一次对话历史**
把断线期间缺的内容补齐。用户不必再手点「重试」,也不会看着一段有洞的对话。

## Motivation

这是 `opendesign-workbench-p1` 归档时(08-04)转出来的两条欠账之一(T6)。
归档结论 `ARCHIVED-SUPERSEDED` 明确写了:**不追认它已完成**,T6 单独留账,
理由是「用户会真碰上」——合上笔记本、切网络、gateway 重启,都会走到这条路上。

现状(08-04 逐行核过磁盘,`web/src/chat/ChatPage.tsx:255`):

```ts
ws.onclose = () => {
  if (!cancelled) setView({ kind: "error", msg: "连接已断开" });
};
```

一次 `onclose` 就把整页打进 error 态,唯一出路是用户自己点「重试」
(`ChatPage.tsx:667`,做法是 `attempt + 1` 触发整条连接 effect 重跑)。
**没有任何自动重连,也没有任何缺口补齐。**

## 真问题(第一性)

- 用户原话(08-04,归档 workbench-p1 时我口头交底后他的处置):「先归档」;
  T6 要不要做**当时没拍**。08-04 晚他说「继续往下做」并问「下一个是什么功能」,
  我推荐 T6、他没有异议 —— **这是我的推荐被默认接受,不是他主动提的需求。**
  归档 verify.md 里我自己写的形态是:「合盖/断网后聊天卡在断开态要手点」。
- 真正要解决的是:**信任**。一个会自己停摆、要人去点一下才继续的助手,
  用户就不敢让它一直开着;而"一直开着"正是这个产品的形态(工作台常驻在旁边)。
- 我在这中间翻译了什么:把「断开」翻译成了**两件事**——「连接没了」(可自愈)和
  「断线期间漏了内容」(要补)。第二件用户从没提过,是我从协议推出来的:
  ws 断开期间服务端不会缓冲,重连后光挂上去只会看到之后的新消息,
  中间那段静默消失且**界面上看不出少了东西**。⚠️ 如果这条推错(比如上游其实会补发),
  第二半就是白做的复杂度 —— **判据里要有一条直接验证"断线期间的消息确实丢了"**,
  不许拿"我认为协议如此"当依据。

## Scope

- in:**纯逻辑层**新增重连策略模块(退避序列、上限、何时放弃、`online` 事件抢跑),
  依赖注入、不碰 DOM,可离线单测。
- in:`ChatPage` 接线 —— `onclose` 不再直接进 error 态,改为「正在重连…」的轻提示,
  按策略自动重试;彻底放弃后才回落到今天的「连接已断开 + 重试」按钮(那条路保留)。
- in:重连并 attach 成功后,**重拉 `/api/chat/thread/<chatId>`**(现成端点,
  `hydrateFromThread` 现成解析),用服务端的完整历史校正本地 transcript。
- in:e2e 一份,真在浏览器里把 ws 掐断,看它自己回来。
- in(**08-04 用户当场加的:「t5b 可以和 t6 一起做对吧」**):T5b 的两小项 ——
  - **tool_hint / progress 降级显示**。现在 `transcript.ts` 顶部注释白纸黑字写着
    这两个事件「一律忽略」⇒ 助手在后台调工具时界面**零反馈**,看着像卡死。
    与 T6 同一类病(界面不说正在发生什么),同批做合理。
  - **链接 target**:助手给的外链现在会顶掉工作台本页,回来还要重连 —— 与 T6 直接冲突
    (自己把自己的连接踹掉)。改成新标签页打开,`rel="noreferrer"`。
  - **判据与 commit 与 T6 分开**,不混在一起判(合并的是发布批次,不是判据)。

## Non-goals

- **T5b 的「代码块高亮」砍掉**(主 agent 建议、08-04 已跟用户说明,他没有反对):
  机主是室内设计师、不是程序员,对话里几乎不出现代码块;为它要么加新第三方依赖
  (供应链多一个)、要么手写残缺子集。**花在他永远看不到的地方。**
  以后真需要再单独加回来。
- **不做离线消息队列**:断线期间用户敲的字不排队等重连后补发。
  那是另一种产品承诺(「我帮你记着并稍后发出」),做错了比不做更伤 —— 单独一单。
- **不动 nanobot 侧协议**,不改 `ds_web` 代理的任何写口:本单前端为主,
  后端只可能读(已有的 thread 端点)。
- 不改登录/口令流(`PasswordRejected` 那条路原样保留:口令失效不是"断线",
  自动重连不许把它盖住)。
