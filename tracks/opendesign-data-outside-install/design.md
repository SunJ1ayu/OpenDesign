## 对差异(B 卷改了我五处,逐条判)

1. **数据落点:`UserData` → 采纳 B 的 `%LOCALAPPDATA%\OpenDesign\Data`。**
   我原打算塞进 `UserData`(理由:那儿已经是 HOME、少一个概念)。B 指出 `UserData` 是
   **nanobot 的家**(它的 dream 进程会在自己家里写记忆),把业主档案混进去,
   "备份哪个目录"和"谁有权改这些文件"两件事都变糊。**B 对。**
2. **`DS_DATA` → `DS_DATA_ROOT`,而且"设了但无效就拒绝启动,不许静默回退"。**
   我在 A 卷里把"忘了设 env ⇒ 静默写回安装目录"列成了最大的坑,却只打算靠判据盯;
   B 把它变成**运行时行为**:显式设置无效 = fail closed。**采纳** —— 静默回退正是
   "失败没有声音"那一类,这台机器上栽过三次(pip 环境标记、git add 忽略、管道吃 rc)。
3. 🔴 **B 戳穿了我 oracle 的一个盲区,这条最值钱。**
   我的不变量闸是"跑完写口后安装目录哈希不变" —— 它只看得见**程序写的**东西。
   B 点名了另一类:**用户手工放进去、程序只读不写的数据**(`refs/` 里的真图片就是这样进来的,
   `taxonomy.json` 同理)。这类东西我的闸**永远不会红**,而卸载照样删它们。
   ⇒ 判据必须补一路:**"从根目录读入的、用户可编辑的内容"也算数据**,
   靠"扫读口"而不是"扫写口"得到。**这正是双出要买的那种东西:我框子里照不到的地方。**
4. **`set_workspace` 拦截改成"双向重叠"**:不只是"不许在里面",还要"不许把它包住"
   (工作区根设成 `%LOCALAPPDATA%` 就把整个应用状态根罩进去了)。**采纳。**
   B 另外建议校验 `projects_dir` 是安全相对路径 —— **采纳**(同一处写口,顺手)。
5. **迁移:我写"不做",B 说"必须做"。判:折中,做**"检测 + 一次性搬,不覆盖"。
   B 的完整仪式(跨卷 copy+验哈希、冲突报告、迁移收据、保留旧树)是给"已经有大量数据"
   写的;而事实是**这台机器上装完就卸了、一条档案都没产生过**。
   但 B 的核心担心成立且便宜:业主手上**已经有 0.86.0 的安装器**,他完全可能先用出几个项目,
   下一版再装 ⇒ 那时"档案看起来没了"(其实还在旧目录)。
   ⇒ 做最小的一份:启动时发现安装目录里有遗留数据就**搬过去,同名不覆盖**,搬完记一行日志。
   两边同在 `%LOCALAPPDATA%` 下,不存在跨卷。

**B 提出、我判为不采纳的一条**:把代码根 chmod 成只读来当判据。root 跑测试时
**权限位对 root 无效**,这个闸在本机是假的(它会永远绿)。哈希比对留作主判据。

**B 的第 6 问答得比我狠,记账不改**:它说这个方向最可能错在
"`LocalAppData` 这个默认落点" —— 业主可能觉得档案是**他的文档**,应该看得见、能备份、能同步。
现在不改(先把"卸载不丢"这件事做对),但**触发条件写死在这儿**:业主一旦提出
"我想自己看/同步这些档案",落点就该改成他选的目录,而不是再论证一遍 LocalAppData 合理。

## Approach

### 一句话

**安装目录在运行时是只读的。** 业主的东西一律落在**数据根**下,数据根默认等于 `ds_root`
(现有安装零变化),Windows 包把它指到 `%LOCALAPPDATA%\OpenDesign\Data`(**折 B 卷后改的落点**)。

### 1. 数据根怎么解析(唯一真相源)

`bin/ds_common.py` 加一个函数,全仓只有它一处决定这件事:

```python
def data_root(ds_root: str) -> str:
    """业主的东西落在哪。默认 = ds_root(git-pull 安装保持原样);
    Windows 包由外壳设 DS_DATA_ROOT 指到安装目录之外。
    **设了但不可用(不存在且建不出来 / 不是目录)⇒ 抛错,绝不静默回退 ds_root。**"""
```

- 默认值 = `ds_root` ⇒ **本机开发仓、公司机、家里机全部零变化**,1136 条判据不用改题面。
- Windows 包:`ds_shell_core` 造子进程环境时加 `DS_DATA_ROOT=<…\OpenDesign\Data>`,
  与已经在传的 `DS_ROOT` 并列(三个 MCP + ds-web 都吃这份 env)。
- 🔴 **fail closed(折 B 卷)**:"设了但无效就静默回退安装目录"是本单最危险的失败形态——
  一切看起来正常,而业主的东西正在往会被删的地方写。**宁可起不来。**
- **为什么不是"把 ds_root 整个挪出去"**:`ds_root` 里装的是**代码**(bin/web/assets/
  workspace 契约),更新时要整棵换掉;数据必须活过那次换。两者混在一个根下正是本单要拆的。

### 2. 哪些东西跟着搬(读写口清单)

| 名字 | 现在 | 之后 |
|---|---|---|
| `projects/`(含 `.trash`) | `ds_root/` | `data_root/` |
| `clients/` | `ds_root/` | `data_root/` |
| `index.md` | `ds_root/` | `data_root/` |
| `refs/` + `refs-index.md` + `refs-vocab.md` | `ds_root/` | `data_root/` |
| `organize/`(plans、audit.log、.apply.lock) | `ds_root/` | `data_root/` |
| `config/workspace.json`、consent、user taxonomy | `ds_root/config/` | `data_root/config/` |
| `bin/ web/ assets/ workspace/ 版本号.txt` `config/nanobot.config.windows.jsonc` | `ds_root/` | **不动(代码)** |

⚠️ `config/` 是**混的**:模板是代码、workspace.json 与 consent 是数据 ⇒ 按文件分,不按目录分。

**这份清单是机械抽出来的,不是我列的**(2026-08-15 实扫):`bin/*.py` 里
`os.path.join(<…ds_root…>, …)` 共 **47 处、11 个文件**,而且 **47 处全是数据** ——
`ds_root` 唯一的代码用途在 `bin/ds_provision.py`(pathlib 写法,读 `config/` 里的模板和
`bin/ds_merge_config.py`)。⇒ 得到一条能上闸的规则:**`join(ds_root, …)` 一处都不该再有**,
数据一律走 `data_root(ds_root)`。

⚠️ **但机械扫写口扫不到一整类**(B 卷戳穿的):**用户手工放进去、程序只读不写的东西** ——
`refs/` 里的真图片就是这么进来的(`ds_refs.add_ref` 要求文件**已经在** `refs/` 底下,
它只往索引里记一笔)。这类数据不出现在任何写口里,却照样会被卸载删掉。
⇒ 清单要**读口也扫一遍**,`refs/` 与 `config/taxonomy` 都是这么找出来的。

### 3. 那道拦截(业主追问逼出来的)

`set_workspace` / `bind_project` 的根:与**安装目录**、与**应用状态根**
(`%LOCALAPPDATA%\OpenDesign` 整个)**任一方向重叠都拒绝** —— 相等 / 在它下面 / 把它包住
(折 B 卷:我原来只想到"在里面";把工作区设成 `%LOCALAPPDATA%` 就是"包住"那一种)。
理由是"删得掉的地方不能放他的原件"。拒绝时说人话并把路径念给他听。
顺手:`projects_dir` 校验成安全相对路径(解析后仍在 workspace root 内且确为目录)。
—— 现在只校验"绝对路径 + 目录存在"(`ds_tools.py:905-913`),这道拦截**从来没有过**。

### 3b. 迁移(折 B 卷后从"不做"改成"做最小的一份")

启动时:数据根 ≠ ds_root 且 ds_root 底下发现遗留数据(清单里那些名字)⇒ **一次性搬过去,
同名一律不覆盖**,搬完在日志里记一行。两边同在 `%LOCALAPPDATA%` 下,不跨卷。
理由见「对差异」第 5 条:业主手上已经有 0.86.0 的安装器,他完全可能先用出几个项目。
**不做 B 卷那套完整仪式**(跨卷 copy+验哈希、冲突报告、迁移收据、保留旧树)——
那是给"已经有大量数据"写的,这里的实际量是 0。

### 4. 文案跟着改

卸载确认页那句、可选框的描述,改成与实现一致(现在写的是假话)。

## Key trade-offs / risks

- **`DS_DATA` 没设 = 老行为**:这是最大的安全垫(现有两台机器不受影响),
  也是最大的坑 —— **Windows 包忘了设 env,就静默退回把数据写进安装目录**,
  而且一切看起来正常。⇒ 判据必须有一条专门问"包里那条 env 真的传到了三个 MCP 与 ds-web"。
- 一次性改 ~25 个调用点,漏一个就是"大部分搬了、有一个还在老地方",
  而那一个照样会被卸载删掉。⇒ **不能靠人眼数**,见下面的 oracle。
- 不做迁移:如果将来有人在 Windows 包里已经产生过档案,升级后会"看起来数据没了"
  (其实还在老目录)。本单业主机器上不存在这种情况,**但这条要写进真机清单让他确认**。

## Alternatives considered

- **让卸载器"跳过"那几个子目录**:白名单藏在一棵正被 `RMDir /r` 删的树里,
  且更新换整棵树时照样丢。治标,否。
- **软链接/junction 把数据目录接进安装树**:Windows 上要权限、备份工具语义混乱,
  且 `RMDir /r` 对 junction 的行为是我在 Linux 上验不了的那一类。否。
- **把 `ds_root` 整个搬到 LOCALAPPDATA、安装目录只放启动器**:更新时要替换代码,
  等于把"可换的"和"不可换的"继续绑在一起,问题原样还在。否。

## Test strategy (oracle)

主 agent 写,不外包。三层:

1. **不变量闸(本单最重的一条,动态)**:设 `DS_DATA=<临时目录>`,
   把**所有写口**跑一遍(建项目 / 写档案 / 加参考图 / set_workspace / bind_project /
   整理计划落盘与执行 / consent 落盘),然后断言:**`ds_root` 那棵树前后哈希一致**
   (逐文件 sha256,忽略 `__pycache__`)。
   - 这比"列一份数据清单"强在:**它不需要我列全** —— 将来谁再加一种数据文件,
     只要写进安装目录就当场红。我这次栽的正是"我把位置做成了闸、没把清单做成闸"。
2. **env 真的传到了**(防上面那个坑):断言外壳造出来的子进程环境里
   `DS_DATA` 存在且指向 UserData —— 三个 MCP 与 ds-web 四份 env 都要问到。
3. **拦截闸**:`set_workspace` 给安装目录里/数据根里的路径 ⇒ 拒绝 + 人话 + 不落盘;
   给正常路径 ⇒ 照常成功(**双向验**,别造一个"永远拒绝"的闸)。
4. **老行为零变化**:不设 `DS_DATA` 时,现有 1136 条判据 + 36 条 e2e 全绿。

**这个 oracle 能被什么骗过?**

- **骗法一:写口没跑到。** 闸①是"跑一遍写口再比哈希",如果某个写口我没在判据里调用,
  它就永远不会暴露。⇒ 写口清单必须**从代码里机械抽**(grep 出所有 `join(ds_root, …)`
  的数据名),不是我凭记忆列。**这条是本 oracle 最脆的地方,先写在这儿。**
  ⇒ 已上**静态闸**兜底:`bin/*.py` 里不许再出现 `os.path.join(<ds_root>, …)`
  (`ds_provision.py` 那两处代码路径显式白名单)。写口没跑到,静态闸照样红。
- 🔴 **骗法五(B 卷戳穿的,我 A 卷完全没想到):只读的用户数据。**
  程序从不写 `refs/` 里的图片、也不写 `config/taxonomy.json`(用户手工放/改),
  ⇒ **哈希闸永远不会为它们红**,而卸载照样删。
  ⇒ 判据补一条**不靠写口**的:拿一份"用户手工放进去的东西"(一张图 + 一份 taxonomy)
  放进数据根,跑完全流程后断言**程序仍然找得到它们**(即读口也走了数据根)。
  另加 B 卷的 **canary**:往 ds_root 塞一个清单里没有的 `future-kind/canary.bin`,
  断言它**不会被当成代码悄悄忽略** —— 迁移要么带上它、要么明说"有东西我没认识"。
- **骗法二:哈希比的是空树。** 如果测试里 `ds_root` 用的是个空的临时目录,
  "前后一致"毫无意义 ⇒ 必须拿**真的仓库树**(或至少含 projects/refs/config 的仿真树)当基线,
  且断言基线**非空**。
- **骗法三:`DS_DATA` 在测试进程里被别的判据串味**(08-15 刚栽过一次同款:
  模块级改 `os.environ` 把另一份判据整块变成 SKIP)⇒ 设/还原都在 setUp/tearDown 里。
- **骗法四:闸②问的是我自己造的 env,不是真的那份。** 必须调 `ds_shell_core` 真的那个
  造环境函数,而不是在判据里重写一遍期望(同 08-14「两张考卷对同一前提做了相反假设」)。
- **它问不出的**:Windows 上 `RMDir /r` 到底删了什么 —— 那只有业主真机能答,
  已写进真机清单(装 → 建一个项目 → 卸载 → 档案还在不在)。
