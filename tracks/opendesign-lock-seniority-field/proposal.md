# Proposal: opendesign-lock-seniority-field

- Date: 2026-09-02
- Status: open(未开工 —— 由 opendesign-slow-lock-scan 的 accepted deviation 派生)

## Goal

给单实例锁的线上协议加一个**先来后到**的字段,让"我和对面谁先站住"这件事
不再只能从端口号大小推断。这样 `_someone_ahead_of` 就能在**不引入双向让位**的前提下
问整段,把今天结构上够不着的那条拓扑盲区堵上。

## Motivation

`opendesign-slow-lock-scan` 收口时唯一敞着的数据面缺口(那一单已记为 accepted deviation)。

**盲区长什么样**(四步,每步都可能真实发生):
1. 业主启动第一份 OpenDesign,`base` 端口正被某个陌生程序占着 ⇒ 第一份落在 `base+1`;
2. 那个陌生程序后来退出了 ⇒ `base` 空出来;
3. 业主启动第二份,快扫**漏判**第一份(要求 connect 落在实测尾巴上,~1% 量级);
4. 第二份绑上 `base` ⇒ `_someone_ahead_of(base)` 只问 `p < base` ⇒ **前面一个口都没有**
   ⇒ 放行 ⇒ **两份 OpenDesign 并存,两个后台对着同一个 data_root**。

第 4 步是**结构性**的,不是概率:兜底那一层在这个拓扑上根本够不着。
今天唯一的防线是第 3 步的 connect 期限(`lock_timeouts()` 两个 1.5s,判据 l2 钉着下限
≥1.5,不许再往下调)—— 也就是说**整条防线只有一层**,而且它防的是"漏判"这个前提本身。

## 真问题(第一性)

- 用户原话:(本条不是业主报的,是 2026-09-01/02 两轮 panel 评审逼出来的)
  业主可观察到的形态会是:"我明明只开了一个,它把我的改动弄丢了/覆盖了"。
- 真正要解决的是:**同一台机器上不许有第二份 OpenDesign 写同一份档案**。
  端口号顺序只是"谁先到"的一个**代理变量**,而它在上面那条拓扑里恰好失真。
- 我在这中间翻译了什么:把"单实例"翻译成了"占住最靠前的那个锁位"。
  这个转译在陌生程序占过 base 的机器上不成立 —— 这一单就是来修这个转译的。

## Scope

- in: 锁协议加先来后到字段(候选:握手回帧里带上第一份的启动时间戳 / 单调序号 / 锁纪元);
- in: `_someone_ahead_of` 改成问整段并按该字段裁决,让位方向仍然唯一;
- in: 判据 —— 上面那条四步拓扑必须有一条判据钉着(今天没有);
- in: **第一件事不是加字段,是先证明便宜修法不够** —— 见下面"这一单的第 0 步"。
- in: 对照组 —— `probes/yield_race.py` 已经是现成的验收台:它同时量
  (1) 盲区堵不堵得住 (2) 同时启动活下来几份 (3) 错开启动时还剩多少危险。
  新方案的验收线:**盲区堵住 且 各错开档上 0 存活恒为 0 且 存活 2 份恒为 0**,
  而且要**连跑几遍比** —— 0ms 那一档单遍方差极大(同一支探针给出过 6/30~21/40)。

## 这一单的第 0 步(2026-09-02 补,改掉了它原来的立论)

**原来的立论已经被自己的收据推翻**:这份 proposal 最初写的是
"A 放行 / B、C 都出现 0 存活,没有一组两件事兼得 ⇒ 必须加字段"。
但那三组数全是 `threading.Barrier` 对齐的**近同时启动**;第三轮评审(subglm)与
主 agent 自审 D2 各自独立指出这一点后补量错开启动,结论翻了:

    组            0ms       1ms     2ms   5ms   10ms   50ms  200ms  500ms
    A 树上的实现    0         0       0     0     0      0     0      0
    B 问整段       10~13/40  1/40    0     0     0      0     0      0
    C base回头看   6~21/40   0       0     0     0      0     0      0

⇒ **双向让位的危险窗口只有 1~2ms 量级**。所以 C(甚至 B)不再是"行不通",
它是一笔取舍。**这一单的第 0 步就是把这笔取舍算清楚**:

1. 量 C 在真实场景下的危险窗口:两个**进程**(不是同进程两线程)、Windows 上,
   两次 acquire 的时间差分布长什么样 —— 落进 1~2ms 的概率有多大;
2. 如果 C 够(极窄窗口 vs 数据面盲区,业主拍板过取舍方向),那这一单就**只做 C**,
   不做协议改动,先来后到字段留成 backlog;
3. 只有当 C 也接不住(比如业主那台机器上两次 acquire 真的常常撞进同一毫秒),
   才做原方案的先来后到字段。

**别跳过第 0 步直接做字段** —— 那正是这份 proposal 第一版犯的错:
拿一个量具造出来的现象当"结构性",然后据此选了更贵的那条路。

## Non-goals

- 不动 `lock_timeouts()` 的两个 1.5s(那是另一层防线,判据 l2 钉着);
- 不做跨机器/跨用户的实例仲裁;
- 不在这一单里查"业主那台 Windows 上 6 个锁位为什么全耗满"(仍然敞着,见
  `tracks/opendesign-slow-lock-scan/proposal.md` 的"还不知道的")。

## 已经有的家当(别重做)

- `tracks/opendesign-slow-lock-scan/probes/yield_race.py` —— 两份同时启动 × N 轮 ×
  两组对照,直接量"活下来几份"。这一单的验收就靠它。
- 收据 `tracks/opendesign-slow-lock-scan/evidence/20260902T005336Z-01-yield-race-30-rounds.txt`
  是改造前的基线。

## 风险

- 数据一致性(两份写同一个 data_root)⇒ impact-risk 预期 **high**;
- 改的是**并发裁决**,而 2026-09-01 的实测已经证明:朴素的"问整段"会把
  一大片同时启动变成一个窗口都不开(比例方差大,别引用比例;稳的是它会发生)。
  **任何方案都必须先过 yield_race 的三组对照,而且连跑几遍。**
