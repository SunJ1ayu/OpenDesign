Core bet: 这次改版真正会咬人的缺陷是**状态类缺陷**(残留的「正在思考」、重开后冒回英文、停止标记挂在本已说完的答案上、换了模型按钮文字不对、问候语停在打开那一刻),不是功能不存在;所以考卷的主轴应当是"用户可见状态",而停止键的时序竞态不靠手快去点,靠**控制助手速度**把它变成可复现的固定状态。

How it works:
- 先立一张状态表(单聊一栏):空草稿 / 有草稿 / 草稿带图(1~4 张)/ +菜单开 / 斜杠列表开(含筛选后)/ 回复中·思考 / 回复中·出字 / 已停止 / 出错后。再立事件集:点+、选技能、打/、打字筛、↑↓、Enter、Tab、Esc、拖图、Ctrl+V、点↑、点■、切栏、切模型、重开窗口。
- 每个矩阵格子的期望结果写成**用户看得见的确切东西**(控件的字/图标、光标位置、气泡文案、灰字),而不是"应正确"。三处聊天栏各是一张同样的表——因为它们"各聊各的",一张表填三遍,不一致本身就是缺陷。
- 每条用例强制以一次**重观测**收尾:切到别的栏再切回 / 关窗重开 / 翻历史回看。停止有关的用例全部收敛到五个固定落点(刚发、思考中、出字中、快说完、已说完一瞬),每个落点只问两件事:屏上剩什么 + 重开后剩什么。
- **确定性刺激代替手速**:用一个故意欠费/错 Key 的供应商拿确定性的出错与改写英文;用超长粘贴把"思考"拉到几十秒,使"思考中点停止"可以稳定重演;正常流用一个守规矩的供应商取"出字"。这样题面点名的失败路径类才可复现。
- 两个顺带小修需要一张**字符串对照表**当 oracle(哪些是后台改写、哪些是厂商原话、英文系统消息对应的中文),这张表要向后台要,不能凭题面猜。
- 交付仍按题面四件套(故事 G/W/T、编号用例表、探索式任务、待拍板疑问)组织,但表里的"期望结果"列全部来自上面那张状态表,不另起炉灶。

Best at: 抓"界面在骗人"的那一类(停止后转圈不收、已停止贴在完整回答后、重开后英文回来、按钮厂商名对不上、问候语不随时间走),并且给时序类用例一个不依赖手速的可复现判据。

Sacrifices: 不深入后台真动作(账本是否真写入、文件是否真移动)——题面已明确"动作可能已完成只是不汇报"这次不改,所以这条**只能验"有没有对用户误报",不能验"动作做没做"**,这个取舍要写死在用例里;重开/切栏使回看成本高、跑一轮慢。若真正的风险在流式协议/模型层而非 UI 状态,这套方向就偏了。

Blind spots in the brief:

- **厂商短名的规则只覆盖了"带括号"的情况**:全角括号（小米）、多个括号、名字本身就是括号、名字前后空格、自定义供应商与内置重名都没说;而且同一模型名可能挂在两家(GLM 套餐 vs GLM 按量),按钮上到底显示哪一家 = 用户判断"这次扣谁的钱"的唯一线索,规格太薄。
