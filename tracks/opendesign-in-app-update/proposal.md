# Proposal: 应用内更新(软件自己发现新版、问一句、装上、并回显新版本号)

- Date: 2026-09-07
- Status: open

## Goal

把业主现在这五步手工活去掉:**打开浏览器 → 找到 GitHub 仓库 → 翻 releases → 下 43MB →
双击重装**。改成:软件自己发现有新版 → **问他一句** → 他点"更新" → 装好 → 重新打开 →
**软件自己报出新版本号**。

**收口判据是最后那半句**:更新成功 = **新起来的进程自己在 `/api/health` 报出新版本号**,
不是"安装器退出码 0"。(CLAUDE.md「在使用现场验证」那条规矩的形状:盘上有新文件 ≠ 部署了。)

## 现状事实(全部本轮实测/读源码得出,不是推测)

1. **全仓零处更新检查代码。** `grep -rniE "update|升级|新版本|releases/latest"` 扫
   `bin/ installer/ src/`,命中的全是 `update_client` / `update_ref` 这类业务写口,
   与"程序自我更新"无关。⇒ 这一单是从零开始,不是改现有逻辑。

2. 🔴 **GitHub 那个最直觉的接口在本仓永远返回 404 —— 而且是静悄悄的。**
   ```
   GET https://api.github.com/repos/SunJ1ayu/OpenDesign/releases/latest  →  http=404 "Not Found"
   ```
   原因:`/releases/latest` **按设计跳过 prerelease**,而本仓 **10 版全是 prerelease**
   (`gh release list`:0.93.0~0.98.3 无一例外)。
   ⇒ 照直觉写法做出来的"查更新",在这个仓库上**永远查不到任何版本,且不会报错**
   —— 一条天生的恒绿路径。必须改用 `GET /releases`(含预发布)再自己挑,
   **并且判据要钉住"预发布也算数"**,否则哪天有人"顺手改回标准接口"没人会发现。

3. **安装布局是平铺覆盖,没有版本化组件、没有指针。**
   `installer/OpenDesign.nsi:113-117`:`SetOutPath "$INSTDIR"` + `File /r "payload\*"`,
   装进 `$LOCALAPPDATA\Programs\OpenDesign`(第 49 行)。
   ⇒ `opendesign-windows-installer` 的 tasks.md 第 229 行写的
   「版本化组件 + 指针在这一单落地」**从来没有落地**(至今是未打勾项)。
   本单如果要走"只下 1.1MB 那层",等于先做一次安装布局重构。

4. 🔴 **本单最危险的失败形状,`.nsi` 自己在注释里写着**(第 92 行):
   > 程序在跑的时候文件是锁着的,而 `RMDir /r` 删不掉会**悄悄**跳过

   ⇒ 边跑边更新 = **一半新一半旧,而且一声不吭**。
   任何做法都必须先把跑着的东西收干净(外壳 + 托盘 + ds_web + nanobot),再替换文件。

5. **已经有一条不用麻烦业主的验证路径。**
   `.github/workflows/windows-package-probe.yml` 能把**真安装包**搬上云 Windows 机器:
   下载 release 资产 → 静默装 → 启动 → 截图 → 收日志 → 一份 `verdicts.tsv` 收据 +
   **住在另一个文件里的第二道退出闸**。它接受 `tag` / `asset` 两个输入。
   ⇒ 本单可以端到端真验:**装 0.98.2 → 在机器上走一遍应用内更新 → 断言它变成 0.98.3
   且还打得开**。这是本项目头一回有"不烧业主真机就能验完"的更新类改动。

## 三个候选做法(design 里定稿)

| | 做法 | 下载量 | 复用已验产物 | 能不能原子切换/回滚 |
|---|---|---|---|---|
| A | 下官方安装器 → 静默跑它覆盖安装 | 43 MB | ✅ 就是业主双击的那个 | ❌ 中途挂 = 半新半旧 |
| B | 自己发一个 zip,更新器解压覆盖 | 小 | ❌ 新增第二种发布物 | ❌ 同上 |
| C | 版本化组件 + 指针原子切换 | 最小 | ❌ 要重构安装布局 | ✅ |

**我的倾向是 A 做第一刀**,理由写进 design(并在那里攻自己的题):
业主的痛点是**那五步手工活**,不是 43MB;而 A 是唯一"不新增任何发布物、
更新用的就是我们每次都逐字节比对过的那一个 exe"的做法。
⚠️ 但要如实说:**A 与仓库里已经写下的意图(第 3 条那个 C)相反** —— 这一点必须在
design 里正面回答,不能默默绕过。

## 业界对照(业主 2026-09-07 当场问「成熟的软件工程也这么做吗」)

**两派都是成熟做法,A 不是偷工减料。**

| 谁 | 做法 | 对应本单 |
|---|---|---|
| Chrome | `Application\<版本号>\` 版本化目录 + 指针原子切换 + 差量下载 + 独立后台更新器,旧版留着可退 | C |
| Firefox | MAR 包 + **独立 `updater.exe`** 在主程序关闭后施工;partial 失败自动回落 complete | C |
| **VS Code (Windows)** | **下载完整 setup.exe → 静默安装 → 重新拉起** | **A** |
| Electron 生态(`electron-updater` NSIS) | 同上;blockmap 差量只是可选加速层,失败回落整包 | **A** |
| Sparkle (macOS) | 下整包 → **验 EdDSA 签名** → 整体替换 | A + 验签 |

⇒ **A 是主流做法之一,且 A→C 是加一层,不是推翻重来。** 差量下载在所有这些实现里
**都带整包回落**,没有一家敢只留差量那条路 —— 这反过来说明先把整包这条路做扎实是对的次序。

### 但业界标配里有三件本单原计划缺的,现在补进来

1. **验签名。** Sparkle 验 EdDSA、Firefox 验 MAR 签名、Chrome 全链签名。
   **我们做不到 —— 没有代码签名证书。** 如实记为缺口,不假装有:
   本单的信任根就只有 **HTTPS 到 github.com** 这一条,sha256 与 exe 同源发布,
   **挡得住"下坏了/被中间人截了包",挡不住"GitHub 账号被盗"**。这句话要原样写进 design。
2. 🔴 **必须有退路 —— 这条推翻了我原来的 A。** Chrome 把旧版目录留着。
   我原来的 A 是**直接覆盖安装**:更新到一半断网/断电/杀软拦一下,
   **业主可能连旧版都打不开了**。这是本单唯一不可接受的结局(见「开工前要先答的」第 1 条)。
   ⇒ 改成:**更新前先把整个 `$INSTDIR` 备份一份 → 装新版 → 起来并回显新版本号才算成功
   → 成功才删备份;起不来就自动把备份换回去。** 43MB 的一份拷贝,磁盘上不值钱。
3. **动手的必须是另一个进程。** 跑着的程序在 Windows 上覆盖不了自己的文件
   (`.nsi:92` 那条注释就是这件事)。A 里这个"另一个进程"天然就是安装器自己 ——
   但**收摊 → 启动安装器 → 重新拉起**这条链必须写死、并且有判据。

## Non-goals(本单明确不做)

- **不做静默自动更新。** 必须他点头才动。(装完的东西是他的,不是我们的。)
- 不做代码签名(没有证书,那是另一件事)。
- 不做"回滚到任意历史版本"(**但"退回上一版"是必做的**,见业界对照第 2 条)。
- 不顺手重构安装布局(那是 C,真要做单独一单)。

## 开工前要先答的(design 的任务)

1. 更新失败 / 断网 / 下到一半 时,业主的软件**还打得开吗**?这是唯一不可接受的结局。
2. 校验:下回来的 exe 凭什么信它?(HTTPS + 我们自己发的 sha256 —— 但两者同源,要如实写清信任根到底在哪。)
3. 谁来收摊(退出跑着的进程)、谁来重新拉起、以及**新版本号由谁来回显**。
